# Chapter 78 answer quality

- Solve the exact question and every requested deliverable. Related background does not replace an answer.
- Read the full question before editing. Do not fill answers by category, keyword, title alone, or generic templates.
- For coding tasks, give the actual implementation in the answer, explain inputs and outputs, and run behavior checks. Preserve stated constraints (for example, no attention means no attention).
- Include readable PyTorch code for neural-network and tensor-training questions. Use NumPy where it helps derive or implement numerical algorithms. Explain shapes and target alignment.
- Reuse supplied data contracts. If code, data, or requirements are missing, say exactly what is unavailable; distinguish a chosen demonstration fixture from the original exercise. Do not invent hidden-test results.
- For system design, answer the requested API/data model/consistency/scaling/failure details and explain the accompanying diagram. A generic architecture picture is not a complete design answer.
- Use plain connected explanations: problem, approach, why it works, worked example, edge cases and validation. Use LaTeX for equations where helpful.
- Preserve W/F identifiers, priority groups, manual anchors and navigation links. Do not claim a question is verified solely because a page exists, has code fences, or reaches a word count.
- Existing local changes belong to the user. Work on assigned files only; never revert unrelated edits. The coordinating agent owns shared catalogs, git commits and publication during a parallel review.
