## Question

Problem: Implement Two Distributed Matrix Multiplication Strategies (DP and FSDP) Using a Communication Simulator

Implement distributed matrix multiplication C = A @ B across world_size simulated ranks, once as Data Parallel (DP) and once as Fully Sharded Data Parallel (FSDP), using only a provided Communicator to exchange data between ranks.

Provided
Communicator(world_size) with one collective, all_gather(rank, data) -&gt; list: every rank contributes data and receives the list of all ranks' contributions, ordered by rank. It is barrier-synchronized, so every rank must call it the same number of times in the same order.
run(fn, A, B, world_size): starts one thread per rank, calls fn(A, B, rank, world_size, comm) on each, and returns rank 0's result.

### Requirements

1. dp_mat_mul(A, B, rank, world_size, comm) — the input A is sharded by rows across ranks and the parameters B are replicated on every rank. Compute this rank's rows of C, then gather the outputs so every rank returns the full C.
2. fsdp_mat_mul(A, B, rank, world_size, comm) — the parameters B are sharded across ranks (each rank owns only one shard, for example a block of columns). Temporarily gather the shards to reconstruct B, multiply this rank's row-shard of A, then gather the outputs so every rank returns the full C.
3. Both results must match single-machine A @ B (checked with np.allclose).
4. State which dimension you shard for A, B and C, and where each communication step happens (input distribution, parameter gather, output gather).
5. Avoid deadlocks: all ranks issue the same collectives in the same order.
Input
A: NumPy array of shape (m, k); B: NumPy array of shape (k, n).
rank in [0, world_size), world_size &gt;= 1, and a shared Communicator.
Output

The full matrix C of shape (m, n) on every rank.

Constraints and edge cases

```text
world_size = 1 must reduce to plain A @ B for both strategies.
```

m (and, for FSDP, the sharded dimension of B) need not be divisible by world_size; uneven shards must still give the correct result.

### Examples

A is 4x3, B is 3x5, world_size = 2: run(dp_mat_mul, A, B, 2) equals A @ B.
A is 8x8, B is 8x8, world_size = 4: run(fsdp_mat_mul, A, B, 4) equals A @ B.
A is 7x5, B is 5x6, world_size = 3 (uneven shards): both strategies equal A @ B.

## Worked solution

### Solution outline

1. Use deterministic array_split row boundaries for A, including empty shards when ranks exceed rows. In DP each rank multiplies its A rows by replicated B, all-gathers local C row blocks and concatenates them in rank order.
2. For the exercise’s FSDP simulation, define B shards explicitly, for example by output columns. Each rank all-gathers its B shard and reconstructs B by column concatenation, then multiplies its own A row shard.
3. All-gather the local C row blocks and concatenate to return the full C on every rank. DP uses one collective here; FSDP uses parameter gather followed by output gather, in identical order on every rank.
4. Test rectangular/uneven dimensions, one rank and empty shards against A@B. This is a communication exercise, not a full FSDP optimizer/autograd implementation; state the peak memory cost of temporarily gathering all B.

### Understand why the approach works

#### Follow tensor ownership and the resource bottleneck

For every major tensor, state who owns it before and after each collective. Data parallelism divides examples; tensor parallelism divides operations/weights; pipeline parallelism divides layers. Their communication and memory effects differ, so a diagram saying “use more GPUs” is incomplete.

For $C=AB$, $A\in\mathbb R^{m\times k}$ and $B\in\mathbb R^{k\times n}$, a row partition gives

$$
C_r=A_rB,\qquad C=\operatorname{ConcatRows}(C_0,\ldots,C_{p-1}).
$$

Concatenating output shards is different from summing partial products. Backward communication depends on which variables were replicated and where multiple contributions to the same derivative must be added.

Estimate the bottleneck with a roofline bound:

$$
\text{attainable FLOP/s}\leq
\min\!\left(F_{\rm peak},\;\text{bandwidth}\times\frac{\text{FLOPs}}{\text{bytes moved}}\right).
$$

Then add synchronization, imbalance, launch and checkpoint overhead rather than treating the ideal bound as achieved speed.

For a platform/scheduler, distinguish desired state, observed state and durable job completion. Launching a container or receiving a provider response does not prove the computation succeeded. Checkpoint application state, fence stale owners, publish only complete artifacts and monitor both utilization and tenant wait time. A design that maximizes utilization by starving a large job violates a different important service objective.

### Work a small example

A:(5,3), B:(3,4), world_size=2 gives A row counts 3 and 2; concatenating the two local outputs must recover (5,4), not sum them.

### Edge cases and common mistakes

Calling the same barrier different numbers of times across ranks, or concatenating B column shards along the row axis.

### Check your reasoning on related cases

**Compare data, tensor and pipeline parallel training.** Two data-parallel workers with local batch 8 process a global batch of 16 if one synchronized update uses both batches without extra accumulation.

Where does gradient accumulation fit? It increases effective batch per update without adding devices, at extra sequential compute time.

**Derive the backward communication of a row-sharded linear layer.** For W=[W0 W1], dX=dY0*W0ᵀ+dY1*W1ᵀ. Neither worker's contribution alone is the complete input gradient.

When is reduce-scatter useful? When the summed input gradient should also remain sharded for the next operation.
