## Question

Fee Calculation with Boolean Flag and Numeric Parameter

Suppose there are only two parameters: one can be a T/F flag and the other can be any number X. Under this condition, how would you design a mechanism to calculate three different fee schedules? The fee per share increases with longevity; let's say 0.2, 0.3, 0.4. The cap is 1.5.

## Worked solution

### Solution outline

1. Clarify whether X is quantity, holding duration, an encoded tier or another variable, and whether the 1.5 cap is total or per-share. The two inputs alone do not uniquely identify an unstated fee contract.
2. Under a declared example, let X be nonnegative holding duration, thresholds t1<t2 select rates 0.2/0.3/0.4, and the boolean choose standard versus a documented alternative schedule. Represent rates/thresholds as a table, not deeply nested duplicated formulas.
3. For a total-fee convention fee=min(1.5,base_rate(X)*quantity), quantity must be fixed or separately known; it cannot be recovered from an X already used solely as duration. For a per-unit convention cap the rate instead.
4. Validate boundary equality, negative/nonfinite X and rounding. Explain exactly what policy information is missing rather than silently inventing thresholds or overloading one scalar with multiple meanings.

### Understand why the approach works

#### Turn prose policy into a versioned decision table

List the inputs, units, effective date and precedence of each rule. A threshold example is incomplete until equality and rounding behavior are specified. If the prompt supplies two inputs but the fee depends on an independent quantity and duration, name the missing information rather than encoding an unstated policy.

Store rule versions and validity intervals so a past result can be reproduced. Calculate money using an explicit decimal/minor-unit convention, and return a breakdown with the applied version when users need an explanation. A cache key must include every dimension that changes the result.

State transitions involving rewards or payments need idempotency and an audit trail: a replayed review submission cannot legitimately grant a second bonus. Separate eligibility validation, moderation/publication and reward posting so partial failures have visible states.

Test immediately below, exactly at and immediately above each threshold, plus null/unknown inputs and conflicting rules. Clarify whether a cap applies to a total or a per-unit rate. The product rule is the authority; a model score or a client field should not invent a new entitlement. This is a method for reasoning about the exercise, not a statement of current legal or tax rules.

### Work a small example

If X is explicitly declared to be quantity, a selected rate 0.3 and total cap 1.5 produce fee min(1.5,0.3*X); X=10 gives 1.5. This example still needs a stated schedule-selection rule.

### Edge cases and common mistakes

Claiming a boolean alone can select three independent schedules, or applying a cap to the wrong unit.
