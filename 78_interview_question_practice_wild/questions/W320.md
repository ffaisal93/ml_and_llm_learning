## Question

Backend Data Handling and Optimization

Implement an API using Python Flask to handle large-scale data. Assume the backend holds millions of data entries, optimize the API to return data to the frontend efficiently.

### Requirements

Implement pagination to support large data volumes.
Utilize caching (e.g., Redis) to improve data fetch efficiency.
Implement rate limiting to protect the server.
Optimize backend to support high-concurrency requests.
Notes
Gunicorn and Nginx can be used for handling concurrent requests on a Flask application.
Test Cases
Input: Request first page of data, 100 entries per page.
Input: Request data that exists in cache, check response speed.
Input: Rapid repeated requests to test rate limiting.
Input: Response time under high concurrency requests.

## Worked solution

### Return indexed pages; keep tenant state out of global response caches

No application schema is given. The runnable **Flask demo** uses `entries(id INTEGER PRIMARY KEY,tenant TEXT,payload TEXT)` and an index on `(tenant,id)`. Install `flask redis`; inject a Redis client, database path, demo token→tenant mapping and cursor-signing secret. The executable module is [flask_301_350.py](../flask_301_350.py). It uses a real Flask test client in tests, with an explicit Redis test double rather than pretending a Redis daemon ran.

`GET /entries?limit=100&cursor=...` reads `id>after ORDER BY id LIMIT limit+1`, returns items and a signed tenant-bound cursor, and never loads millions of rows. Keyset pagination avoids O(offset) work, but is not a consistent snapshot across concurrent edits; use immutable IDs plus a snapshot watermark if that promise is needed. Cache the serialized response for 30 seconds by tenant, cursor and page size; a production mutation path needs versioned invalidation or an explicit 30-second staleness promise. A cache key omitting tenant is a data leak.

The atomic Redis script enforces a demonstration fixed 60-second/60-request window per tenant; it is not exact sliding-window enforcement. Return 429 with Retry-After on quota exhaustion, 401 on invalid credentials and 400 on bad cursor/limit. Fail closed with 503 if the limiter is unavailable; an ordinary cache read/write failure can fall through after admission. Derive identity from authenticated credentials, not user-supplied tenant query parameters. Demo static bearer tokens are a seam for production identity middleware.

```python
"""W320 Flask/Redis demo; SQLite read path can be swapped for a pooled DB."""
import hashlib
import json
import sqlite3
from flask import Flask,request,jsonify
from itsdangerous import URLSafeSerializer,BadSignature

LIMIT_LUA="""
local n=redis.call('INCR',KEYS[1])
if n==1 then redis.call('PEXPIRE',KEYS[1],60000) end
return {n,redis.call('PTTL',KEYS[1])}
"""

def create_app(db_path,redis_client,tokens,signing_secret):
    app=Flask(__name__)
    signer=URLSafeSerializer(signing_secret,salt='data-cursor-v1')

    @app.get('/entries')
    def entries():
        bearer=request.headers.get('Authorization','')
        tenant=tokens.get(bearer.removeprefix('Bearer ')) if bearer.startswith('Bearer ') else None
        if tenant is None:return jsonify(error='unauthorized'),401
        try:
            used,ttl=redis_client.eval(LIMIT_LUA,1,'rl:'+tenant)
        except Exception:
            return jsonify(error='limiter_unavailable'),503
        if int(used)>60:
            return jsonify(error='rate_limited'),429,{'Retry-After':str(max(1,(int(ttl)+999)//1000))}
        try:
            limit=int(request.args.get('limit','100'))
            if not 1<=limit<=100:raise ValueError()
            after=0
            if request.args.get('cursor'):
                payload=signer.loads(request.args['cursor'])
                if payload['tenant']!=tenant:raise ValueError()
                after=int(payload['after'])
                if after<0:raise ValueError()
        except (ValueError,KeyError,TypeError,BadSignature):
            return jsonify(error='invalid_pagination'),400
        key='entries:v1:'+hashlib.sha256(json.dumps([tenant,after,limit]).encode()).hexdigest()
        try:cached=redis_client.get(key)
        except Exception:cached=None
        if cached is not None:return app.response_class(cached,mimetype='application/json')
        # Demo schema entries(id INTEGER PRIMARY KEY,tenant TEXT,payload TEXT),
        # index CREATE INDEX entries_tenant_id ON entries(tenant,id).
        with sqlite3.connect(db_path,timeout=2) as db:
            db.row_factory=sqlite3.Row
            rows=db.execute('SELECT id,payload FROM entries WHERE tenant=? AND id>? ORDER BY id LIMIT ?',
                            (tenant,after,limit+1)).fetchall()
        has_more=len(rows)>limit;rows=rows[:limit]
        result={'items':[dict(r) for r in rows],
                'next_cursor':signer.dumps({'tenant':tenant,'after':rows[-1]['id']}) if has_more else None}
        body=json.dumps(result)
        try:redis_client.setex(key,30,body)
        except Exception:pass
        return app.response_class(body,mimetype='application/json')
    return app

if __name__=='__main__':
    import os,redis
    app=create_app(os.environ['DB_PATH'],redis.Redis.from_url(os.environ['REDIS_URL']),
                   {os.environ['DEMO_API_TOKEN']:'demo'},os.environ['CURSOR_SECRET'])
    app.run(host='127.0.0.1',port=5000)

```

Deploy behind TLS/Nginx and Gunicorn with bounded workers, database connection pooling for PostgreSQL/MySQL and timeouts/backpressure; adding threads alone does not make SQLite writes or slow database queries scale. Inspect EXPLAIN for the keyset range, instrument p95/p99/cache hits/DB time and load-test realistic concurrency. Tests cover first/next pages, tenant isolation, cache reuse, invalid cursor, bounded size and 429; no high-concurrency response-time number is fabricated. For millions of rows, query work remains proportional to page size when the index is used, while hot caches absorb repeated first-page reads.
