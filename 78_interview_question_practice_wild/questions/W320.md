## Question

<pre class="question-text" style="white-space:pre-wrap;font-family:inherit;line-height:1.55">Backend Data Handling and Optimization

Implement an API using Python Flask to handle large-scale data. Assume the backend holds millions of data entries, optimize the API to return data to the frontend efficiently.

Requirements
Implement pagination to support large data volumes.
Utilize caching (e.g., Redis) to improve data fetch efficiency.
Implement rate limiting to protect the server.
Optimize backend to support high-concurrency requests.
Notes
Gunicorn and Nginx can be used for handling concurrent requests on a Flask application.
Test Cases
Input: Request first page of data, 100 entries per page.
Input: Request data that exists in cache, check response speed.
Input: Rapid repeated requests to test rate limiting.
Input: Response time under high concurrency requests.</pre>

## Worked solution

1. Measure a representative request trace and database plan before rewriting the Flask application. Inspect N+1 queries, row multiplication, missing indexes, payload size and serialization cost.
2. Batch or preaggregate queries at the correct grain, select needed columns, use cursor pagination and add indexes aligned with filters/order. Avoid changing semantics to make a benchmark look faster.
3. Move long independent work to a bounded background job path; configure connection pools, timeouts and worker concurrency according to actual database/CPU limits.
4. Validate outputs against the original on edge cases and benchmark p95/p99 under matched load. Cache only with authorization, invalidation and versioning semantics explicit.

### Small example / sanity check

Joining reservations and prices before aggregation can multiply rows; separately preaggregating each relation can improve both speed and correctness.

### Common trap

Adding worker threads to hide an already saturated database or caching one user’s response for another user.
