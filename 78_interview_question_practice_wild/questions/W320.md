## Question

Backend Data Handling and Optimization

Implement an API using Python Flask to handle large-scale data. Assume the backend holds millions of data entries, optimize the API to return data to the frontend efficiently.

### Requirements

Implement pagination to support large data volumes.
Utilize caching (e.g., Redis) to improve data fetch efficiency.
Implement rate limiting to protect the server.
Optimize backend to support high-concurrency requests.
Notes
Gunicorn and Nginx can be used for handling concurrent requests on a Flask application.
Test Cases
Input: Request first page of data, 100 entries per page.
Input: Request data that exists in cache, check response speed.
Input: Rapid repeated requests to test rate limiting.
Input: Response time under high concurrency requests.

## Worked solution

### Solution outline

1. Measure a representative request trace and database plan before rewriting the Flask application. Inspect N+1 queries, row multiplication, missing indexes, payload size and serialization cost.
2. Batch or preaggregate queries at the correct grain, select needed columns, use cursor pagination and add indexes aligned with filters/order. Avoid changing semantics to make a benchmark look faster.
3. Move long independent work to a bounded background job path; configure connection pools, timeouts and worker concurrency according to actual database/CPU limits.
4. Validate outputs against the original on edge cases and benchmark p95/p99 under matched load. Cache only with authorization, invalidation and versioning semantics explicit.

### Understand why the approach works

#### Establish row grain before writing a join

Say what one output row represents: an event, user, vendor, parent type or time interval. Then inspect the cardinality of every join. Joining two one-to-many relations can multiply rows and inflate both totals and averages; `DISTINCT` is not a general repair because legitimate equal-valued records can also exist.

For mergeable averages store a sum and count:

$$
\bar x_{\rm pooled}=\frac{\sum_g \operatorname{sum}_g}{\sum_g \operatorname{count}_g}.
$$

Do not average subgroup means unless the intended weighting gives each group equal weight. Likewise, daily distinct users cannot be added to obtain monthly distinct users.

Use half-open time windows, such as `timestamp >= start AND timestamp < end`, and name the timezone. For point-in-time training, feature **availability time** must not exceed prediction time; event occurrence and availability can differ.

Choose tie semantics deliberately: `ROW_NUMBER` produces a fixed number of rows under a deterministic secondary order, while `DENSE_RANK` preserves equal primary scores. A predicate on a nullable right-table column in `WHERE` can undo the unmatched-row preservation of a `LEFT JOIN`. Test duplicate events, absent dimension rows, nulls, tied maxima and an empty denominator. These cases explain correctness more convincingly than running only one ordinary example.

### Work a small example

Joining reservations and prices before aggregation can multiply rows; separately preaggregating each relation can improve both speed and correctness.

### Edge cases and common mistakes

Adding worker threads to hide an already saturated database or caching one user’s response for another user.

### Check your reasoning on related cases

**Optimize a latest-jobs query over a large table.** An ORDER BY created_at DESC LIMIT 20 query may benefit from an aligned index; a function on created_at can prevent a simple index lookup.

Why can OFFSET pagination get slower? The database may still traverse and discard the skipped rows.

**How do you debug a production latency regression?** If median latency is stable but p99 worsens, a small fraction of long requests or queueing spikes may dominate the regression.

Why can throughput improve while user latency worsens? Larger batches can increase queueing and per-request waiting.

**Design a cache without serving incorrect data.** Two identical question strings from users with different document permissions must not automatically share a retrieved-answer cache entry.

Why can invalidation be preferable to TTL alone? Critical updates may need to take effect sooner than the ordinary expiry window.
