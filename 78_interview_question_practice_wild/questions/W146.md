## Question

Apple ML Engineer phone screen (Round 2), shared editor. You are given a stream of labeled (text, label) records and must build an end-to-end online pipeline that:
1. Processes tokens online — one record at a time, no pre-reading the whole corpus.
2. Generates embeddings for each token/document.
3. Trains a classifier on the stream and predicts for new records.

Keep it simple: hashed token ids, an embedding table you update online, mean-pool for the document vector, a linear softmax head, and SGD. It is not asking you to pretrain word2vec or a Transformer.

Before coding, clarify: single-pass online vs. replayable stream; binary vs. fixed multi-class C; vocabulary growth (feature hashing vs. lazy growth); embedding dim (32–64); optimizer; and metrics (progressive validation).

## Worked solution

### Solution outline

1. Define versioned endpoints and schemas for token processing, embeddings and classification; specify input normalization, maximum sizes, supported batch shapes and error types.
2. Keep model/preprocessing versions in responses and cache keys. Batch compatible work under latency budgets, preserve request/output mapping and handle partial errors explicitly.
3. For streaming input, retain only the state the model needs and distinguish append-only token updates from corrections. Return normalized probabilities or scores under a documented label order.
4. Enforce tenant quotas, privacy and bounded queues; measure quality, p99 latency, token throughput and failure rates under representative lengths.

### Understand why the approach works

#### Separate service time, queueing and memory

A request's observed latency is not just the model kernel duration:

$$
T_{\rm request}=T_{\rm queue}+T_{\rm preprocess}+T_{\rm prefill}
+T_{\rm decode}+T_{\rm delivery}.
$$

Prefill processes the prompt; decode repeatedly adds tokens. Measure both time to first token and inter-token latency, because a configuration can improve aggregate throughput while worsening the user's experience. Batching amortizes work but may increase waiting.

Estimate the KV tensor budget independently of fixed weights. For equal-length requests,

$$
M_{\rm KV}=2BLT H_{\rm KV}d_h s,
$$

where $L$ is layer count, $T$ cached length and $s$ bytes per element. The factor two is keys plus values. With $L=32$, $T=4096$, $H_{\rm KV}=8$, $d_h=128$, $B=1$ and $s=2$, the raw cache is $512$ MiB, before allocator overhead.

Use measured capacity to set admission and live-token limits. If a worker serves batches of at most $b$ in $s_b$ seconds, $b/s_b$ is an optimistic service-rate ceiling, not a per-request guarantee. Sustained arrivals above that rate grow backlog; even lower averages can hide damaging bursts. Bound queues, define cancellation and partial-failure behavior, and compare latency on matched length/concurrency distributions rather than one isolated request.

### Work a small example

A stored embedding produced by version A must not silently be compared with a query embedding from incompatible version B. A failed item cannot shift every later batch result by one index.

### Check your reasoning on related cases

**Implement the scheduling core of a dynamic batcher.** With b_max=3 and five overdue requests, two dispatches should call the model on batches of sizes 3 and 2.

Is t_max an unconditional latency guarantee? No; overloaded queues can wait longer than their dispatch deadlines.

**Estimate an LLM serving capacity budget.** Ten requests at 4000 cached tokens consume the same idealized KV tensor space as twenty at 2000, assuming identical models and no block rounding.

What happens if traffic shifts toward longer outputs? Cache residency and decode work rise even at unchanged request arrival rate.

**Design a rate-limited LLM classification pipeline.** If a request times out after the provider processed it, a retry must not create two independent downstream records for the same item.

How do you handle backlog growth? Scale within budget, reduce per-item cost or apply admission and prioritization policies.
