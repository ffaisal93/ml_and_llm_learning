## Question

You are given an N-ary tree where each node is a separate server. Each node can only talk to its parent and its children. Communication is asynchronous; messages may arrive late, out of order, be duplicated, or be lost. Write the per-node logic so the tree can count its total number of nodes, with only the root printing the final total.

Interface (you cannot change send_async; treat it as a black box):

```text
class Message:
def __init__(self, kind, request_id, payload): ...
class Node:
def __init__(self, node_id, parent_id, children): ...
def send_async(self, to_node_id, message): ...  # provided
def call(self, from_node_id, message): ...       # you implement
```

The interview has three parts: (1) basic counting assuming perfect delivery, (2) handling duplicate messages, (3) handling lost messages (packet loss). Leaf nodes reply 1; internal nodes send request_count to all children, wait for all replies, then reply 1 + sum(child_counts) to their parent; the root prints the total.

## Worked solution

### Solution outline

1. Key per-node state by request_id. A leaf replies count=1; an internal node sends one logical request to each child, records one response per child id, and returns 1+sum(child_counts) once all distinct children reply.
2. Cache the completed response. Duplicate requests resend that response or reuse the existing in-flight work; duplicate child replies do not increment the sum again. Only the root publishes the final result once per request.
3. For loss, retry outstanding child requests with a bounded/backoff timer while permitting cached-response retransmission. Acknowledge results or retain them under an explicit lifetime/garbage-collection policy.
4. Perfect-delivery counting uses 2*(N-1) edge messages for one request/response traversal. Retries increase that. Completion under packet loss requires an eventual-delivery/fairness assumption; no algorithm can guarantee a correct complete count through a permanently unreachable subtree without changing the contract.

### Understand why the approach works

#### State what an acknowledgment guarantees

Distinguish accepted in memory, appended to a local file, flushed durably, replicated and committed. A client-visible success must correspond to the promised boundary; otherwise recovery can lose operations the client believes are complete.

A retry is not necessarily a new logical operation. Use a stable operation id, bind it to request parameters, and atomically record its state and result with the business change where possible. If a worker finishes an effect and crashes before acknowledgment, the repeated id lets a recipient recognize it.

Timeouts mean lack of observed response, not proof that no action happened. Leases and heartbeats detect suspected failure; fencing tokens prevent an expired owner from committing after a successor took over. In a partition, stronger consistency may require rejecting some requests rather than allowing conflicting leaders.

Walk through one failure between each pair of durable transitions. For tree aggregation, record one contribution per child and request id; duplicate messages must not increase the count. For an external effect, reconcile uncertain outcomes rather than silently retrying under a new identity. Explain liveness assumptions separately: permanent loss of access to required state can make guaranteed completion impossible even when the protocol preserves safety.

### Work a small example

If child C reports count=7 twice, its parent still contributes only 7 once. If C’s first reply is lost, the parent’s repeated request obtains C’s cached response.

### Edge cases and common mistakes

Counting received messages instead of distinct children or timing out a missing subtree and calling the partial sum the exact total.
