## Question

You will take ownership of an existing small codebase. The interview has two parts:

Part A: Hands-on debugging and patching (30 minutes)

You are given a codebase and a reproducible issue (e.g., failing unit tests, incorrect output for certain inputs, a crash, or a performance anomaly).

### Requirements

Run the project (or follow provided repro steps) to locate the root cause.
Apply a minimal change to fix the bug.
Add or update tests if needed to prevent regressions.
Explain how you validated the fix (which tests passed, which edge cases are covered).

### Constraints

Refactoring is allowed, but justify why it is the minimum necessary.
Consider edge cases and maintainability.
Part B: High-level improvements as a long-term owner (15 minutes)

Assume you will own this code long-term. Answer:

What high-level changes would you propose to improve quality and delivery velocity (architecture boundaries, error handling, logging/observability, testing strategy, CI/CD, performance/capacity, dependency management, etc.)?
How would you prioritize them and why?
How would you roll them out safely (migration/refactor strategy, gradual rollout, compatibility layers, etc.)?

Language-agnostic. Your answer should include your debugging approach, the patch, and a long-term improvement roadmap.

## Worked solution

### Reproduce before choosing a patch

No codebase, failing input or test output is actually attached to this question. Therefore a root cause or patch to that nonexistent supplied repository cannot honestly be identified. The concrete illustration below demonstrates the required reasoning; it is labeled a fixture, not a claim about the original exercise.

In the first five minutes read run/setup instructions, install pinned dependencies, execute the stated repro and preserve its exact error/expected behavior. During minutes 5–15 trace the failing data path, inspect the smallest relevant functions and reduce to a discriminating regression. Make one minimal cause-directed change during minutes 15–23, then spend 23–30 on the regression, surrounding tests, input boundaries and diff review. A performance issue needs a baseline profile and comparable load, not just a passing unit test.

### A concrete minimal-patch demonstration

Suppose the documented API says a missing price defaults to zero, while a real zero price must stay zero:

```python
# Buggy fixture


def price_or_default(price, default=10):
    return price or default


assert price_or_default(0) == 10  # Reproduces the wrong behavior.


# Minimal fix: distinguish missingness from falsiness.
def price_or_default(price, default=10):
    return default if price is None else price


assert price_or_default(0) == 0
assert price_or_default(None) == 10
assert price_or_default(4) == 4
assert price_or_default(-1) == -1
```

The invariant is “only None means missing.” Replacing one boolean condition fixes the cause without redesigning pricing. A real patch would cite the actual function/line, the failing regression before it, the same regression after it and the executed suite. Do not merely replace an expected output to make the test green.

### Prioritize long-term ownership work

First address recurring correctness/security and recovery risks: pin dependencies, encode the repaired invariant in focused tests, validate inputs at boundaries, expose structured errors and correlation ids, and prevent sensitive logs. Next improve delivery confidence: deterministic CI for tests/lint/type checks, reproducible build artifacts, staged deploy, health checks and a one-step rollback. Then address measured hotspots or confusing architecture: isolate domain logic from storage/network adapters, add contract/integration tests around those seams, profile representative workloads and define capacity/error budgets. A new framework or rewrite comes only with demonstrated benefit.

For each item state observed pain, impact, effort, acceptance metric and owner. Introduce compatibility adapters, migrate one caller at a time, compare old/new results in shadow, then remove old paths after adoption. Database changes use additive schema → dual-compatible code → backfill/verify → traffic switch → cleanup. Keep the immediate fix separate from cleanup and monitor its business symptom after release. The actual roadmap order depends on evidence from the missing repository; this is an actionable prioritization method, not invented findings.
