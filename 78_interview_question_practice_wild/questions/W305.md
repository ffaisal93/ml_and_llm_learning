## Question

A streaming service logs a watch event whenever a viewer's progress through a movie is reported. To judge how well a newly launched movie is landing, the data team wants to know, for every viewer and movie, how far the viewer really got. Write a function that classifies each (viewer, movie) pair into a completion bucket from a raw, messy stream of those events.

### What to implement

```text
def classify_completion(events: list[tuple[str, str, float]]) -> list[tuple[str, str, int]]
```

events: a list of (user_id, movie_id, percent_watched) tuples. user_id and movie_id are strings; percent_watched is a number from 0 to 100 inclusive. Events arrive in any order, and the same user and movie can appear many times (progress is reported repeatedly, and late events are common).
Return a list of (user_id, movie_id, bucket) tuples, where bucket is 30, 50 or 80.

### Rules

1. Deduplicate. For each (user_id, movie_id) pair, only the highest percent_watched over all of its events counts. The order of the events does not matter.
2. Bucket. A pair belongs to the largest threshold in (30, 50, 80) that its highest percentage reaches or exceeds. So 30 belongs to bucket 30, 79.99 to bucket 50, 80 and 100 to bucket 80.
3. Below 30. A pair whose highest percentage is below 30 is left out of the result.
4. Order. Sort the result by movie_id ascending, then user_id ascending (plain string comparison), with exactly one tuple per pair.
5. No events, or no pair reaching 30, gives an empty list.

### Examples

Example 1: deduplication keeps the maximum, not the latest.

```python
events = [("u1", "m1", 20), ("u1", "m1", 85), ("u1", "m1", 40)]
```

-&gt; [("u1", "m1", 80)]     (the highest progress is 85, even though the last event says 40)

Example 2: buckets, boundaries, sorting and the cutoff.

```text
events = [("u2", "m1", 50), ("u1", "m1", 29.9), ("u3", "m1", 30),
```

("u1", "m0", 79.99), ("u2", "m0", 100)]
-&gt; [("u1", "m0", 50), ("u2", "m0", 80), ("u2", "m1", 50), ("u3", "m1", 30)]

("u1", "m1") stays below 30 and is dropped; the rest are sorted by movie, then user.

### Constraints

Up to 2 * 10^5 events, and up to 2 * 10^5 distinct pairs.
The function should run in O(n log n) time; comparing every event with every other event is too slow.
Standard library only.

## Worked solution

### Solution outline

The definition of completion and the observation window determine the label before modeling begins.

1. Define eligible starts, completion thresholds, replays, partial sessions and late events.
2. Construct user/item/context features available at the intended prediction time and split by time or entity as appropriate.
3. Compare a simple baseline, inspect duration and user-segment effects and evaluate the downstream intervention rather than classification alone.

### Understand why the approach works

#### Design the decision, not only the predictor

State which user action follows the model output, when the prediction occurs and which errors are costly. Then define labels and features using information available at that time. A feature recorded after the outcome is not made legitimate by being stored in the same table.

For a retrieval/ranking product, use a cascade: generate a broad eligible set, score a bounded candidate set, then apply policy and presentation rules. Evaluate retrieval recall separately because a ranker cannot rescue an item excluded upstream. Availability, permissions and budgets are hard constraints, not merely features a model may learn to respect.

Expected action utility can be written as

$$
a^*(x)=\arg\max_a\sum_y P(y\mid x)\,U(a,y).
$$

This makes clear why a probability metric and a product objective are different. The same calibrated probability may produce different actions when error costs change.

Describe a baseline, time/entity-aware validation, exposure logging and one controlled rollout. For a recommender, unexposed items are not automatically observed negatives. For moderation or fraud, mature labels and human-review capacity matter. Finish with a failure walkthrough: what happens when features are stale, the model is unavailable or the distribution changes? A simpler fallback with explicit monitoring is often more defensible than an elaborate system without an operational plan.
