## Worked solution

1. Build an agent loop with explicit stop conditions. An agent alternates deciding what to do with receiving observations; the surrounding program must enforce limits.
2. Represent task state, available typed tools, execution history and a completion condition explicitly.
3. Validate each proposed tool call, execute with bounded time and record the observation. Distinguish read operations from consequential actions.
4. Stop on success, budget exhaustion, repeated failure or required human input; return an honest partial result if the objective is not reached.
5. Design tool schemas and validate LLM outputs. A tool response becomes useful only when its structure and meaning are checked by ordinary code.
6. Specify names, field types, required fields, bounds and enumerations; validate syntax before execution.
7. Perform semantic checks such as date ordering, inventory availability, authorization and allowed resource identifiers.
8. Return structured errors that allow a bounded repair attempt. Keep untrusted tool output separate from higher-priority instructions.
9. Evaluate an agent whose outputs vary between runs. Score whether it achieved the task safely and efficiently, not whether it followed one memorized trajectory.
10. Create tasks with explicit success checks and resettable environments. Run multiple seeds or repeated trials under fixed budgets.
11. Track outcome success, invalid actions, unnecessary tool calls, cost, latency and recovery behavior.
12. Audit trajectories to diagnose failures, while reporting uncertainty across tasks and runs rather than hiding nondeterminism.

### Small example / sanity check

A search agent should stop after evidence answers the query, not continue calling search until its token budget is exhausted.

### Common trap

Giving the model unlimited retries without checking whether state or evidence changed.
