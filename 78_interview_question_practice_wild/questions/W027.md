## Question

Dynamic Batch Inference

An inference service receives requests one at a time, but a model runs far more efficiently on a batch. Build the scheduling core of a dynamic batcher: it collects incoming requests and releases a batch to the model when the batch is full or when the oldest request has waited long enough, then hands each output back to the request it belongs to.

### What to implement

```text
class DynamicBatcher with these members. Time is passed in as a number of seconds, so the class has no clock or threads and is easy to test.
```

__init__(self, model, b_max: int, t_max: float): model is a callable that takes a list of inputs and returns a list of outputs of the same length and order. b_max is the largest batch size and t_max the longest a request may wait in the queue before it is released. Raise ValueError if b_max &lt; 1 or t_max &lt; 0.
submit(self, x, now: float) -&gt; int: add input x, which arrived at time now, to the end of the queue. Return its request id. Ids are 0, 1, 2, ... in submission order.
next_deadline(self) -&gt; float | None: the time at which the oldest queued request reaches t_max, or None if the queue is empty.
should_dispatch(self, now: float) -&gt; bool: whether a batch is due at time now.
dispatch(self, now: float) -&gt; list[tuple[int, object]]: if no batch is due, return [] and do not call the model. Otherwise remove a batch from the queue, call model exactly once on it, and return (request_id, output) pairs in queue order.

### Rules

1. The queue is first in, first out.
2. A batch is due at time now when the queue is not empty and either it holds at least b_max requests, or now &gt;= arrival_time_of_oldest + t_max. The deadline is inclusive.
3. A dispatched batch holds the first min(b_max, queue length) requests of the queue. This holds even when the deadline passed long ago: a backlog must leave in batches of up to b_max, not one request at a time.
4. model is called once per batch, never once per request, and its i-th output belongs to the i-th input of the batch.
5. The wait of a request means the time from its arrival until its batch is dispatched.

### Examples

Example 1: the batch fills up. b_max = 3, t_max = 0.05. Submit 1 at time 0.00, 2 at 0.01 and 3 at 0.02, with a model that multiplies each input by 10. At now = 0.02 the queue holds 3 requests, so dispatch(0.02) returns [(0, 10), (1, 20), (2, 30)], and the model was called once with [1, 2, 3].

Example 2: the deadline. Same settings. Submit 1 at 0.00 and 2 at 0.01. dispatch(0.04) returns [], because the oldest request has waited only 0.04. next_deadline() is 0.05, and dispatch(0.05) returns [(0, 10), (1, 20)]: request 1 rides along with request 0.

Example 3: a backlog. Same settings. Submit 5 requests, all at time 0.00, and look at time 0.1. The first dispatch(0.1) returns the first 3 requests. The deadline has passed for the other two, so a second dispatch(0.1) returns both of them together. The model sees batches of sizes 3 and 2, not five single-item calls.

### Constraints

1 &lt;= b_max &lt;= 1024, 0 &lt;= t_max.
now never decreases between calls.
At most 10^5 requests are queued at once. Every operation should take time proportional to the size of the batch it handles, not to the queue length.
All inputs of one batch have whatever shape model accepts. With PyTorch the model wrapper would call torch.stack on the list; the batcher does not look inside the inputs.
Follow-up 1: a bound on waiting time

A worker loop calls dispatch whenever it is idle, and one model call takes s seconds. Under what condition is the wait of every request at most t_max + s, and what happens when requests arrive faster than b_max / s per second?

Follow-up 2: connecting it to real threads

How would you turn this core into a service in which each client blocks until its own result is ready, without a busy loop?

## Worked solution

### Solution outline

#### Implement the scheduling core of a dynamic batcher.

A batcher trades a small queueing delay for more efficient model calls.

1. Keep a FIFO queue of request id, payload and arrival time. Assign ids monotonically.
2. Dispatch when size reaches b_max or the oldest request reaches its inclusive deadline. Remove up to b_max items and call the model once.
3. Map outputs back by request id. Preserve a backlog for subsequent dispatches; define model-failure handling separately. The coding lab implements the deterministic core.

#### Bound latency in a batch service under load.

A dispatch deadline is a scheduling rule; queue stability is a separate requirement.

1. If a worker handles at most b requests per model call taking s seconds, its optimistic sustained capacity is b/s requests per second.
2. A bound like wait<=t_max+s needs additional conditions: a ready batch can be served after at most one current model call, with no earlier queued backlog or competing delay.
3. Under sustained arrivals above service capacity, backlog grows; bound the queue and apply admission control or add capacity. Below average capacity, bursts can still violate a per-request bound.

### Understand why the approach works

#### Separate service time, queueing and memory

A request's observed latency is not just the model kernel duration:

$$
T_{\rm request}=T_{\rm queue}+T_{\rm preprocess}+T_{\rm prefill}
+T_{\rm decode}+T_{\rm delivery}.
$$

Prefill processes the prompt; decode repeatedly adds tokens. Measure both time to first token and inter-token latency, because a configuration can improve aggregate throughput while worsening the user's experience. Batching amortizes work but may increase waiting.

Estimate the KV tensor budget independently of fixed weights. For equal-length requests,

$$
M_{\rm KV}=2BLT H_{\rm KV}d_h s,
$$

where $L$ is layer count, $T$ cached length and $s$ bytes per element. The factor two is keys plus values. With $L=32$, $T=4096$, $H_{\rm KV}=8$, $d_h=128$, $B=1$ and $s=2$, the raw cache is $512$ MiB, before allocator overhead.

Use measured capacity to set admission and live-token limits. If a worker serves batches of at most $b$ in $s_b$ seconds, $b/s_b$ is an optimistic service-rate ceiling, not a per-request guarantee. Sustained arrivals above that rate grow backlog; even lower averages can hide damaging bursts. Bound queues, define cancellation and partial-failure behavior, and compare latency on matched length/concurrency distributions rather than one isolated request.

### Readable reference implementation

Read the explanation first, then trace one small input through these functions. This is the same implementation used by the local checks; its stated simplifications still apply.

```python
import math
from collections import deque
from dataclasses import dataclass
import numpy as np


class DynamicBatcher:
    """Pure scheduling core; no threads, clock or production retry policy."""
    def __init__(self, model, b_max, t_max):
        if b_max < 1 or t_max < 0:
            raise ValueError("invalid batching limits")
        self.model, self.b_max, self.t_max = model, b_max, t_max
        self.queue, self.next_id = deque(), 0

    def submit(self, x, now):
        request_id = self.next_id
        self.next_id += 1
        self.queue.append((request_id, x, now))
        return request_id

    def next_deadline(self):
        return None if not self.queue else self.queue[0][2] + self.t_max

    def should_dispatch(self, now):
        return bool(self.queue) and (len(self.queue) >= self.b_max or now >= self.next_deadline())

    def dispatch(self, now):
        if not self.should_dispatch(now):
            return []
        batch = [self.queue.popleft() for _ in range(min(self.b_max, len(self.queue)))]
        outputs = list(self.model([item[1] for item in batch]))
        if len(outputs) != len(batch):
            raise ValueError("model returned the wrong number of outputs")
        return [(item[0], result) for item, result in zip(batch, outputs)]
```

### Work a small example

With b_max=3 and five overdue requests, two dispatches should call the model on batches of sizes 3 and 2.

### Edge cases and common mistakes

Calling the model once per item, returning outputs to the wrong clients, or expiring all overdue requests as one-item batches.
