## Question

Worker processes keep asking a database for the newest job that nobody has picked up yet, and as the table grew to 100 million rows that query became very slow. Explain what the database does today, fix it inside the database itself, back the fix with numbers, and then handle follow-ups on variations of the query, concurrent workers, write cost and rollout.

### Setup

1. Table job(id bigint primary key, status text, created_on timestamp, ...), about 200 bytes per row, in a relational database with B-tree indexes (for example PostgreSQL or MySQL/InnoDB). The only index is the primary key.

```text
2. 100,000,000 rows in total. About 20,000,000 of them have status = 'new'; the rest are in other states such as 'running' and 'done'.
```

3. The query, run frequently by worker processes:

```sql
SELECT * FROM job WHERE status = 'new' ORDER BY created_on DESC LIMIT 1;
```

### Requirements

1. Explain why the query is slow today: which plan the database has to use, and roughly how much data it reads.
2. Fix it in the database itself. A cache in front of the database is out of scope.
3. Justify every design choice in your fix (for example, which columns and in which order) and estimate the cost before and after: pages or rows read per query, and the size of anything you add. State your assumptions.
Follow-up 1: alternatives that come close

Which alternative fixes come close to yours, and why are they worse?

Follow-up 2: two statuses instead of one

The filter becomes status IN ('new', 'retry'). What changes?

Follow-up 3: many workers claiming jobs at once

Many workers run the query at the same time, and each must claim a different job. What changes?

Follow-up 4: write cost and maintenance

What does the fix cost on writes, and what maintenance does it need?

Follow-up 5: verifying and rolling out on a live table

How do you verify the fix and roll it out on a live 100M-row table?

## Worked solution

### Index the filter and desired order, then claim atomically

With only a primary-key index, id does not provide the requested created_on order or filter. A typical plan is a sequential/parallel scan, filtering status, then a top-N sort. Top-N LIMIT 1 can keep only the best tuple in memory; it need not fully sort 20M matches, but still examines about 100M rows. At 200 bytes/row, logical data is 20 GB; assuming 40 rows per 8-KiB page gives about 2.5M heap pages (20.48 GB) before bloat/toast. Warm cache changes IO latency, not the linear scan work.

For the fixed 'new' query in PostgreSQL, build a partial ordered B-tree. Include id as a deterministic tie-break and use the same order in the claim:

```sql
-- PostgreSQL, run outside an explicit transaction:
CREATE INDEX CONCURRENTLY job_new_latest
 ON job(created_on DESC,id DESC) WHERE status='new';

-- Atomic claim, one short transaction per batch:
BEGIN;
WITH picked AS (
 SELECT id FROM job WHERE status='new' ORDER BY created_on DESC,id DESC
 FOR UPDATE SKIP LOCKED LIMIT 1
)
UPDATE job SET status='running' FROM picked WHERE job.id=picked.id
RETURNING job.*;
COMMIT;
```

Only 20M new rows enter the index. Assume 32-byte entries and 80% fill: about 800 MB plus upper pages/metadata, versus roughly 4 GB for an all-row index of similar width. A fanout around 200 gives a height near four levels; finding the first eligible leaf plus one heap fetch is roughly five page visits, often one or two actual reads with warm upper levels. MVCC dead entries/locked rows can require more visits, so “one read always” is false. SELECT * still needs the heap; including every 200-byte row in the index wastes space/write bandwidth.

A general `(status,created_on DESC,id DESC)` index also works and is portable to MySQL, but stores all 100M rows. An index only on status finds 20M candidates then still needs selection; only on created_on may scan many newer non-new jobs. BRIN is small and helps correlated ranges but does not directly find the newest new tuple. For `status IN ('new','retry')`, a single status-leading B-tree does not globally order both ranges; fetch top candidates per status and merge, or use a partial created_on index whose predicate includes both statuses. Parameterized predicates must be planner-provably compatible with a partial index.

The short `FOR UPDATE SKIP LOCKED` transaction makes workers choose different unlocked rows and changes status before releasing locks. Add a lease/attempt token and recovery of abandoned running jobs; delivery after worker crashes still needs idempotent work. Newest-first can starve older jobs under continuous arrivals, a separate scheduling policy decision.

Every new insert/status transition updates index membership, creates WAL and can prevent HOT updates; deletes/changes leave dead entries needing autovacuum. Monitor index bloat, vacuum lag, write p99 and replication. Use concurrent online creation (engine-specific), budget extra disk/WAL, inspect invalid indexes after interrupted builds, ANALYZE, compare EXPLAIN (ANALYZE, BUFFERS) on representative non-destructive/staged queries and canary worker load. Measure before/after pages, latency and write cost; the numbers here are explicit estimates, not an executed 100M-row benchmark.
