## Question

<pre class="question-text" style="white-space:pre-wrap;font-family:inherit;line-height:1.55">Worker processes keep asking a database for the newest job that nobody has picked up yet, and as the table grew to 100 million rows that query became very slow. Explain what the database does today, fix it inside the database itself, back the fix with numbers, and then handle follow-ups on variations of the query, concurrent workers, write cost and rollout.

Setup
1.
Table job(id bigint primary key, status text, created_on timestamp, ...), about 200 bytes per row, in a relational database with B-tree indexes (for example PostgreSQL or MySQL/InnoDB). The only index is the primary key.
2.
100,000,000 rows in total. About 20,000,000 of them have status = &#x27;new&#x27;; the rest are in other states such as &#x27;running&#x27; and &#x27;done&#x27;.
3.
The query, run frequently by worker processes:
SELECT * FROM job WHERE status = &#x27;new&#x27; ORDER BY created_on DESC LIMIT 1;
Requirements
1.
Explain why the query is slow today: which plan the database has to use, and roughly how much data it reads.
2.
Fix it in the database itself. A cache in front of the database is out of scope.
3.
Justify every design choice in your fix (for example, which columns and in which order) and estimate the cost before and after: pages or rows read per query, and the size of anything you add. State your assumptions.
Follow-up 1: alternatives that come close

Which alternative fixes come close to yours, and why are they worse?

Follow-up 2: two statuses instead of one

The filter becomes status IN (&#x27;new&#x27;, &#x27;retry&#x27;). What changes?

Follow-up 3: many workers claiming jobs at once

Many workers run the query at the same time, and each must claim a different job. What changes?

Follow-up 4: write cost and maintenance

What does the fix cost on writes, and what maintenance does it need?

Follow-up 5: verifying and rolling out on a live table

How do you verify the fix and roll it out on a live 100M-row table?</pre>

## Worked solution

1. Optimize a latest-jobs query over a large table. Match the access path to the actual filters and ordering, then verify using a query plan.
2. Inspect selectivity, join cardinalities, sort costs and how many rows must be scanned.
3. Consider an index beginning with selective equality filters followed by the requested order/time field, depending on the database and query.
4. Use keyset pagination when appropriate and measure write/storage overhead as well as read gains.

### Small example / sanity check

An ORDER BY created_at DESC LIMIT 20 query may benefit from an aligned index; a function on created_at can prevent a simple index lookup.

### Common trap

Adding many indexes without checking whether the optimizer uses them or whether writes become too costly.
