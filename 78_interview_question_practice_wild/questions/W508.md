## Question

<pre class="question-text" style="white-space:pre-wrap;font-family:inherit;line-height:1.55">Build a React component FilterableList that shows a dataset and lets the user narrow it with filter controls. The visible results must update immediately whenever a control changes.

What to implement

FilterableList({ items }), where each item has the shape { id, name, description, status, type } (all strings; status is &quot;active&quot; or &quot;inactive&quot;, type is &quot;camera&quot; or &quot;sensor&quot;).

1.
Render the matching items as a list or as cards, showing at least the name, status and type of each.
2.
Provide three controls: a text input for a keyword search, a select for status and a select for type. Each select has an &quot;all&quot; option meaning no restriction.
3.
An item is visible only if it passes every active control (AND): the search text must appear in its name or description, and its status and type must equal the selected values unless &quot;all&quot; is selected.
4.
Search is case-insensitive and ignores leading and trailing whitespace; a query that is empty or only whitespace matches everything.
5.
A &quot;Reset&quot; button restores all controls to their initial values, which shows the full dataset again.
6.
When nothing matches, show an explicit &quot;No results&quot; message instead of an empty area.
Deliverables
The component and its filtering logic. The filtering rule itself should be a pure function of the item and the filter values.
A short explanation of your state design: which values are stored in state, which are derived from it, and where memoization helps.
Example
items = [
{ id: 1, name: &quot;Lobby Camera&quot;,   description: &quot;front door&quot;, status: &quot;active&quot;,   type: &quot;camera&quot; },
{ id: 2, name: &quot;Garage Sensor&quot;,  description: &quot;motion&quot;,     status: &quot;inactive&quot;, type: &quot;sensor&quot; },
{ id: 3, name: &quot;Garage Camera&quot;,  description: &quot;side door&quot;,  status: &quot;active&quot;,   type: &quot;camera&quot; },
]
query &quot;garage&quot;                         -&gt; items 2 and 3
query &quot;  GARAGE  &quot;, status &quot;active&quot;     -&gt; item 3
query &quot;door&quot;, type &quot;sensor&quot;            -&gt; No results
Reset                                  -&gt; items 1, 2 and 3
Constraints
Filtering must not mutate items.
Do not store the filtered list in state; compute it from items and the filter values.
Assume up to a few thousand items; no pagination is required.</pre>

## Worked solution

1. Define the view state, loading/error/empty states, accessibility and server API contract before choosing a component structure. Keep authoritative validation and authorization on the server.
2. Debounce and cancel obsolete search requests; tag responses with request versions so a slow old result cannot overwrite a newer query. Cache and paginate under stable cursor rules.
3. For large lists use windowed rendering, bounded retained state and incremental loading; preserve scroll position and deduplicate ids across pages. Live comments need a reconnect cursor and a defined ordering policy.
4. Validate input both client- and server-side, handle duplicate submits idempotently, and log experiment exposure consistently. Test slow networks, keyboard/screen-reader navigation and out-of-order responses.

### Small example / sanity check

The response for query “a” may arrive after the response for “apple”; the UI must keep the result for the current query, not whichever HTTP call finishes last.

### Common trap

Rendering 100000 DOM rows or treating disabled client buttons as an authorization or duplicate-payment control.
