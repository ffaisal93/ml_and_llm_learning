## Question

Build a React component FilterableList that shows a dataset and lets the user narrow it with filter controls. The visible results must update immediately whenever a control changes.

### What to implement

FilterableList({ items }), where each item has the shape { id, name, description, status, type } (all strings; status is "active" or "inactive", type is "camera" or "sensor").
1. Render the matching items as a list or as cards, showing at least the name, status and type of each.
2. Provide three controls: a text input for a keyword search, a select for status and a select for type. Each select has an "all" option meaning no restriction.
3. An item is visible only if it passes every active control (AND): the search text must appear in its name or description, and its status and type must equal the selected values unless "all" is selected.
4. Search is case-insensitive and ignores leading and trailing whitespace; a query that is empty or only whitespace matches everything.
5. A "Reset" button restores all controls to their initial values, which shows the full dataset again.
6. When nothing matches, show an explicit "No results" message instead of an empty area.
Deliverables
The component and its filtering logic. The filtering rule itself should be a pure function of the item and the filter values.
A short explanation of your state design: which values are stored in state, which are derived from it, and where memoization helps.

### Constraints

Filtering must not mutate items.
Do not store the filtered list in state; compute it from items and the filter values.
Assume up to a few thousand items; no pagination is required.

## Worked solution

### Solution outline

1. Define the view state, loading/error/empty states, accessibility and server API contract before choosing a component structure. Keep authoritative validation and authorization on the server.
2. Debounce and cancel obsolete search requests; tag responses with request versions so a slow old result cannot overwrite a newer query. Cache and paginate under stable cursor rules.
3. For large lists use windowed rendering, bounded retained state and incremental loading; preserve scroll position and deduplicate ids across pages. Live comments need a reconnect cursor and a defined ordering policy.
4. Validate input both client- and server-side, handle duplicate submits idempotently, and log experiment exposure consistently. Test slow networks, keyboard/screen-reader navigation and out-of-order responses.

### Understand why the approach works

#### Separate current intent from asynchronous results

Represent loading, empty, success, stale and error states explicitly. When a user types or changes a filter, the current request version changes; an older response must not overwrite newer state merely because it arrived later.

Debounce expensive requests, cancel obsolete work when possible and still compare request generations on completion, because cancellation may race with delivery. A form's disabled button is a usability feature, not a replacement for server idempotency or authorization.

For long feeds and tables, use stable ids, cursor pagination and windowed rendering rather than retaining an ever-growing DOM. Preserve scroll position and explain what happens when new items arrive ahead of the current cursor. Live updates need a reconnect/snapshot policy.

Test keyboard navigation, screen-reader labeling, slow networks, duplicate submit, out-of-order responses and partial backend failure. Report end-to-end p95/p99 and payload/rendering costs, not only framework benchmark scores. A frontend can appear responsive while displaying stale or unauthorized data, so correctness and accessibility belong in the design alongside performance.

### Work a small example

The response for query “a” may arrive after the response for “apple”; the UI must keep the result for the current query, not whichever HTTP call finishes last.

### Edge cases and common mistakes

Rendering 100000 DOM rows or treating disabled client buttons as an authorization or duplicate-payment control.

### Check your reasoning on related cases

**Design idempotency for an order or booking API.** A timeout after successful booking should not create a second booking when the client retries the same key.

What if a downstream service is not transactional with your database? Use a durable state machine and reconciliation, not an unsupported exactly-once claim.

**Design a cache without serving incorrect data.** Two identical question strings from users with different document permissions must not automatically share a retrieved-answer cache entry.

Why can invalidation be preferable to TTL alone? Critical updates may need to take effect sooner than the ordinary expiry window.
