## Question

<pre class="question-text" style="white-space:pre-wrap;font-family:inherit;line-height:1.55">This problem asks for a quantitative recommendation on which language model a product should use once latency and cost are counted, and how to design so that better models can be adopted later.

Task

A product serves 1,000,000 requests a day. Each request has 1,500 input tokens and 300 output tokens. The latency budget is 2 seconds at p95. Two models are available (illustrative round numbers, not any vendor&#x27;s real prices):

Input USD /1M tokens	Output USD /1M tokens	Time to first token	Output tokens/s
Large model	3.00	15.00	0.8 s	40
Small model	0.15	0.60	0.3 s	150

Answer the following, showing the calculation for every number.

1.
Cost and latency. Compute each model&#x27;s cost per request, its cost per day, and the time to produce a full 300-token response.
2.
Cascade. The small model answers every request, and a check escalates 15% of requests to the large model. Compute the daily cost and the saving against using the large model alone. Compute the latency of an escalated request, and propose two ways to reduce it.
3.
Agents. An agent makes 5 sequential model calls per task. Compute the task latency with each model, and give three structural changes that reduce it without changing the model.
4.
The latency budget. How many output tokens can the small model produce within 2 seconds? Propose changes to the output or the product that meet the budget.
5.
Multimodal input. Explain how image or audio input changes the cost and latency analysis, and when an upstream conversion step (for example OCR or transcription) is preferable to a multimodal model.
6.
Changing models over time. Model capability improves every few months and the problem domain shifts. Describe an architecture and an evaluation process that make adopting a better model a configuration change rather than a rewrite.</pre>

## Worked solution

1. Estimate an LLM serving capacity budget. Capacity is constrained by memory, computation, memory traffic and arrival patterns, so one parameter count is insufficient.
2. Estimate weight bytes, KV bytes for the live-token budget, temporary buffers and runtime overhead.
3. Benchmark prefill and decode at representative lengths and concurrency; measure throughput and tail latency together.
4. Set admission limits below the measured saturation point and handle overload with bounded queues, rejection or a stated fallback.
5. Choose a quantization approach and validate its cost. Quantization stores or computes numbers with fewer bits, trading representational precision for memory and possibly speed.
6. Specify which tensors are quantized: weights, activations or KV cache, and at what granularity and scale representation.
7. Estimate actual bytes including scales and metadata. Benchmark kernels on the target hardware; smaller storage does not automatically mean faster execution.
8. Evaluate representative tasks, long contexts and sensitive slices against a baseline. Keep a rollback path if quality regresses.
9. Reduce RAG latency without sacrificing correctness blindly. Optimize the measured critical path while protecting retrieval and answer quality.
10. Trace query processing, retrieval, reranking, prompt assembly, prefill and generation separately, including p95 and p99.
11. Try bounded candidate counts, batching, parallel independent retrieval and version-aware caches. Shorten redundant context before discarding necessary evidence.
12. Compare quality, latency and cost on the same query set; canary changes and preserve timeouts and fallbacks.

### Apply the exact contract

Measure quality, p95/p99 latency, throughput and cost under the same workload. Eliminate models violating a hard constraint, then choose on the remaining quality/cost frontier. Include queueing, retries and output length rather than quoting isolated per-token execution speed; validate the selected configuration on important failure slices.

### Small example / sanity check

Ten requests at 4000 cached tokens consume the same idealized KV tensor space as twenty at 2000, assuming identical models and no block rounding.

### Common trap

Sizing only for average context length or filling nominal GPU memory until allocations fail.
