## Question

This problem asks for a quantitative recommendation on which language model a product should use once latency and cost are counted, and how to design so that better models can be adopted later.

Task

A product serves 1,000,000 requests a day. Each request has 1,500 input tokens and 300 output tokens. The latency budget is 2 seconds at p95. Two models are available (illustrative round numbers, not any vendor's real prices):

Input USD /1M tokens	Output USD /1M tokens	Time to first token	Output tokens/s
Large model	3.00	15.00	0.8 s	40
Small model	0.15	0.60	0.3 s	150

Answer the following, showing the calculation for every number.
1. Cost and latency. Compute each model's cost per request, its cost per day, and the time to produce a full 300-token response.
2. Cascade. The small model answers every request, and a check escalates 15% of requests to the large model. Compute the daily cost and the saving against using the large model alone. Compute the latency of an escalated request, and propose two ways to reduce it.
3. Agents. An agent makes 5 sequential model calls per task. Compute the task latency with each model, and give three structural changes that reduce it without changing the model.
4. The latency budget. How many output tokens can the small model produce within 2 seconds? Propose changes to the output or the product that meet the budget.
5. Multimodal input. Explain how image or audio input changes the cost and latency analysis, and when an upstream conversion step (for example OCR or transcription) is preferable to a multimodal model.
6. Changing models over time. Model capability improves every few months and the problem domain shifts. Describe an architecture and an evaluation process that make adopting a better model a configuration change rather than a rewrite.

## Worked solution

### Solution outline

#### Estimate an LLM serving capacity budget.

Capacity is constrained by memory, computation, memory traffic and arrival patterns, so one parameter count is insufficient.

1. Estimate weight bytes, KV bytes for the live-token budget, temporary buffers and runtime overhead.
2. Benchmark prefill and decode at representative lengths and concurrency; measure throughput and tail latency together.
3. Set admission limits below the measured saturation point and handle overload with bounded queues, rejection or a stated fallback.

#### Choose a quantization approach and validate its cost.

Quantization stores or computes numbers with fewer bits, trading representational precision for memory and possibly speed.

1. Specify which tensors are quantized: weights, activations or KV cache, and at what granularity and scale representation.
2. Estimate actual bytes including scales and metadata. Benchmark kernels on the target hardware; smaller storage does not automatically mean faster execution.
3. Evaluate representative tasks, long contexts and sensitive slices against a baseline. Keep a rollback path if quality regresses.

#### Reduce RAG latency without sacrificing correctness blindly.

Optimize the measured critical path while protecting retrieval and answer quality.

1. Trace query processing, retrieval, reranking, prompt assembly, prefill and generation separately, including p95 and p99.
2. Try bounded candidate counts, batching, parallel independent retrieval and version-aware caches. Shorten redundant context before discarding necessary evidence.
3. Compare quality, latency and cost on the same query set; canary changes and preserve timeouts and fallbacks.

### Understand why the approach works

#### Separate service time, queueing and memory

A request's observed latency is not just the model kernel duration:

$$
T_{\rm request}=T_{\rm queue}+T_{\rm preprocess}+T_{\rm prefill}
+T_{\rm decode}+T_{\rm delivery}.
$$

Prefill processes the prompt; decode repeatedly adds tokens. Measure both time to first token and inter-token latency, because a configuration can improve aggregate throughput while worsening the user's experience. Batching amortizes work but may increase waiting.

Estimate the KV tensor budget independently of fixed weights. For equal-length requests,

$$
M_{\rm KV}=2BLT H_{\rm KV}d_h s,
$$

where $L$ is layer count, $T$ cached length and $s$ bytes per element. The factor two is keys plus values. With $L=32$, $T=4096$, $H_{\rm KV}=8$, $d_h=128$, $B=1$ and $s=2$, the raw cache is $512$ MiB, before allocator overhead.

Use measured capacity to set admission and live-token limits. If a worker serves batches of at most $b$ in $s_b$ seconds, $b/s_b$ is an optimistic service-rate ceiling, not a per-request guarantee. Sustained arrivals above that rate grow backlog; even lower averages can hide damaging bursts. Bound queues, define cancellation and partial-failure behavior, and compare latency on matched length/concurrency distributions rather than one isolated request.

### Apply this question’s exact contract

Measure quality, p95/p99 latency, throughput and cost under the same workload. Eliminate models violating a hard constraint, then choose on the remaining quality/cost frontier. Include queueing, retries and output length rather than quoting isolated per-token execution speed; validate the selected configuration on important failure slices.

### Work a small example

Ten requests at 4000 cached tokens consume the same idealized KV tensor space as twenty at 2000, assuming identical models and no block rounding.

### Edge cases and common mistakes

Sizing only for average context length or filling nominal GPU memory until allocations fail.

### Check your reasoning on related cases

**Choose a quantization approach and validate its cost.** A nominal 4-bit weight tensor uses one quarter the raw weight bytes of a 16-bit tensor, before scales, packing and unquantized tensors.

Why do outliers matter? A few large values can consume a shared quantization range and reduce resolution for common values.

**Reduce RAG latency without sacrificing correctness blindly.** If generation takes 2 seconds and retrieval takes 50 milliseconds, halving retrieval alone saves only 25 milliseconds of the serial path.

Why can caching hurt freshness? Cached answers may outlive the document or policy version that supported them.
