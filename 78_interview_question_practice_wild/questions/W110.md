## Question

This problem asks for a quantitative recommendation on which language model a product should use once latency and cost are counted, and how to design so that better models can be adopted later.

Task

A product serves 1,000,000 requests a day. Each request has 1,500 input tokens and 300 output tokens. The latency budget is 2 seconds at p95. Two models are available (illustrative round numbers, not any vendor's real prices):

Input USD /1M tokens	Output USD /1M tokens	Time to first token	Output tokens/s
Large model	3.00	15.00	0.8 s	40
Small model	0.15	0.60	0.3 s	150

Answer the following, showing the calculation for every number.
1. Cost and latency. Compute each model's cost per request, its cost per day, and the time to produce a full 300-token response.
2. Cascade. The small model answers every request, and a check escalates 15% of requests to the large model. Compute the daily cost and the saving against using the large model alone. Compute the latency of an escalated request, and propose two ways to reduce it.
3. Agents. An agent makes 5 sequential model calls per task. Compute the task latency with each model, and give three structural changes that reduce it without changing the model.
4. The latency budget. How many output tokens can the small model produce within 2 seconds? Propose changes to the output or the product that meet the budget.
5. Multimodal input. Explain how image or audio input changes the cost and latency analysis, and when an upstream conversion step (for example OCR or transcription) is preferable to a multimodal model.
6. Changing models over time. Model capability improves every few months and the problem domain shifts. Describe an architecture and an evaluation process that make adopting a better model a configuration change rather than a rewrite.

## Worked solution

### Cost and completion latency

Use $C=(1500\,c_{in}+300\,c_{out})/10^6$. Treat the table as deterministic service-time planning inputs, not a measured p95 guarantee. Approximate full-response latency by TTFT + output_tokens/rate (if TTFT already includes the first output token, replace 300 by 299).

| Model | Input/request | Output/request | Total/request | Daily total | Full response |
|---|---:|---:|---:|---:|---:|
| Large | $1500(3)/10^6=$.0045 | $300(15)/10^6=$.0045 | $.009 | $1M(.009)=$9,000 | $.8+300/40=8.3$s |
| Small | $1500(.15)/10^6=$.000225 | $300(.60)/10^6=$.000180 | $.000405 | $1M(.000405)=$405 | $.3+300/150=2.3$s |

Neither completes a 300-token reply within 2 seconds even before queueing and networking. The average arrival rate is $10^6/86400=11.57$ requests/s; capacity must also handle bursts and tail lengths.

### Cascade and sequential agents

The cascade pays for all small-model calls and 150,000 large-model calls: $405+150000(.009)=$**1,755/day**, excluding checker cost. Savings are $9000-1755=$**7,245/day**, or **80.5%**. A request escalated after the complete small answer takes $2.3+8.3=$**10.6s** plus checker overhead. Fifteen percent escalation means the slow route materially affects p95. Early routing based on the prompt/partial answer can avoid waiting for the full small answer; speculative parallel large generation can shorten latency but spends more and needs cancellation. Reusing a small draft through supported speculative decoding is another possibility requiring model/server compatibility and measurement.

Five sequential full calls take $5(8.3)=$**41.5s** large or $5(2.3)=$**11.5s** small, assuming the same input/output sizes at every call; real growing histories can cost more. Reduce serial depth by combining planning/formatting calls, execute independent tool/model branches concurrently, and cache deterministic repeated subresults under versioned keys. Stop early once the task is solved; streaming changes perceived progress but does not remove dependency latency.

### Meet the actual latency requirement

Within 2s the small model has $2-.3=1.7$s to decode, giving $1.7(150)=$**255 tokens** under the stated convention. Cap to fewer than 255 to reserve time for queue/network/checks, ask for a concise first answer with optional expansion, or return a typed summary and make detailed work asynchronous. If the budget means TTFT rather than full completion, state that explicitly; both table TTFTs fit, but completion still does not. Measure p95 under load instead of adding averages and labeling them p95.

Images add resolution/crop-dependent image tokens or per-image charges, encoding time and larger attention/cache work. Audio adds duration-dependent input units, transcription and possibly audio generation. Benchmark those paths separately; text-only token prices cannot estimate them directly. OCR/transcription is preferable when text content suffices, the upstream error rate is acceptable and reusable conversion lowers cost. It loses layout, visual reasoning, prosody and speaker cues; multimodal understanding may be needed for those tasks. Include conversion latency, privacy, retries and downstream error costs.

### Change models through an explicit interface

Expose a provider adapter `generate(messages, model_config, output_schema, deadline, request_id)` with normalized usage/errors/streaming events. Keep task prompts, schemas, routing thresholds and provider-specific capability mappings versioned outside business logic. Pin a model version per request; store input/evidence versions and outcome traces with sensitive content protected. Maintain frozen task/safety/latency/cost evaluations plus a rolling recent-domain set. Replay candidate models against baseline, test structured-output/tool compatibility, canary a small traffic share and promote configuration only if quality and latency budgets pass. Keep immediate rollback and acknowledge that a new tokenizer or tool protocol can require adapter work: an interface makes it localized, not magically unnecessary.
