## Question

<pre class="question-text" style="white-space:pre-wrap;font-family:inherit;line-height:1.55">GenAI Quant SWE Manager Deep Dive

Manager round for a GenAI / quant-infra SWE role, focused on practical LLM fine-tuning tradeoffs, production agent frameworks, prior scope, scale, latency, quality, cost, and reliability decisions.

Requirements

This round is a manager / technical deep dive rather than a coding prompt. Topics include:

Role scope and how past experience maps to GenAI / quant-infrastructure work.
When to choose full-precision SFT versus LoRA versus QLoRA.
How data size, model size, GPU memory, latency, quality target, and cost constraints affect that choice.
Agentic frameworks such as Pydantic-style structured output or ADK-style orchestration.
Production concerns: schema validation, tool calling, orchestration, state management, evaluation, observability, avoiding uncontrolled agent behavior, and avoiding silent failure.
Past project scope, concrete tech stack, why a particular solution was chosen, and how the solution would change at larger scale or tighter latency.
Notes
High-level &quot;I used LLMs&quot; answers are not enough. The round probes whether the candidate has made real tradeoffs under constraints.
Be concrete about hardware, model size, training budget, quality target, and serving latency.
Treat agent reliability as an engineering system: typed interfaces, validation, logs, evals, fallback behavior, and monitoring.</pre>

## Worked solution

1. Explain your most technically complex ML project. A strong answer demonstrates decisions and evidence, not a list of technologies.
2. State the user problem, constraints and your own contribution separately from the team's work.
3. Describe the data, baseline, hardest technical failure, alternatives considered and why the chosen approach fit.
4. Quantify the result using a valid comparison, explain limitations and say what you would change next. Use real experiences rather than invented metrics.
5. How do you debug a production latency regression? Locate the changed stage and workload before rewriting the model or adding hardware.
6. Compare request mix, prompt/output lengths, concurrency and cache hit rates against the baseline period.
7. Trace queueing, preprocessing, retrieval, model execution and network time separately, including tail percentiles.
8. Check deployment changes, batching, memory pressure and retries; validate a targeted fix under matched load and keep rollback available.
9. Estimate an LLM serving capacity budget. Capacity is constrained by memory, computation, memory traffic and arrival patterns, so one parameter count is insufficient.
10. Estimate weight bytes, KV bytes for the live-token budget, temporary buffers and runtime overhead.
11. Benchmark prefill and decode at representative lengths and concurrency; measure throughput and tail latency together.
12. Set admission limits below the measured saturation point and handle overload with bounded queues, rejection or a stated fallback.

### Small example / sanity check

“I reduced p95 latency from 800 to 500 ms on a matched workload while keeping task accuracy within the predefined margin” states both benefit and guardrail.

### Common trap

Saying “we built an LLM system” without explaining your choices or how success was measured.
