## Worked solution

### Sorting: bounds and the mechanism behind them

Quicksort partitions around a pivot. Balanced partitions give T(n)=2T(n/2)+Θ(n)=Θ(n log n); repeatedly choosing an extreme gives T(n)=T(n−1)+Θ(n)=Θ(n²). Random pivoting yields expected O(n log n) for any fixed input independent of the randomness, not a deterministic worst-case bound. First/last pivots fail on sorted data; median-of-three helps common patterns but adversarial input still exists. Three-way partition avoids wasting recursion on many equal keys. Recurse on the smaller partition and iterate the larger to bound stack O(log n); naive recursion can reach O(n).

Heapsort gives deterministic O(n log n) and O(1) auxiliary array space but worse locality/branch behavior than quicksort in many workloads. Mergesort gives O(n log n), is naturally stable and sequential-I/O friendly, but conventional array merging needs O(n) scratch space. Introsort starts with quicksort and switches to heapsort at a depth limit, combining common-case locality and worst-case protection. Stability, element move cost, cache behavior, data distribution and external storage decide the winner; comparison-sort Ω(n log n) does not constrain radix/counting methods under bounded-key assumptions.

### Linux primitives in the relevant execution path

A syscall crosses from user mode into the kernel to request an operation; it need not switch to another process. A context switch saves/restores execution context and may change address space/TLB state; switching threads in one process can avoid an address-space change but still has scheduling/cache costs. An interrupt notifies the CPU of an asynchronous device/timer event; the handler does bounded work and often defers heavier processing. An exception/page fault is synchronous to an instruction and may trigger disk I/O; do not call every kernel entry an interrupt.

Shared memory maps the same physical pages into multiple processes, avoiding repeated payload copies but requiring synchronization and a clear lifetime/ownership protocol. `mmap` maps file-backed or anonymous memory; access faults pages in lazily and uses page cache. `MAP_SHARED` exposes shared updates under synchronization/persistence rules, while `MAP_PRIVATE` is copy-on-write. Mapping a terabyte does not instantly load a terabyte, but touches, page tables, address space and truncation hazards still matter. Shared visibility is not equivalent to crash-durable fsync/msync semantics.

### tail -n without reading a huge file unnecessarily

For n≤0 output nothing. Open the regular file in binary mode, capture its size and examine the last byte. A final newline terminates the last line; it does not create an extra empty line. Starting at EOF, read fixed-size blocks backward (e.g. an assumed 64 KiB), scan each block from right to left and count newline delimiters. Skip the one exactly at EOF; after the nth earlier delimiter, the output begins immediately after it. If fewer than n lines exist, start at zero. Then stream bytes **forward** from that offset to the captured EOF, so memory is O(block size), even when n or an individual line is enormous. UTF-8 multibyte boundaries do not affect newline-byte discovery; decode only at a complete line boundary or emit bytes directly.

Example: `a\nb\n` with n=1 skips the final delimiter and finds the preceding one, outputting `b\n`; `a\nb` outputs `b`. A one-line file without newline returns all bytes. The scan costs O(bytes inspected in the suffix), at worst O(file size), plus unavoidable output cost. n huge approaches a full forward output but need not allocate n lines. `mmap` can simplify indexed backward access, but ordinary seek/read avoids giant mappings and concurrent-truncation fault risks. Define concurrent-file behavior: use an initial-size snapshot, cap reads at it, and report shrink/read errors; `tail -f` is a separate rotation-following feature. For a pipe, consume forward into a deque of n lines or a disk spool; memory is proportional to retained **bytes**, not a constant merely because line count is capped.
