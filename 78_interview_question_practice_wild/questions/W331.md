## Question

A host opens their dashboard and picks a date range; the page renders per-listing aggregates (nights booked, average price). With 100+ listings per host, the page becomes slow. Diagnose and redesign.

### Requirements

Three tables: Listings, Reservations, Pricing.
For a host with many listings and a user-picked date range, compute per-listing nights_booked and avg_price.
Page latency target: sub-second.
Notes
Diagnose first: the naive query joins three large tables and aggregates per listing — fan-out from a single host's listings to thousands of reservations × pricing rows is the cost.
Pre-aggregation: maintain a daily roll-up table ListingStatsDaily(listing_id, date, nights_booked, gross_revenue, price_count). The page query becomes a single range aggregation per listing, served from a 100x smaller table.
Refresh strategy: streaming (Kafka → materialized view on reservation events) or batch (nightly job over the previous day). Pick batch for "yesterday and earlier" + a smaller per-listing live view for "today".
Index choices: composite index (host_id, listing_id, date) on ListingStatsDaily; partition by month for cheap pruning.
Caching: cache the rendered dashboard per (host_id, date_range) for 60 seconds; invalidate on the host's own booking events.

## Worked solution

### Remove the reservation×price fan-out before tuning servers

First profile request traces and EXPLAIN/row counts: repeated per-listing queries, an unbounded three-table join, missing range indexes and payload size are distinct causes. Joining each reservation to every pricing row for a listing multiplies facts and can inflate both booked nights and revenue; an index cannot repair a wrong aggregation grain. Define a booked night by overlap of `[check_in,check_out)` with the report dates and define average price as booked-night revenue divided by priced booked nights. If product means advertised calendar price instead, keep a separate numerator/count.

Maintain `ListingStatsDaily(listing_id,date,nights_booked,gross_revenue,price_count)` at one listing/day grain, derived from deduplicated bookings/cancellations/price corrections. Historical closed days can batch nightly; today and late changes use an idempotent live delta or recompute affected days. Never add both a full daily recompute and the same live deltas. Query a host's listing IDs once and aggregate the smaller daily facts:

```sql
-- Chosen schema: listings(id,host_id), listing_stats_daily(listing_id,date,nights_booked,gross_revenue,price_count).
SELECT l.id AS listing_id,COALESCE(SUM(s.nights_booked),0) AS nights_booked,
       SUM(s.gross_revenue)/NULLIF(SUM(s.price_count),0) AS avg_price
FROM listings l LEFT JOIN listing_stats_daily s
 ON s.listing_id=l.id AND s.date>=:start_date AND s.date<=:end_date
WHERE l.host_id=:host_id GROUP BY l.id ORDER BY l.id;
```

For daily facts with revenue 100,count1 and revenue300,count2, average is 400/3, not mean(100,150)=125. LEFT JOIN retains empty listings; NULLIF returns NULL average with no priced nights. Keep date predicates in ON so empty listings are not dropped. The provided three source tables lack full column contracts, so this is an explicit rollup schema rather than a guessed original join.

At 100 listings over 365 days, read roughly 36,500 compact daily rows instead of a reservation×pricing product. This is a sizing comparison, not a guaranteed 100× reduction or subsecond benchmark. Index `(listing_id,date)` and `Listings(host_id,id)`; the suggested `(host_id,listing_id,date)` rollup index requires actually storing host_id and handling ownership changes. Month partitioning prunes wide histories. Cache by host,range,permissions/data version for ~60 seconds and invalidate on relevant booking/cancel edits. Verify aggregate correctness against raw small fixtures and run a representative 100+-listing load test before asserting the latency target.
