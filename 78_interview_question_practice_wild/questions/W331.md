## Question

A host opens their dashboard and picks a date range; the page renders per-listing aggregates (nights booked, average price). With 100+ listings per host, the page becomes slow. Diagnose and redesign.

### Requirements

Three tables: Listings, Reservations, Pricing.
For a host with many listings and a user-picked date range, compute per-listing nights_booked and avg_price.
Page latency target: sub-second.
Notes
Diagnose first: the naive query joins three large tables and aggregates per listing — fan-out from a single host's listings to thousands of reservations × pricing rows is the cost.
Pre-aggregation: maintain a daily roll-up table ListingStatsDaily(listing_id, date, nights_booked, gross_revenue, price_count). The page query becomes a single range aggregation per listing, served from a 100x smaller table.
Refresh strategy: streaming (Kafka → materialized view on reservation events) or batch (nightly job over the previous day). Pick batch for "yesterday and earlier" + a smaller per-listing live view for "today".
Index choices: composite index (host_id, listing_id, date) on ListingStatsDaily; partition by month for cheap pruning.
Caching: cache the rendered dashboard per (host_id, date_range) for 60 seconds; invalidate on the host's own booking events.

## Worked solution

### Solution outline

Match the access path to the actual filters and ordering, then verify using a query plan.

1. Inspect selectivity, join cardinalities, sort costs and how many rows must be scanned.
2. Consider an index beginning with selective equality filters followed by the requested order/time field, depending on the database and query.
3. Use keyset pagination when appropriate and measure write/storage overhead as well as read gains.

### Understand why the approach works

#### Establish row grain before writing a join

Say what one output row represents: an event, user, vendor, parent type or time interval. Then inspect the cardinality of every join. Joining two one-to-many relations can multiply rows and inflate both totals and averages; `DISTINCT` is not a general repair because legitimate equal-valued records can also exist.

For mergeable averages store a sum and count:

$$
\bar x_{\rm pooled}=\frac{\sum_g \operatorname{sum}_g}{\sum_g \operatorname{count}_g}.
$$

Do not average subgroup means unless the intended weighting gives each group equal weight. Likewise, daily distinct users cannot be added to obtain monthly distinct users.

Use half-open time windows, such as `timestamp >= start AND timestamp < end`, and name the timezone. For point-in-time training, feature **availability time** must not exceed prediction time; event occurrence and availability can differ.

Choose tie semantics deliberately: `ROW_NUMBER` produces a fixed number of rows under a deterministic secondary order, while `DENSE_RANK` preserves equal primary scores. A predicate on a nullable right-table column in `WHERE` can undo the unmatched-row preservation of a `LEFT JOIN`. Test duplicate events, absent dimension rows, nulls, tied maxima and an empty denominator. These cases explain correctness more convincingly than running only one ordinary example.

### Apply this question’s exact contract

Preaggregate reservations and pricing at a compatible listing-day grain before joining. Maintain separate sums/counts for average price, so the final average is sum(price_sum)/sum(price_count), not average(daily_average). Intersect reservations with the requested date window using the agreed night-boundary convention. A rollup keyed by listing/date and a host→listing lookup avoids reservation×pricing row multiplication.

### Work a small example

An ORDER BY created_at DESC LIMIT 20 query may benefit from an aligned index; a function on created_at can prevent a simple index lookup.

### Edge cases and common mistakes

Adding many indexes without checking whether the optimizer uses them or whether writes become too costly.
