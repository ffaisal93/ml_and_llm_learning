## Question

<pre class="question-text" style="white-space:pre-wrap;font-family:inherit;line-height:1.55">A host opens their dashboard and picks a date range; the page renders per-listing aggregates (nights booked, average price). With 100+ listings per host, the page becomes slow. Diagnose and redesign.

Requirements
Three tables: Listings, Reservations, Pricing.
For a host with many listings and a user-picked date range, compute per-listing nights_booked and avg_price.
Page latency target: sub-second.
Notes
Diagnose first: the naive query joins three large tables and aggregates per listing — fan-out from a single host&#x27;s listings to thousands of reservations × pricing rows is the cost.
Pre-aggregation: maintain a daily roll-up table ListingStatsDaily(listing_id, date, nights_booked, gross_revenue, price_count). The page query becomes a single range aggregation per listing, served from a 100x smaller table.
Refresh strategy: streaming (Kafka → materialized view on reservation events) or batch (nightly job over the previous day). Pick batch for &quot;yesterday and earlier&quot; + a smaller per-listing live view for &quot;today&quot;.
Index choices: composite index (host_id, listing_id, date) on ListingStatsDaily; partition by month for cheap pruning.
Caching: cache the rendered dashboard per (host_id, date_range) for 60 seconds; invalidate on the host&#x27;s own booking events.</pre>

## Worked solution

1. Optimize a latest-jobs query over a large table. Match the access path to the actual filters and ordering, then verify using a query plan.
2. Inspect selectivity, join cardinalities, sort costs and how many rows must be scanned.
3. Consider an index beginning with selective equality filters followed by the requested order/time field, depending on the database and query.
4. Use keyset pagination when appropriate and measure write/storage overhead as well as read gains.

### Apply the exact contract

Preaggregate reservations and pricing at a compatible listing-day grain before joining. Maintain separate sums/counts for average price, so the final average is sum(price_sum)/sum(price_count), not average(daily_average). Intersect reservations with the requested date window using the agreed night-boundary convention. A rollup keyed by listing/date and a host→listing lookup avoids reservation×pricing row multiplication.

### Small example / sanity check

An ORDER BY created_at DESC LIMIT 20 query may benefit from an aligned index; a function on created_at can prevent a simple index lookup.

### Common trap

Adding many indexes without checking whether the optimizer uses them or whether writes become too costly.
