## Question

Text models read tokens, and a program often has to count the tokens of a very large input to stay under a length limit. This question uses a byte-level tokenizer that is defined by a slow reference implementation. You explain how it works, write a fast version that returns exactly the same result, and then estimate the token count of a huge input by tokenizing only a small sample of it.

The reference tokenizer

A tokenizer is created from token_alphabet, a list of bytes objects. A token's id is its index in the list. You may assume:
1. token_alphabet has at least 256 elements.
2. It is sorted in non-decreasing order of token length.
3. All elements are unique.
4. The first 256 elements are the single-byte tokens: token_alphabet[i] == bytes([i]) for i from 0 to 255.

The class below is the starting point. slow_tokenize is the authoritative definition of the behavior. Do not modify it.

### What to implement

1. Explain the reference. Write an English description of how slow_tokenize works, precise enough for a strong student to re-implement it from scratch.
2. tokenize(self, text: bytes) -&gt; list[int]: return exactly what slow_tokenize(text) returns, but fast.
3. estimate_token_count(self, text: bytes, sample_size: int, rng: random.Random) -&gt; int: estimate len(self.tokenize(text)) without tokenizing the whole text.

### Rules

For tokenize:
1. The result must be identical to slow_tokenize for every valid alphabet and every input, including the empty input.
2. You may precompute anything in __init__, add helper methods and fields, and use the standard library. Do not change slow_tokenize.

For estimate_token_count:
3. You may call self.tokenize any number of times, but the total number of bytes passed to it over all calls must not exceed sample_size.
4. Other than calling self.tokenize, do not implement tokenizer logic. All randomness must come from rng; the same rng seed must give the same result.
5. If sample_size &gt;= len(text), return the exact token count.
6. Accuracy: when len(text) &gt; sample_size, the estimate is within 20% of the true count with probability at least 0.9 over the choice of rng. When sample_size &gt; 10000, it is within 5% with probability at least 0.9. This is required for texts made of words or short records of at most 64 bytes each (for example space-separated words), whose character, such as the typical word length, may change slowly along the text. Judge it on such text with a realistic alphabet, not on adversarial inputs.

### Examples

Example 1:

```python
token_alphabet = [bytes([i]) for i in range(256)] + [b"ab", b"bc", b"abc"]
```

tokenize(b"abc")    -&gt;  [258]
tokenize(b"abcab")  -&gt;  [258, 256]

Explanation: for b"abc", token 256 (ab) merges the first two bytes to give [256, 99]. Token 257 (bc) finds no pair. Token 258 (abc) merges 256 and 99, so the result is [258]. The text b"abcab" first becomes [256, 99, 256], and then only the first two ids merge.

Example 2:

```python
token_alphabet = [bytes([i]) for i in range(256)] + [b"bc", b"ab"]
```

tokenize(b"abc")  -&gt;  [97, 256]

Explanation: token 256 (bc) has a lower id than token 257 (ab), so it is applied first and gives [97, 256]. Token 257 then finds no pair (97, 98). The order of ids decides, not the position in the text.

Example 3:

```python
token_alphabet = [bytes([i]) for i in range(256)] + [b"aa", b"aaa", b"aaaa"]
```

tokenize(b"aaaaaaa")  -&gt;  [258, 257]

Explanation: aa merges left to right to give [256, 256, 256, 97]. Token aaa merges (256, 97) to give [256, 256, 257]. Token aaaa merges (256, 256) to give [258, 257]. A merge in one step never merges again in the same step.

Example 4:

```python
token_alphabet = [bytes([i]) for i in range(256)] + [b"ab"]
```

estimate_token_count(b"ab" * 600, 1200, rng)   -&gt;  600
estimate_token_count(b"ab" * 5000, 1000, rng)  -&gt;  about 5000

Explanation: in the first call the budget covers the whole text of 1200 bytes, so the exact count is returned. In the second call the text has 10000 bytes and exactly 5000 tokens, and a sample of 1000 bytes is enough to estimate it.

### Constraints

256 &lt;= len(token_alphabet) &lt;= 50000, and every token has at most 16 bytes.
For tokenize, len(text) &lt;= 10^6. A solution should handle that size in a few seconds in Python.
For estimate_token_count, len(text) may be as large as 10^9, so do not copy or scan the whole text. sample_size &gt;= 1000.

## Worked solution

### Match the reference's ranked pair passes

Start from byte ids. For each multi-byte token id in ascending order, find all two-token decompositions present in the alphabet and merge their nonoverlapping occurrences left-to-right exactly once. This is **ranked pair merging**, not greedy longest-byte-prefix matching. In “abc” an earlier bc token can consume b before a later ab token is considered.

Precompute `(left_id,right_id)->merged_id`. Maintain a linked sequence of live token nodes plus a heap ordered by `(merge_rank,leftmost_original_position)`. Pop the earliest valid pair, merge it, tombstone the right node and offer only affected neighboring pairs. Version checks discard stale heap entries. All components of a token are strictly shorter than it, and length-sorted ids make their ids smaller. Thus a merge can only create candidates at **higher** rank, never a new same-rank pair that the slow reference would not revisit. Position tie-breaking reproduces its left-to-right nonoverlap rule.

```python
import heapq,random,time

class ByteTokenizer:
    def __init__(self,token_alphabet):
        self.token_alphabet=token_alphabet
        self.token_to_id={token:idx for idx,token in enumerate(token_alphabet)}
        self.pair_rank={}
        for rank in range(256,len(token_alphabet)):
            token=token_alphabet[rank]
            for cut in range(1,len(token)):
                a=self.token_to_id.get(token[:cut]);b=self.token_to_id.get(token[cut:])
                if a is not None and b is not None:self.pair_rank[a,b]=rank

    def slow_tokenize(self,text):
        token_ids=list(text)
        for cur_token_id in range(256,len(self.token_alphabet)):
            cur_token_bytes=self.token_alphabet[cur_token_id];pairs_to_merge=set()
            for split_point in range(1,len(cur_token_bytes)):
                left_id=self.token_to_id.get(cur_token_bytes[:split_point])
                right_id=self.token_to_id.get(cur_token_bytes[split_point:])
                if left_id is not None and right_id is not None:pairs_to_merge.add((left_id,right_id))
            new_token_ids=[];i=0
            while i<len(token_ids):
                if i<len(token_ids)-1 and (token_ids[i],token_ids[i+1]) in pairs_to_merge:
                    new_token_ids.append(cur_token_id);i+=2
                else:new_token_ids.append(token_ids[i]);i+=1
            token_ids=new_token_ids
        return token_ids

    def tokenize(self,text):
        n=len(text)
        if not n:return []
        # Nodes retain original leftmost byte positions. Removed nodes are tombstoned.
        ids=list(text);previous=list(range(-1,n-1));following=list(range(1,n+1))
        alive=bytearray([1])*n;versions=[0]*n;heap=[]
        def offer(left):
            if left<0 or left>=n or not alive[left]:return
            right=following[left]
            if right==n:return
            rank=self.pair_rank.get((ids[left],ids[right]))
            if rank is not None:heapq.heappush(heap,(rank,left,right,versions[left],versions[right]))
        for left in range(n-1):offer(left)
        while heap:
            rank,left,right,lv,rv=heapq.heappop(heap)
            if not alive[left] or not alive[right] or following[left]!=right or versions[left]!=lv or versions[right]!=rv:continue
            ids[left]=rank;versions[left]+=1;alive[right]=0
            after=following[right];following[left]=after
            if after<n:previous[after]=left
            offer(previous[left]);offer(left)
        result=[];node=0
        while node<n:
            result.append(ids[node]);node=following[node]
        return result

    def estimate_token_count(self,text,sample_size,rng):
        n=len(text)
        if sample_size<1:raise ValueError('positive sample budget required')
        if sample_size>=n:return len(self.tokenize(text))
        # Stratified random contiguous windows reduce slow spatial distribution drift.
        # Use longer windows at larger budgets to reduce boundary bias.
        target_window=256 if sample_size<=10000 else 2048
        windows=max(1,sample_size//target_window)
        base,extra=divmod(sample_size,windows);tokens=bytes_used=0
        for j in range(windows):
            length=base+(j<extra)
            lo=j*n//windows;hi=(j+1)*n//windows
            start=rng.randrange(lo,hi-length+1) if hi-lo>=length else rng.randrange(0,n-length+1)
            tokens+=len(self.tokenize(text[start:start+length]));bytes_used+=length
        return int(round(tokens*n/bytes_used))
```

### Estimate count within the actual byte budget

If budget covers input, tokenize it exactly once. Otherwise sample randomized contiguous windows stratified over the full byte range, tokenize only those windows and multiply observed tokens/bytes by total length. Reuse only the supplied rng. Longer windows reduce extra boundary tokens; stratification helps when writing style changes slowly. The code passes exactly sample_size bytes in total and never scans/copies the whole huge input.

The stated 90%-probability accuracy cannot be proved for every text from the qualitative phrase “realistic alphabet/slowly changing”: no distribution, mixing rate or variance bound is provided, and finite samples cannot guarantee arbitrary-population accuracy. Treat those targets as empirical acceptance requirements on a declared representative word/record corpus, measure relative-error success over many seeds at ≤10k and >10k budgets, and increase sampling/window length within budget if it fails. Do not claim a universal statistical guarantee from this heuristic. Boundary bias and a localized rare style shift are specific limitations.

The executable checks all tokenization examples and 1,000 randomized exact matches to the unchanged reference, deterministic estimates and exact sampled-byte accounting, then times about one million bytes. A separate170,103-byte short-word fixture with a gradual distribution shift had59,999 true tokens. Across100 seeds, all100 estimates met20% tolerance at a1,000-byte budget (worst6.04% relative error), and all100 met5% tolerance at12,000 bytes (worst.882%). These are empirical fixture results, not a universal confidence theorem. Preprocessing costs O(sum token lengths), encoding O(n log n) worst case with O(n) heap/link storage; each successful merge removes a node and creates at most two offers. A production implementation can use compact arrays to reduce Python-object overhead. The estimate's work depends on sample_size, not billion-byte input length, aside from constant-time slice access.
