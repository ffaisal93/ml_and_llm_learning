## Question

<pre class="question-text" style="white-space:pre-wrap;font-family:inherit;line-height:1.55">Text models read tokens, and a program often has to count the tokens of a very large input to stay under a length limit. This question uses a byte-level tokenizer that is defined by a slow reference implementation. You explain how it works, write a fast version that returns exactly the same result, and then estimate the token count of a huge input by tokenizing only a small sample of it.

The reference tokenizer

A tokenizer is created from token_alphabet, a list of bytes objects. A token&#x27;s id is its index in the list. You may assume:

1.
token_alphabet has at least 256 elements.
2.
It is sorted in non-decreasing order of token length.
3.
All elements are unique.
4.
The first 256 elements are the single-byte tokens: token_alphabet[i] == bytes([i]) for i from 0 to 255.

The class below is the starting point. slow_tokenize is the authoritative definition of the behavior. Do not modify it.

class ByteTokenizer:
def __init__(self, token_alphabet: list[bytes]):
self.token_alphabet = token_alphabet
# Map token byte sequences to indices
self.token_to_id = {token: idx for idx, token in enumerate(token_alphabet)}

def slow_tokenize(self, text: bytes) -&gt; list[int]:
# STEP 1: every byte is its own single-byte token (b&quot;hello&quot; -&gt; [104, 101, 108, 108, 111]).
token_ids: list[int] = list(text)

# STEP 2: visit each multi-byte token in ascending order of its index,
# and merge adjacent pairs of tokens that spell it.
for cur_token_id in range(256, len(self.token_alphabet)):
cur_token_bytes = self.token_alphabet[cur_token_id]

# All pairs (left token, right token) whose bytes join to the current token.
pairs_to_merge: set[tuple[int, int]] = set()
for split_point in range(1, len(cur_token_bytes)):
left_id = self.token_to_id.get(cur_token_bytes[:split_point])
right_id = self.token_to_id.get(cur_token_bytes[split_point:])
if left_id is not None and right_id is not None:
pairs_to_merge.add((left_id, right_id))

# One left-to-right pass: merge each matching adjacent pair into the current token.
new_token_ids: list[int] = []
i = 0
while i &lt; len(token_ids):
if i &lt; len(token_ids) - 1 and (token_ids[i], token_ids[i + 1]) in pairs_to_merge:
new_token_ids.append(cur_token_id)
i += 2
else:
new_token_ids.append(token_ids[i])
i += 1
token_ids = new_token_ids

return token_ids
What to implement
1.
Explain the reference. Write an English description of how slow_tokenize works, precise enough for a strong student to re-implement it from scratch.
2.
tokenize(self, text: bytes) -&gt; list[int]: return exactly what slow_tokenize(text) returns, but fast.
3.
estimate_token_count(self, text: bytes, sample_size: int, rng: random.Random) -&gt; int: estimate len(self.tokenize(text)) without tokenizing the whole text.
Rules

For tokenize:

1.
The result must be identical to slow_tokenize for every valid alphabet and every input, including the empty input.
2.
You may precompute anything in __init__, add helper methods and fields, and use the standard library. Do not change slow_tokenize.

For estimate_token_count:

3.
You may call self.tokenize any number of times, but the total number of bytes passed to it over all calls must not exceed sample_size.
4.
Other than calling self.tokenize, do not implement tokenizer logic. All randomness must come from rng; the same rng seed must give the same result.
5.
If sample_size &gt;= len(text), return the exact token count.
6.
Accuracy: when len(text) &gt; sample_size, the estimate is within 20% of the true count with probability at least 0.9 over the choice of rng. When sample_size &gt; 10000, it is within 5% with probability at least 0.9. This is required for texts made of words or short records of at most 64 bytes each (for example space-separated words), whose character, such as the typical word length, may change slowly along the text. Judge it on such text with a realistic alphabet, not on adversarial inputs.
Examples

Example 1:

token_alphabet = [bytes([i]) for i in range(256)] + [b&quot;ab&quot;, b&quot;bc&quot;, b&quot;abc&quot;]
tokenize(b&quot;abc&quot;)    -&gt;  [258]
tokenize(b&quot;abcab&quot;)  -&gt;  [258, 256]

Explanation: for b&quot;abc&quot;, token 256 (ab) merges the first two bytes to give [256, 99]. Token 257 (bc) finds no pair. Token 258 (abc) merges 256 and 99, so the result is [258]. The text b&quot;abcab&quot; first becomes [256, 99, 256], and then only the first two ids merge.

Example 2:

token_alphabet = [bytes([i]) for i in range(256)] + [b&quot;bc&quot;, b&quot;ab&quot;]
tokenize(b&quot;abc&quot;)  -&gt;  [97, 256]

Explanation: token 256 (bc) has a lower id than token 257 (ab), so it is applied first and gives [97, 256]. Token 257 then finds no pair (97, 98). The order of ids decides, not the position in the text.

Example 3:

token_alphabet = [bytes([i]) for i in range(256)] + [b&quot;aa&quot;, b&quot;aaa&quot;, b&quot;aaaa&quot;]
tokenize(b&quot;aaaaaaa&quot;)  -&gt;  [258, 257]

Explanation: aa merges left to right to give [256, 256, 256, 97]. Token aaa merges (256, 97) to give [256, 256, 257]. Token aaaa merges (256, 256) to give [258, 257]. A merge in one step never merges again in the same step.

Example 4:

token_alphabet = [bytes([i]) for i in range(256)] + [b&quot;ab&quot;]
estimate_token_count(b&quot;ab&quot; * 600, 1200, rng)   -&gt;  600
estimate_token_count(b&quot;ab&quot; * 5000, 1000, rng)  -&gt;  about 5000

Explanation: in the first call the budget covers the whole text of 1200 bytes, so the exact count is returned. In the second call the text has 10000 bytes and exactly 5000 tokens, and a sample of 1000 bytes is enough to estimate it.

Constraints
256 &lt;= len(token_alphabet) &lt;= 50000, and every token has at most 16 bytes.
For tokenize, len(text) &lt;= 10^6. A solution should handle that size in a few seconds in Python.
For estimate_token_count, len(text) may be as large as 10^9, so do not copy or scan the whole text. sample_size &gt;= 1000.</pre>

## Worked solution

1. Optimize a tokenizer without changing its semantics. An efficient encoder must preserve the specified tokenization, including tie rules and boundaries.
2. First implement and test a simple reference over small strings and special tokens.
3. For fixed-vocabulary longest matching, consider a trie; for ranked BPE merges, use a representation that updates neighboring merge candidates efficiently.
4. Benchmark normalization, Unicode handling and merge operations separately, comparing exact token ids against the reference.
5. Implement a deterministic toy tokenizer, then explain what BPE adds. A tokenizer turns text into a reproducible token sequence; BPE learns reusable merges beyond individual symbols.
6. Define the base alphabet and normalization policy, including whitespace and unknown characters.
7. For BPE training, repeatedly count adjacent pairs, choose the most frequent under a deterministic tie rule, merge non-overlapping occurrences and update the vocabulary.
8. At encoding time apply learned merge ranks, not a fresh frequency count on each document. Keep decoding and special-token handling explicit.

### Small example / sanity check

Changing a merge tie-break can alter token ids even if the decoded text is identical.

### Common trap

Replacing a BPE encoder with greedy longest-vocabulary matching and assuming the results always agree.
