## Question

Text models read tokens, and a program often has to count the tokens of a very large input to stay under a length limit. This question uses a byte-level tokenizer that is defined by a slow reference implementation. You explain how it works, write a fast version that returns exactly the same result, and then estimate the token count of a huge input by tokenizing only a small sample of it.

The reference tokenizer

A tokenizer is created from token_alphabet, a list of bytes objects. A token's id is its index in the list. You may assume:
1. token_alphabet has at least 256 elements.
2. It is sorted in non-decreasing order of token length.
3. All elements are unique.
4. The first 256 elements are the single-byte tokens: token_alphabet[i] == bytes([i]) for i from 0 to 255.

The class below is the starting point. slow_tokenize is the authoritative definition of the behavior. Do not modify it.

```python
# STEP 2: visit each multi-byte token in ascending order of its index,
```


for split_point in range(1, len(cur_token_bytes)):

if left_id is not None and right_id is not None:

### What to implement

1. Explain the reference. Write an English description of how slow_tokenize works, precise enough for a strong student to re-implement it from scratch.
2. tokenize(self, text: bytes) -&gt; list[int]: return exactly what slow_tokenize(text) returns, but fast.
3. estimate_token_count(self, text: bytes, sample_size: int, rng: random.Random) -&gt; int: estimate len(self.tokenize(text)) without tokenizing the whole text.

### Rules

For tokenize:
1. The result must be identical to slow_tokenize for every valid alphabet and every input, including the empty input.
2. You may precompute anything in __init__, add helper methods and fields, and use the standard library. Do not change slow_tokenize.

For estimate_token_count:
3. You may call self.tokenize any number of times, but the total number of bytes passed to it over all calls must not exceed sample_size.
4. Other than calling self.tokenize, do not implement tokenizer logic. All randomness must come from rng; the same rng seed must give the same result.
5. If sample_size &gt;= len(text), return the exact token count.
6. Accuracy: when len(text) &gt; sample_size, the estimate is within 20% of the true count with probability at least 0.9 over the choice of rng. When sample_size &gt; 10000, it is within 5% with probability at least 0.9. This is required for texts made of words or short records of at most 64 bytes each (for example space-separated words), whose character, such as the typical word length, may change slowly along the text. Judge it on such text with a realistic alphabet, not on adversarial inputs.

### Examples

Example 1:

```python
token_alphabet = [bytes([i]) for i in range(256)] + [b"ab", b"bc", b"abc"]
```

tokenize(b"abc")    -&gt;  [258]
tokenize(b"abcab")  -&gt;  [258, 256]

Explanation: for b"abc", token 256 (ab) merges the first two bytes to give [256, 99]. Token 257 (bc) finds no pair. Token 258 (abc) merges 256 and 99, so the result is [258]. The text b"abcab" first becomes [256, 99, 256], and then only the first two ids merge.

Example 2:

```python
token_alphabet = [bytes([i]) for i in range(256)] + [b"bc", b"ab"]
```

tokenize(b"abc")  -&gt;  [97, 256]

Explanation: token 256 (bc) has a lower id than token 257 (ab), so it is applied first and gives [97, 256]. Token 257 then finds no pair (97, 98). The order of ids decides, not the position in the text.

Example 3:

```python
token_alphabet = [bytes([i]) for i in range(256)] + [b"aa", b"aaa", b"aaaa"]
```

tokenize(b"aaaaaaa")  -&gt;  [258, 257]

Explanation: aa merges left to right to give [256, 256, 256, 97]. Token aaa merges (256, 97) to give [256, 256, 257]. Token aaaa merges (256, 256) to give [258, 257]. A merge in one step never merges again in the same step.

Example 4:

```python
token_alphabet = [bytes([i]) for i in range(256)] + [b"ab"]
```

estimate_token_count(b"ab" * 600, 1200, rng)   -&gt;  600
estimate_token_count(b"ab" * 5000, 1000, rng)  -&gt;  about 5000

Explanation: in the first call the budget covers the whole text of 1200 bytes, so the exact count is returned. In the second call the text has 10000 bytes and exactly 5000 tokens, and a sample of 1000 bytes is enough to estimate it.

### Constraints

256 &lt;= len(token_alphabet) &lt;= 50000, and every token has at most 16 bytes.
For tokenize, len(text) &lt;= 10^6. A solution should handle that size in a few seconds in Python.
For estimate_token_count, len(text) may be as large as 10^9, so do not copy or scan the whole text. sample_size &gt;= 1000.

## Worked solution

### Solution outline

#### Optimize a tokenizer without changing its semantics.

An efficient encoder must preserve the specified tokenization, including tie rules and boundaries.

1. First implement and test a simple reference over small strings and special tokens.
2. For fixed-vocabulary longest matching, consider a trie; for ranked BPE merges, use a representation that updates neighboring merge candidates efficiently.
3. Benchmark normalization, Unicode handling and merge operations separately, comparing exact token ids against the reference.

#### Implement a deterministic toy tokenizer, then explain what BPE adds.

A tokenizer turns text into a reproducible token sequence; BPE learns reusable merges beyond individual symbols.

1. Define the base alphabet and normalization policy, including whitespace and unknown characters.
2. For BPE training, repeatedly count adjacent pairs, choose the most frequent under a deterministic tie rule, merge non-overlapping occurrences and update the vocabulary.
3. At encoding time apply learned merge ranks, not a fresh frequency count on each document. Keep decoding and special-token handling explicit.

### Understand why the approach works

#### Build the computation before optimizing it

Start by saying which axis represents examples, positions, heads and features. With batch size $B$, query length $T_q$, key length $T_k$ and head width $d_k$, a head receives $Q\in\mathbb R^{B\times T_q\times d_k}$ and $K\in\mathbb R^{B\times T_k\times d_k}$. Values may have a different final width $d_v$. The essential operation is

$$
S=\frac{QK^\top}{\sqrt{d_k}}+M,\qquad
P_{ij}=\frac{\exp(S_{ij}-m_i)}{\sum_j\exp(S_{ij}-m_i)},\qquad O=PV.
$$

Here the transpose affects the final two axes, $m_i=\max_j S_{ij}$ is a row maximum, and $M$ contains zero for allowed positions and $-\infty$ for forbidden ones. Each query produces one distribution **over keys**, so summing the wrong axis changes the operation even when the output shape looks plausible.

For a tiny check, give a query access to exactly one key. Its output must equal that key's value, regardless of the score. Then change a forbidden future token: earlier causal outputs must remain unchanged. These checks expose mistakes that a random shape test misses.

Explain the limitation of the simple implementation. Explicitly materializing $P$ uses $O(T_qT_k)$ score storage per head. A reference implementation is useful for correctness; a tiled kernel can avoid that materialization while preserving the mathematical attention operation. Generation additionally needs correct target shifts, positions and cache state, not just a working matrix multiplication.
