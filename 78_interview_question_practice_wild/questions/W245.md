## Question

Design a component that answers "is this user id new?" and records it if so, for a population that starts at one million ids and keeps growing. Trade latency, memory and accuracy against each other, and say which one you give up at each step.

The operation

check_and_insert(user_id) -&gt; bool returns True if the id was not seen before, and records it. It returns False if the id was already recorded. Ids are opaque strings of up to 36 bytes.

### Parts

1. Baseline. Start with one million ids on one machine. Give the simplest correct design and estimate its memory. State its latency and its failure modes (process restart, growth).
2. Memory pressure. Memory is now limited to a few megabytes for the hot path, and most calls are for ids that are new. Introduce a probabilistic structure. Size it for a 1% false-positive rate at one million ids: give the bits per id, the total size, and the number of hash functions. Then repeat for 0.1%.
3. Correctness. Explain exactly what a false positive and a false negative would do to check_and_insert. Show how your design still returns the correct answer for every call.
4. Durability and growth. The id set must survive restarts and grow to one billion ids that do not fit in memory. Design the storage layer: what lives in memory, what lives on disk, how writes are made durable, and how a lookup proceeds.
5. Concurrency. Two requests with the same new id arrive at the same time. Make sure exactly one of them gets True.

## Worked solution

### Exactness belongs to the authoritative set

For one million opaque IDs, start with an exact hash set and an atomic lock around test-and-insert. The raw string payload is at most 36 MB; an illustrative 64-bit runtime budget of 50–80 bytes/string plus 20–40 bytes of table slack means roughly 100–160 MB total, not 36 MB. Measure the actual runtime. Average operations are O(1), but hash-table resizing and adversarial hashing affect tails. A process restart loses an unpersisted set; unbounded growth eventually exhausts RAM.

A Bloom filter is only a negative-lookup accelerator. For n items and target false-positive probability f,

$$m=-n\ln f/(\ln2)^2,\qquad k=(m/n)\ln2.$$

At n=1,000,000, f=.01 needs 9.585 bits/id, 9.585 million bits = 1.198 MB (1.143 MiB), k ≈ 6.64 so use 7 hashes. At f=.001 it needs 14.378 bits/id, 1.797 MB (1.714 MiB), k ≈ 9.97 so use 10. A false positive says “possibly old” for a new ID; returning False directly would wrongly discard a new user. A correct Bloom filter has no false negatives for inserted IDs, but a lost update/restart/deletion implementation bug can create one and incorrectly report an old user as new.

### Durable read/write path

Use a sharded exact on-disk key-value/LSM set with WAL and per-key owner serialization. Each request routes to the owning shard. Under that key's lock: consult a synchronized Bloom filter; if positive, verify exact membership; if negative, skip that membership probe; append a new ID durably to the WAL/set, update the filter before releasing ownership, then return True. If exact membership exists, return False. On restart rebuild/recover the filter before trusting negatives. A unique insert/conditional put in a database can replace the owner lock; it is the final concurrency authority, even when the filter says absent.

Two simultaneous new IDs serialize at the authority: one durable insert returns True, the other sees existing and returns False. Write acknowledgment precedes returning True; a crash with an ambiguous client response requires an operation key if retries must recover the original boolean rather than return the now-correct “already present.” Replicate synchronously if surviving machine loss is required. Filter and exact-set updates must never expose a committed ID with an uninitialized negative filter.

With 90% new calls, expected **verification membership probes** are $0.10+0.90f$: .109 at 1% and .1009 at .1%, assuming synchronized filters and one exact probe per positive. This is not a universal count of physical disk reads: a cached positive may read zero pages, an uncached LSM lookup may touch multiple files, and unique inserts/index maintenance/compaction can read disk too. Under the explicit idealization “one uncached exact lookup = one disk read, append-only insert requires none,” those are the expected reads/call. State this distinction rather than promising it for a B-tree.

At one billion IDs, raw payload can be 36 GB and a 1% global Bloom filter is about 1.2 GB, exceeding the few-MB hot budget. Use per-SSTable on-disk filters with bounded cache, partitioned filter blocks, and an in-memory memtable/WAL index; account for their cache misses separately. Growing a fixed filter beyond its design n raises false positives; rotate/grow partitioned filters with the immutable sorted runs. The correctness trade is always extra exact work on positives, never silently accepting approximate membership as exact.
