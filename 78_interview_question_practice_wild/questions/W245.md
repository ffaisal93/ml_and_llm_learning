## Question

<pre class="question-text" style="white-space:pre-wrap;font-family:inherit;line-height:1.55">Design a component that answers &quot;is this user id new?&quot; and records it if so, for a population that starts at one million ids and keeps growing. Trade latency, memory and accuracy against each other, and say which one you give up at each step.

The operation

check_and_insert(user_id) -&gt; bool returns True if the id was not seen before, and records it. It returns False if the id was already recorded. Ids are opaque strings of up to 36 bytes.

Parts
1.
Baseline. Start with one million ids on one machine. Give the simplest correct design and estimate its memory. State its latency and its failure modes (process restart, growth).
2.
Memory pressure. Memory is now limited to a few megabytes for the hot path, and most calls are for ids that are new. Introduce a probabilistic structure. Size it for a 1% false-positive rate at one million ids: give the bits per id, the total size, and the number of hash functions. Then repeat for 0.1%.
3.
Correctness. Explain exactly what a false positive and a false negative would do to check_and_insert. Show how your design still returns the correct answer for every call.
4.
Durability and growth. The id set must survive restarts and grow to one billion ids that do not fit in memory. Design the storage layer: what lives in memory, what lives on disk, how writes are made durable, and how a lookup proceeds.
5.
Concurrency. Two requests with the same new id arrive at the same time. Make sure exactly one of them gets True.
Deliverables
A diagram or step list of the read path and the write path.
The sizing numbers from Part 2, with the formulas.
The expected number of disk reads per call for a workload where 90% of calls carry a new id.</pre>

## Worked solution

1. Define the shared-state invariant and the linearization point of each operation. Protect check-and-insert, task transitions and cache mutations with one appropriate lock or atomic primitive, not separate unlocked checks.
2. Wait on a condition variable in a while loop that rechecks the predicate under the lock; release it while waiting and notify after the state transition. Compute expensive work outside the lock with an explicit single-flight/in-flight marker where needed.
3. For cancellation, distinguish queued cancellation from cooperative cancellation of running work; release resources and complete waiters exactly once.
4. Test concurrent duplicates, spurious wakeups, exceptions and shutdown. A local lock does not provide cross-process or distributed atomicity.

### Small example / sanity check

Two threads racing to add the same user id must return one insertion and one already-present result. Waiting for a cache fill must not block the filler from acquiring its completion lock.

### Common trap

Holding the lock across slow external work or using if instead of while around a condition wait.
