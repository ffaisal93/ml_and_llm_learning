## Question

You are given a fixed set of 4 business tables (schemas resemble Notion's real data). In a 1-hour SQL screen, you need to solve 5 SQL query questions that repeatedly use these 4 tables. Topics covered include:

### Requirements

For each question, return the requested result set (typically dimension columns plus one or more metrics).
Correctly handle nulls, deduplication, and row multiplication caused by joins.
The final question has 3 sub-questions. You may solve them step-by-step, and use the result of an earlier sub-question as a filter for later sub-questions (e.g., via CTEs/subqueries).

## Worked solution

### Solution outline

1. The five concrete sub-questions and four complete schemas are not supplied, so exact final queries are not identifiable from the topic list alone. Do not invent table/column names and present them as the required outputs.
2. For each actual sub-question, state output grain, join keys/cardinalities, null treatment, filters and tie rules, then preaggregate one-to-many relations before joining.
3. Use a LEFT JOIN with filters in the appropriate ON clause to preserve unmatched left rows. Use self-joins with distinct aliases and full composite keys; parenthesize OR conditions so they cannot bypass required filters.
4. Use CTEs for the staged final question and window functions over already-correct aggregates. The SQL lab and the separate block/event/country questions provide fully worked, executable examples of these operations.

### Understand why the approach works

#### Establish row grain before writing a join

Say what one output row represents: an event, user, vendor, parent type or time interval. Then inspect the cardinality of every join. Joining two one-to-many relations can multiply rows and inflate both totals and averages; `DISTINCT` is not a general repair because legitimate equal-valued records can also exist.

For mergeable averages store a sum and count:

$$
\bar x_{\rm pooled}=\frac{\sum_g \operatorname{sum}_g}{\sum_g \operatorname{count}_g}.
$$

Do not average subgroup means unless the intended weighting gives each group equal weight. Likewise, daily distinct users cannot be added to obtain monthly distinct users.

Use half-open time windows, such as `timestamp >= start AND timestamp < end`, and name the timezone. For point-in-time training, feature **availability time** must not exceed prediction time; event occurrence and availability can differ.

Choose tie semantics deliberately: `ROW_NUMBER` produces a fixed number of rows under a deterministic secondary order, while `DENSE_RANK` preserves equal primary scores. A predicate on a nullable right-table column in `WHERE` can undo the unmatched-row preservation of a `LEFT JOIN`. Test duplicate events, absent dimension rows, nulls, tied maxima and an empty denominator. These cases explain correctness more convincingly than running only one ordinary example.

### Work a small example

An illustrative users LEFT JOIN filtered_events preserves users without events; putting a right-table predicate in WHERE can accidentally turn it into an inner join.

### Edge cases and common mistakes

Claiming to solve five missing query statements or hiding row multiplication behind DISTINCT without checking the intended grain.

### Check your reasoning on related cases

**Find the top three vendors by net charge over the last two years.** A vendor with charges 100 and refunds 30 has net charge 70, not gross charge 100.

What if multiple currencies exist? Convert using an explicit rate/date policy before adding amounts.

**Find each user's consecutive login-day streaks.** Days 1,2,4,5,6 contain streaks of lengths 2 and 3; multiple logins on day 5 do not lengthen either streak.

How do you count currently active streaks? Restrict run end dates using a stated as-of and grace policy.

**Find the most frequent event type and its most popular plan.** The globally most popular plan need not be the most popular plan inside the most frequent event type.

What ambiguity should you clarify? Whether “most frequent” counts events, distinct users or distinct sessions.

**Calculate project duration and budget per employee.** A 1000-unit project assigned equally to four employees contributes 250 units each, not 1000 each, if allocation rather than participation totals is requested.

Why can summed durations be misleading? Employees may work on overlapping projects simultaneously.
