You name the observation tool you&#x27;d run (tail -f, dmesg, ps, df, iostat, netstat, tcpdump, log search) and the interviewer reads back the output you&#x27;d see.

## Worked solution

1. How do you debug a production latency regression? Locate the changed stage and workload before rewriting the model or adding hardware.
2. Compare request mix, prompt/output lengths, concurrency and cache hit rates against the baseline period.
3. Trace queueing, preprocessing, retrieval, model execution and network time separately, including tail percentiles.
4. Check deployment changes, batching, memory pressure and retries; validate a targeted fix under matched load and keep rollback available.
5. Detect a data-pipeline issue before retraining a model. Operational data checks can explain metric changes more directly than model modifications.
6. Compare feature freshness, null rates, value ranges, schema versions and entity-join coverage with normal baselines.
7. Trace a few affected examples end to end from source event to served feature and prediction.
8. Repair and backfill safely, then reassess model performance on mature labels before deciding whether retraining is needed.

### Apply the exact contract

First assess impact and preserve evidence; check recent changes, dependency health and saturation. For disk-full, inspect filesystem space/inodes, open deleted files and runaway logs before deleting anything; for a server outage, trace DNS→load balancer→process→dependency. Apply a reversible mitigation and verify recovery. Never present indiscriminate deletion or restart loops as the diagnosis.

### Small example / sanity check

If median latency is stable but p99 worsens, a small fraction of long requests or queueing spikes may dominate the regression.

### Common trap

Comparing two benchmark runs with different lengths or concurrency and attributing the difference solely to code.
