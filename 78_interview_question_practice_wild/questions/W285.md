## Question

Meta Production Engineer signature round. The interviewer reads a one-sentence production incident (e.g. 'Customer orders are failing; you've just been paged at 2 AM; there was a recent code or traffic change'). You drive the diagnosis step by step — pure Linux/SRE skills, no code.

You name the observation tool you'd run (tail -f, dmesg, ps, df, iostat, netstat, tcpdump, log search) and the interviewer reads back the output you'd see.
Each output narrows the hypothesis space; you pick the next probe.
Surface a root cause (disk full, OOM kill, stuck connection pool, expired cert, runaway log, kernel OOM).
Discuss immediate mitigation and durable fix separately.

Scoring axis is the order you ask, not the answer. The interviewer adds constraints ('no metrics', 'customer impact ongoing') to test how you reprioritize.

## Worked solution

### Start with impact and the failing boundary

This is an interactive verbal diagnosis, not a command checklist with a predetermined cause. State which requests/regions fail, when it began and whether a rollout/traffic change correlates. Check external request/DNS/TLS/load-balancer health, then the specific host/process/dependency. If no monitoring exists, use a known safe request and system tools to gather direct evidence. Preserve the incident timeline and take a reversible customer-impact mitigation in parallel when justified.

For a web-server-down trace, ask for `curl -v`/TLS results, DNS resolution and load-balancer target health. If the host is reachable but connection refused, inspect `ss -lntp` (or platform `netstat`) and service/process state with `ps`/service logs. If connections open but hang, inspect request/connection counts, thread/worker saturation, dependency latency and connection-pool limits. `top`, `vmstat`, `iostat` distinguish CPU, memory and I/O pressure; `dmesg`/kernel logs can confirm OOM kills rather than guessing from an absent process. Packet captures are scoped to the suspect link and protect sensitive traffic.

### A conditional disk-full walkthrough

Suppose application logs report ENOSPC. Run `df -h` **and** `df -i` on the actual affected mount: byte exhaustion and inode exhaustion need different fixes. Use a bounded directory-size inspection on that mount to locate growth, not an expensive full-system scan under overload. If filesystem usage is high but visible files do not explain it, inspect deleted-but-open files (`lsof +L1`), mount/snapshot/reserved-space behavior and process file descriptors. A runaway log may still hold disk after unlinking, so blind deletion is both destructive and ineffective.

Immediate mitigation could drain the affected instance, extend a volume where supported, rotate/reopen a confirmed expendable log through its documented mechanism, or stop the proven runaway producer. Do not delete database files, unknown logs or audit evidence. If no safe cleanup is known, use a healthy replica/capacity route and an approved repair. Then verify free bytes/inodes, successful representative orders, latency/error recovery and backlog drain; a restarted process alone is not proof of recovery.

### Distinguish alternative evidence and durable repair

OOM: confirm kernel kill/cgroup limits and memory growth, mitigate by rollback/drain or a bounded resource change, then identify leak/burst and load-test. Expired certificate: verify certificate chain/expiry/SNI, rotate through the standard deployment and test clients, then add expiry automation. Connection-pool exhaustion: establish waiting versus active connections, slow dependency/transaction behavior and retry amplification; bound retries/timeouts and fix the cause instead of just increasing every pool.

For disk growth, durable repair includes log size/retention/rotation, volume/inode alerts, quotas, producer rate limits and a restore test; for any cause add a reproducer/canary and ownership. Adapt the next probe to the interviewer's observed output and ongoing impact. Missing measurements should narrow the plan, not justify claiming a root cause. No live system is changed by this answer; every branch is conditional on evidence, as the verbal round requires.
