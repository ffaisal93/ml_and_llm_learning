## Question

Meta Production Engineer signature round. The interviewer reads a one-sentence production incident (e.g. 'Customer orders are failing; you've just been paged at 2 AM; there was a recent code or traffic change'). You drive the diagnosis step by step — pure Linux/SRE skills, no code.

You name the observation tool you'd run (tail -f, dmesg, ps, df, iostat, netstat, tcpdump, log search) and the interviewer reads back the output you'd see.
Each output narrows the hypothesis space; you pick the next probe.
Surface a root cause (disk full, OOM kill, stuck connection pool, expired cert, runaway log, kernel OOM).
Discuss immediate mitigation and durable fix separately.

Scoring axis is the order you ask, not the answer. The interviewer adds constraints ('no metrics', 'customer impact ongoing') to test how you reprioritize.

## Worked solution

### Solution outline

#### How do you debug a production latency regression?

Locate the changed stage and workload before rewriting the model or adding hardware.

1. Compare request mix, prompt/output lengths, concurrency and cache hit rates against the baseline period.
2. Trace queueing, preprocessing, retrieval, model execution and network time separately, including tail percentiles.
3. Check deployment changes, batching, memory pressure and retries; validate a targeted fix under matched load and keep rollback available.

#### Detect a data-pipeline issue before retraining a model.

Operational data checks can explain metric changes more directly than model modifications.

1. Compare feature freshness, null rates, value ranges, schema versions and entity-join coverage with normal baselines.
2. Trace a few affected examples end to end from source event to served feature and prediction.
3. Repair and backfill safely, then reassess model performance on mature labels before deciding whether retraining is needed.

### Understand why the approach works

#### Preserve enough information to aggregate correctly

Logs describe events; counters, gauges and histograms summarize different measurements. A counter increment is not interchangeable with the current number of live objects, and a gauge may decrease for legitimate reasons.

For latency, percentiles are not mergeable by averaging them. Combine raw observations or compatible histogram/sketch state, then compute the requested quantile. An average is mergeable through sum and count, but carries different information from a tail measure.

Keep client queues bounded and state whether an emit call means accepted in RAM, written or durably flushed. Batch/fsync group commit can amortize I/O, but acknowledging before the required flush weakens durability. Backpressure/drop policy must protect the application rather than cause an outage while observing it.

Use event and ingest timestamps for late data, and avoid unbounded labels such as a unique request id in every metric series. Alert on sustained actionable conditions with deduplication and recovery state. Test collector failure, disk-full conditions, malformed records and counter resets. Security also matters: core dumps and diagnostic payloads may contain credentials, so indexing convenience must not imply broad access.

### Apply this question’s exact contract

First assess impact and preserve evidence; check recent changes, dependency health and saturation. For disk-full, inspect filesystem space/inodes, open deleted files and runaway logs before deleting anything; for a server outage, trace DNS→load balancer→process→dependency. Apply a reversible mitigation and verify recovery. Never present indiscriminate deletion or restart loops as the diagnosis.

### Work a small example

If median latency is stable but p99 worsens, a small fraction of long requests or queueing spikes may dominate the regression.

### Edge cases and common mistakes

Comparing two benchmark runs with different lengths or concurrency and attributing the difference solely to code.

### Check your reasoning on related cases

**Detect a data-pipeline issue before retraining a model.** An online feature defaulting to zero after a failed join can hurt predictions even though the model artifact is unchanged.

Which alerts need ownership? Every actionable check should identify the responsible pipeline and a response playbook.
