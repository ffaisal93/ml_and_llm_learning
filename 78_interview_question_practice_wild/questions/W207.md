## Question

Machine Learning Systems Engineer, Siri Runtime Systems and Interaction (Apple). The loop starts with a 30-minute hiring-manager screen. Reported technical topics for the role include serving/runtime systems, a cross-evaluation harness, working with a database, and building services with FastAPI and LangGraph with explicit state management.

How would you prepare for this ML systems screening and discuss designing a low-latency ML runtime/serving service?

## Worked solution

### Prepare for a runtime conversation

The prompt gives reported themes, not an exact interview rubric or proprietary Siri architecture. Prepare a two-minute role introduction and a ten-minute project walkthrough with actual ownership, hardware, concurrency, p50/p95/p99, error budget and one production failure. Do not substitute assumed figures for your experience.

For a concrete **illustrative design**, suppose a voice-facing inference service targets p99 under 200 ms for a small classification model at 2,000 requests/s peak. This excludes speech recognition and generation; those require separate budgets. At a measured 20-ms mean worker service time, Little's law gives about 40 concurrent requests at 2,000/s before queueing headroom. Determine replica count from a real load test, since a concurrency calculation is not a throughput benchmark. Allocate, for example, 15 ms gateway/auth, 15 ms feature lookup, 120 ms queue/inference and 50 ms margin; reject or fall back before exceeding the deadline.

Trace client → authenticated FastAPI-style boundary → deadline/admission gate → feature read → model runtime → typed response. Keep database configuration/model metadata out of the GPU hot path with versioned caches; use prepared queries and bounded connection pools. Model rollout is registry → warm replica → shadow/canary → traffic shift, with old versions retained for rollback. Batch only within the remaining deadline and isolate long requests so they cannot monopolize short ones.

A cross-evaluation harness replays the same versioned examples through candidate and baseline, recording task correctness, per-slice regressions, latency, memory, crashes and determinism settings. Pair observations and bootstrap confidence intervals by session or speaker, not correlated utterance. Include timeouts, malformed input, cold start, overload and dependency failure. Gate release on both quality and tail latency.

If a LangGraph-style workflow is relevant, store an explicit state such as `(session_id, revision, intent, slots, tool_result, deadline)`, with bounded transitions and optimistic concurrency. A simple runtime prediction does not need an agent graph. Concurrent turns must either serialize per session or reject stale revisions; retries must not duplicate actions. Ask about device versus server responsibilities, privacy constraints, supported runtimes and on-call ownership. These questions determine whether a proposed database, model server or state graph belongs in the design at all.
