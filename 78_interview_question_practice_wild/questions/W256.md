## Worked solution

### Test strategy and fixture boundaries

This is a test-plan prompt; the supplied empty `solution()` fragment has no executable input/output contract and does not require inventing a coding problem. Assume a staging fleet, deterministic route/GPS simulator, controllable clock, sandbox payment gateway and inspection access to trip, assignment and ledger events. Test the user journey (request→match→pickup→trip→payment), unit-level state/pricing rules, service integration, end-to-end recovery and mobile offline/reconnect. State invariants: one accepted driver per trip, one active exclusive assignment per driver, legal trip transitions, permissioned live location and one intended net charge.

Five complete cases follow; their fixture values are chosen examples, not production facts.

| Case | Preconditions and inputs | Steps | Expected result and evidence |
|---|---|---|---|
| 1. Location freshness/accuracy | Rider at (40.750,-73.990); driver GPS sequences 10 then 9, with sequence 9 arriving last; allowed service polygon configured | Emit seq10 nearby, then older seq9 far away; request a ride; cross a polygon boundary and reconnect | Matching/map use the newest valid timestamp/sequence with age/accuracy metadata; stale seq9 does not teleport the driver; outside-area requests get the configured refusal. Verify location store, app marker and candidate list agree. |
| 2. Race to accept | One OPEN ride, two eligible drivers D1/D2 with no active trips | Deliver both offers; synchronize both acceptance requests; retry the winning request; loser retries | Exactly one conditional assignment succeeds, the other gets conflict/expired offer; rider sees one driver, no duplicate trip and neither driver gets two exclusive rides. Inspect assignment uniqueness and idempotency logs. |
| 3. Payment timeout and duplicate callback | Completed USD 20 test trip with a sandbox token; gateway authorizes but first response is lost | Complete trip, timeout, retry with same payment key, send the same signed success webhook twice | One USD 20 capture/ledger entry, payment PENDING until reconciled then PAID, no duplicate charge/receipt. Mismatched amount or invalid webhook signature is rejected. Check provider ledger and internal ledger, not only HTTP 200. |
| 4. Cancellation versus pickup | Assigned trip, rider/driver online, explicit cancellation-fee policy | Race rider cancel and driver's start-trip transition, then replay both events; reconnect rider | One legal serialization wins. Either canceled with the policy fee and no active trip, or IN_PROGRESS with the appropriate cancellation response; never canceled and running simultaneously. Driver release, rider display and fee ledger converge. |
| 5. Security and peak degradation | Victim trip and unrelated account; chosen peak load profile, latency/error SLO and test duration | Attempt cross-user location/receipt access; run peak and 2× overload with GPS updates/matches/payments; inject matching-node failure and a slow payment dependency | Unauthorized data/actions denied and audited. Under agreed load, measured p95/p99, assignment delay and error rate meet declared SLO; under overload, bounded queues/backpressure and explicit retries preserve assignment/payment invariants. Verify no location leakage, lost accepted booking or duplicate charge after recovery. |

Add soak tests for leaks/battery/network usage, poor-GPS/tunnel cases, accessible vehicles, price/currency/timezone checks and load distribution across geographies. For matching, compare a small deterministic candidate set to expected eligibility/distance/ETA, including no drivers and two riders competing for one driver. Score outcomes and customer-visible state as well as throughput. Failure reports capture correlation IDs, clock/GPS fixtures, state transitions and reproducible seeds with redacted personal data. No numeric production SLO was provided; agree it before declaring a performance test passed. Automate deterministic invariants and use targeted exploratory mobile testing for usability and permissions.
