## Question

A no-coding HM technical screen for an ML Systems Engineer role that turns into a deep review of one recent project and its codebase. Be ready to defend your implementation, covering:
1. Overall architecture and deployment path.
2. How data is collected, cleaned, evaluated, and compared across alternatives.
3. What database / storage layer the project uses, and why that choice fits the workload.
4. Why an agentic architecture was chosen instead of a simpler pipeline.
5. Backend framework details, including FastAPI-style API boundaries and how state is carried through a LangGraph-style workflow.
6. Retrieval: how PDFs are embedded, how similarity is computed, and how the system selects useful passages/documents.
7. Failures and tradeoffs: what broke, what you changed, what you would redesign with more time.

The round may stay on a single project for the full 30 minutes.

## Worked solution

### Walk the code path, not just the architecture nouns

There is no supplied candidate codebase. The following is an **illustrative PDF research assistant** you could use to rehearse; demonstrate the actual files and trade-offs of your own project in the interview.

A `POST /queries` handler authenticates the tenant, validates query length and creates a run. A service calls retrieval, then generation, then citation validation; a repository owns database access. FastAPI-style handlers should not execute blocking embedding work on the event loop: use an async provider client or a bounded worker. Deployment pins model, embedding, prompt and schema versions and can roll back them together.

Ingestion stores original PDFs in object storage and metadata in PostgreSQL: `Document(id, tenant, version, checksum, acl, status)` and `Chunk(id, document_version, page, offsets, text, embedding)`. Extract text with page provenance, OCR scanned pages, remove repeated headers and quarantine extraction failures. Chunk by sections with bounded token size and overlap; evaluate boundary choices rather than assuming more overlap always helps. Unit-normalize vectors and rank by dot product, which equals cosine similarity. Hybrid lexical/vector retrieval helps exact identifiers; rerank a small candidate set and diversify by document. Enforce ACL filtering before any passage enters the model context.

Collect relevance and answer-support labels from representative analyst questions, including unanswerable and revoked-document cases. Split by document and time, compare lexical-only, embedding-only and hybrid baselines, and report Recall@k, supported-answer rate, abstention quality, latency and cost. Human adjudication and inter-rater agreement matter more than an unexplained model judge score.

Choose a state graph only if conditional behavior is needed: query rewrite after empty retrieval, bounded tool invocation, or human review. A simple retrieve–answer chain is preferable for one predictable path. Persist `Run(run_id, tenant, state_version, node, budget, evidence_ids, error)` and checkpoint after each tool result. Use compare-and-swap on `state_version` so two resumptions cannot both advance the run; use a stable tool idempotency key for side effects. Conversation text alone is not execution state.

Example failure: a PDF is replaced but old chunks remain searchable. An immutable version plus an atomic active-version pointer avoids mixing old and new pages; tombstones and cache invalidation cover deletion. Another failure is a valid citation whose passage does not support the claim; a support check must abstain or ask the user, not silently pass JSON validation. Be ready to locate the extraction, indexing, graph transition and evaluation code, state what you personally implemented, and name a simplification you would choose today.
