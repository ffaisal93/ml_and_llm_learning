## Question

Research-track take-home. You get a self-contained ML problem to solve in ~4 hours in your own environment (local IDE or Colab), immediately followed by a 40-minute live review where you present results and field questions.

Recruiter guidance: "It's mostly coding work, but pen and paper could be useful. The problem involves exploratory research, obtaining results, and showing them numerically. You should be comfortable training and evaluating basic models, with some knowledge of ML and visualization libraries (pandas, numpy, matplotlib...). Treat it like an open-book exam: look up documentation, but don't look up the whole problem, and ensure all work is your own." Open-book on docs; no AI tools. The materials are sent at the start of the window, so you cannot prep on the actual problem.

How should you approach this to maximize your score?

## Worked solution

### Prepare before the assessment, then honor its rules

The exercise explicitly permits documentation and forbids AI tools. This is advance process guidance; during the actual four-hour assessment turn off AI/editor assistants, do your own analysis/code, and use documentation only as allowed. Do not look up a full solution or submit AI-generated code as independent work. No assessment materials are supplied here, so there are no problem-specific results to report.

### Four hours with a guaranteed baseline

| Time | Concrete output |
|---|---|
| 0–20 min | Read every requirement, define target/metric/grain/information cutoff and deliverable checklist; inspect files/types |
| 20–50 | Missingness, duplicates, units, label/prevalence/range audit; justified split and dummy/domain benchmark |
| 50–100 | Minimal runnable preprocessing/training/evaluation pipeline, recorded seed and baseline result table |
| 100–155 | One or two hypothesis-led improvements, each with fixed split and comparable compute/configuration |
| 155–190 | Residual/error slices, leakage checks, meaningful uncertainty and one or two explanatory plots |
| 190–220 | Fresh-kernel end-to-end rerun; dependency/version/command instructions; verify saved outputs |
| 220–240 | Short report/presentation, limitations and final completeness check |

Adapt to the supplied problem rather than forcing every task into classification. Numerical results must come from executed code, include baseline and sample size, and use metrics tied to the stated objective. Fit transforms on training only; choose group/time boundaries when rows are dependent. Keep final test untouched while choosing improvements. If the baseline fails or a promised improvement is inconclusive, a precise diagnosis with a reproducible negative result beats an unvalidated rewrite in the final hour.

### Forty-minute review

Aim for a 10–12 minute initial walkthrough: problem/decision and assumptions (2), data/split/leakage (2), baseline and controlled results (3), error cases/plots (2), limitations/next experiment (2). Leave the rest for the panel. Keep code runnable and be ready to derive the loss, trace a transformation and show why the split matches deployment. Show a compact experiment table with configuration, validation/test boundaries, compute and result; do not cherry-pick one run or invent a confidence interval.

When challenged, separate observation from interpretation: “the improvement occurs only in this slice; the interval is wide, so I would collect more data before claiming a general gain.” Prioritize explaining a simple model's assumptions and a failed experiment over listing methods you did not test. Final deliverables are executable work, exact run instructions, requested output files and an honest concise report. A clean rerun is the submission criterion, not merely a notebook containing output from an older code version.
