## Question

Estimate how fast matrix multiplications run on one GPU using the roofline model, then scale the estimate to a 72-layer network and compare two ways of splitting it over two GPUs. This is a pen-and-paper performance-modelling question: show the formula, the arithmetic and the conclusion for each part.

Hardware (one GPU, all numbers given)
Peak compute: 312 TFLOP/s (BF16)
HBM bandwidth: 1.5 TB/s

```text
VRAM: 40 GB (take 1 GB = 10^9 bytes)
```

Link between two GPUs: 300 GB/s per direction
All tensors are BF16 (2 bytes per element). A matmul C = A @ B with A: m x k, B: k x n, C: m x n reads A and B once and writes C once.
1. Cost of a single matmul

For each shape (m, k, n) below, derive:
1. FLOPs: 2 * m * k * n
2. Bytes moved: 2 * (m*k + k*n + m*n)
3. Arithmetic intensity: FLOPs / bytes (FLOP/byte), and the ridge point peak FLOP/s / bandwidth
4. Bound regime: memory-bound below the ridge point, compute-bound above it
5. Predicted time: max(FLOPs / peak FLOP/s, bytes / bandwidth)

Shapes: (1, 8192, 8192), (64, 8192, 8192), (512, 8192, 8192), (4096, 4096, 4096).

2. A 72-layer network on one GPU

The network has 72 layers that alternate between two matmul patterns, 36 layers of each. Every layer reads its own weight matrix, and layers are costed independently.

Pattern A: (m, k, n) = (2048, 8192, 8192)
Pattern B: (m, k, n) = (2048, 8192, 32768)

Compute: (a) the total compute time sum FLOPs / peak, (b) the total data-transfer time sum bytes / bandwidth, (c) the predicted end-to-end time as the sum of the per-layer predicted times from Part 1's rule, and (d) whether all weights plus the largest input and output activation of any one layer fit in 40 GB.

3. Splitting over two GPUs

Compare, for the same network and a single batch of m = 2048 rows:

Pipeline parallelism: layers 1-36 on GPU 0 and layers 37-72 on GPU 1. Only the m x 8192 activation crosses the link once.
Tensor parallelism: every weight matrix is split along n into two halves, one per GPU, so each GPU runs (m, k, n/2). After every layer each GPU sends its half of the output (m * n * 2 / 2 bytes) to the other GPU over the link, with no overlap with compute.

Report end-to-end latency, per-GPU weight memory, and the trade-off (latency against communication volume and memory). Ignore pipeline bubbles: one batch, no micro-batching.

## Worked solution

### Solution outline

#### Apply the roofline model to a matrix multiplication.

The roofline compares available compute throughput with the rate at which needed data can reach the processor.

1. For A:(M,K) and B:(K,N), estimate about 2MKN floating-point operations.
2. Estimate bytes moved under an explicit reuse assumption, then compute arithmetic intensity=FLOPs/bytes.
3. The idealized throughput ceiling is min(peak_FLOPs,bandwidth*intensity). Use profiling to include tiling, launch overhead and cache behavior.

#### Train with mixed precision without losing small gradients.

Lower-precision matrix operations can improve throughput, while sensitive reductions and optimizer state may need higher precision.

1. Choose supported autocast dtypes and keep numerically sensitive loss calculations in an appropriate accumulator precision.
2. For FP16, loss scaling can protect small gradients; unscale before clipping, detect overflow and skip invalid updates. BF16 usually needs less range protection but still has limited mantissa precision.
3. Compare convergence and output quality against a higher-precision baseline; measure actual speed and memory rather than assuming benefits.

### Understand why the approach works

#### Follow tensor ownership and the resource bottleneck

For every major tensor, state who owns it before and after each collective. Data parallelism divides examples; tensor parallelism divides operations/weights; pipeline parallelism divides layers. Their communication and memory effects differ, so a diagram saying “use more GPUs” is incomplete.

For $C=AB$, $A\in\mathbb R^{m\times k}$ and $B\in\mathbb R^{k\times n}$, a row partition gives

$$
C_r=A_rB,\qquad C=\operatorname{ConcatRows}(C_0,\ldots,C_{p-1}).
$$

Concatenating output shards is different from summing partial products. Backward communication depends on which variables were replicated and where multiple contributions to the same derivative must be added.

Estimate the bottleneck with a roofline bound:

$$
\text{attainable FLOP/s}\leq
\min\!\left(F_{\rm peak},\;\text{bandwidth}\times\frac{\text{FLOPs}}{\text{bytes moved}}\right).
$$

Then add synchronization, imbalance, launch and checkpoint overhead rather than treating the ideal bound as achieved speed.

For a platform/scheduler, distinguish desired state, observed state and durable job completion. Launching a container or receiving a provider response does not prove the computation succeeded. Checkpoint application state, fence stale owners, publish only complete artifacts and monitor both utilization and tenant wait time. A design that maximizes utilization by starving a large job violates a different important service objective.

### Work a small example

If bandwidth is 1 TB/s and intensity is 10 FLOPs/byte, the bandwidth ceiling is 10 TFLOPs/s, even if peak compute is 100 TFLOPs/s.

### Edge cases and common mistakes

Counting every scalar reference as an uncached memory transfer, or treating a theoretical bound as achieved performance.

### Check your reasoning on related cases

**Train with mixed precision without losing small gradients.** FP16 has a narrower exponent range than BF16, so a finite FP32 activation can overflow FP16 while remaining representable in BF16.

Why can a reduction overflow when individual elements look reasonable? The accumulated sum may exceed the representable range.
