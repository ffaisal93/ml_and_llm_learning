## Question

A small internal chat service answers commands such as !help with a mock reply. It is written as one function with a global message list and a chain of if/elif prefix checks. Refactor it into an object-oriented design in which every command is its own bot, every channel keeps its own history and its own list of bots, and one server routes messages to channels. The old entry point llm_response must keep returning exactly the same strings.

Legacy code

```python
messages = []   # All chat history in one place
```

```python
def llm_response(user_id: str, text: str) -> str:
    ...
```

"""Legacy function with mock LLM responses."""
messages.append({"user": user_id, "text": text})

if text.startswith("!help"):

```python
return "[help] Available commands: !help, !schedule, !weather"
```

elif text.startswith("!schedule"):

```python
return f"[schedule] Okay {user_id}, your meeting is scheduled."
```

elif text.startswith("!weather"):

```python
return "[weather] It is sunny today."
```

elif text.startswith("!echo"):

```python
return text[5:]
```

else:

```python
return "[error] Unknown command."
```

### What to implement

1. class Bot(ABC) with two abstract methods: can_handle(text: str) -&gt; bool (is this bot responsible for the message) and handle(user_id: str, text: str) -&gt; str (the reply).
2. Four concrete bots, each with the prefix test and the reply of the matching legacy branch: HelpBot (!help), ScheduleBot (!schedule), WeatherBot (!weather) and EchoBot (!echo).
3. class ChatChannel with the constructor ChatChannel(name: str, bots: list[Bot]), the attributes name, bots and messages (a list of {"user": user_id, "text": text} dicts, oldest first), and the methods record_message(user_id, text) -&gt; None and dispatch(user_id, text) -&gt; str.
4. class ChatServer with the constructor ChatServer(), the attribute channels (a dict from channel name to ChatChannel), register_channel(name: str, bots: list[Bot]) -&gt; None and send_message(channel: str, user_id: str, text: str) -&gt; str.
5. llm_response(user_id: str, text: str) -&gt; str, a thin wrapper that sends the message to the channel "default" of one module-level server. That channel has all four bots, in the order help, schedule, weather, echo.

### Rules

1. send_message finds the channel, records the message in that channel's own messages list, then dispatches it.
2. dispatch asks the bots in list order and returns the reply of the first bot whose can_handle is true. If no bot accepts the text, it returns "[error] Unknown command.".
3. A channel only knows its own bots: a command whose bot is not in the channel's list gets the unknown-command reply, even if another channel has that bot.
4. Histories are isolated: a message sent to one channel never appears in another channel's messages.
5. register_channel with an existing name replaces that channel, including its history.
6. send_message to a channel that was never registered raises ValueError.
7. The old module-level messages list does not need to exist any more. Only the return values of llm_response have to stay identical to the legacy ones, for every (user_id, text).
8. A bot matches on the prefix only, as in the legacy code: "!echoes" is an echo message and "!help me" is a help message.

### Constraints

Plain Python 3, standard library only.
Bot objects hold no per-message state; the same bot instance may be shared by several channels.
At most 100 channels, 10 bots per channel and 10^4 messages per channel.

## Worked solution

### Solution outline

1. First preserve observable behavior with characterization tests for normal inputs, ordering, errors and state changes. Extract pure parsing/routing logic from mutable state and external I/O.
2. Represent each bot or handler behind a small interface; use a registry for dispatch and explicit per-channel/conversation state. Make ownership, reset and history retention visible rather than using hidden globals.
3. Inject clocks, model clients and storage so behavior can be tested without a live service. Add concurrency control only around the state that needs it and preserve the existing message/response contract.
4. Ship small verified changes. A longer-term design can add typed requests, bounded context, logging and persistence, but should not silently alter semantics during the refactor.

### Understand why the approach works

#### Write the invariant and identify its atomic boundary

A thread-safe container is not enough if an operation spans several individually safe calls. In “check then insert,” the check and insertion must be one logical atomic action; otherwise two workers can both observe absence and both perform the effect.

Use one lock to protect the smallest relevant shared state. For condition variables, wait in a loop that rechecks the predicate after waking, because wakeup alone does not prove the desired state holds. Do not execute arbitrary slow callbacks under a central registry lock: they may block unrelated work or reenter the same system.

Separate pure transformations, state transitions and external I/O. This makes a small deterministic test possible and keeps a refactor from silently changing behavior. For single-flight loading, represent loading/ready/failed state and notify every waiter once; one canceled waiter need not cancel work still needed by others.

Test interleavings, failure after claiming state, shutdown and stale completion callbacks. State the scope honestly: a Python mutex protects cooperating threads in one process, not another process or machine. A concurrent algorithm's linearization point and ownership rules explain correctness more clearly than a list of synchronization primitives.

### Work a small example

A new prefix handler should be registered without modifying every existing bot. Two channels should not share a conversation history unless that sharing is intentional.
