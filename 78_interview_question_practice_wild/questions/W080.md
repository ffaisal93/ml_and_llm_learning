## Question

Task: Debug an NLP Classifier Training Pipeline (BERT + Linear)

You are given a training codebase skeleton for text classification (you may choose a PyTorch or TensorFlow implementation). The high-level components include:

Dataset
DataLoader
Customized Model   (Transformer/BERT + a few Linear layers)
Trainer            (similar to HuggingFace Transformers)
Evaluation
AUC metric

The code contains multiple bugs that prevent training/evaluation from running correctly or produce incorrect metrics. Your task is to debug and fix the pipeline within a limited time.

Issues you are expected to identify and fix (cover at least these areas)

1. Dataset / label parsing

The dataset parses label as a string.
Training expects labels in a numeric form usable by the loss function (e.g., int / tensor).

2. One-hot encoding bug

A one-hot encoding snippet is provided and can replace the current label logic.
However, the provided one-hot implementation has a dimension/shape mismatch that must be fixed.

3. Incorrect use of model output (last_hidden_state)

The model uses a BERT/Transformer output for classification.
The current usage of last_hidden_state is incorrect, leading to wrong shapes or an invalid classifier head input. Fix it (e.g., choose an appropriate pooling strategy or token representation).

4. Loss bug: applying Softmax before CrossEntropy

The implementation applies softmax before cross entropy loss.
Fix it to follow the correct usage for the chosen framework.

5. AUC metric input/parameter bug

The AUC computation has incorrect inputs and/or key parameters, causing errors or wrong results.
Fix the AUC call so it matches the binary or multiclass setting.

6. Training detail checks

Verify dropout behavior (train vs eval mode).
Verify no incorrect requires_grad settings that freeze parameters unintentionally.
Deliverables
1. A corrected pipeline that trains without crashing and reports a valid AUC.
2. For each bug: the symptom, the root cause, and the fix.
3. A sanity check showing the fixed pipeline learns (for example, overfitting one small batch).

## Worked solution

### Solution outline

#### A classifier's loss does not decrease. What do you check first?

Use a small controlled problem to distinguish a broken training loop from a difficult learning task.

1. Check target encoding, logits/loss compatibility, preprocessing, train mode, optimizer parameters and zero_grad/backward/step order.
2. Inspect finite activations and gradients, then confirm that parameters change. Try overfitting a tiny batch.
3. Once basic learning works, sweep learning rate and compare a simple baseline; change one factor at a time.

#### Fit a baseline on messy tabular data without leakage.

Build a trustworthy split and simple baseline before sophisticated feature engineering.

1. Define the target, prediction time and unit of independence, then split by time or group if required.
2. Fit imputation, scaling and category encodings on training folds only. Start with a dummy baseline and a regularized linear or small tree model.
3. Evaluate slices, missingness patterns and calibration; document features unavailable at decision time and remove them.

### Understand why the approach works

#### Derive a local rule, then apply the chain rule

Treat a layer as a function with a declared input and output shape. Write the scalar loss and its reduction first: a sum, mean over rows and mean over all elements produce different gradient scales. For an affine layer $Y=XW+b$ with upstream gradient $G=\partial L/\partial Y$,

$$
\frac{\partial L}{\partial X}=GW^\top,\qquad
\frac{\partial L}{\partial W}=X^\top G,\qquad
\frac{\partial L}{\partial b}=\sum_i G_{i,:}.
$$

The bias sum is over all leading positions where the same bias was reused. Do not average again if $G$ already contains the mean-loss factor. For example, with one row $x=[2,3]$ and scalar upstream derivative $4$, the weight derivative is $[8,12]$.

Cache the forward values needed by the derivative; compute all gradients before updating parameters. Updating $W$ midway would make the earlier-layer derivative use a different function from the one evaluated forward.

Check a scalar objective using central differences:

$$
\frac{\partial L}{\partial\theta_j}\approx
\frac{L(\theta+h e_j)-L(\theta-h e_j)}{2h}.
$$

Use float64 and several sensible $h$ values. An arbitrarily tiny $h$ loses the difference to rounding, while a large one measures curvature rather than a local derivative. Avoid ReLU's kink at zero during this check, and test inputs, weights and biases separately.

### Apply this question’s exact contract

Inspect the tokenizer/model pairing, attention masks, hidden-state selection and classifier-head dimension. Use raw classification logits with cross-entropy and integer class labels; ensure encoder/head parameters are in the optimizer if intended. Verify device placement, train/eval state and gradient flow. Pooling a padding token or feeding probabilities into a logits loss are independent bugs that a tiny-batch overfit test can reveal.

### Work a small example

Passing softmax probabilities into a loss expecting logits applies a second normalization and can produce weak or misleading gradients.

### Edge cases and common mistakes

Blaming insufficient model size before proving that the optimizer is updating the intended parameters.
