## Question

Write a single SQL query that merges CPU and memory utilization into one unified view for a cloud resource dashboard.

Result columns
resource_type - the literal CPU or Memory indicating which metric the row describes.
application_id - the application with recorded metrics.
average_usage_percentage - the average usage as a percentage, rounded to two decimal places including trailing zeros (e.g. 35.00).

### Rules

Include only metrics recorded in February 2024.
Include only applications whose average usage for that specific resource type is greater than 50%.
Sort ascending by application_id, then ascending by resource_type.
Schema (both tables share the same shape)
cpu_metrics(application_id INT, dt VARCHAR(19), usage_percentage DECIMAL(5,2))
memory_metrics(application_id INT, dt VARCHAR(19), usage_percentage DECIMAL(5,2))

## Worked solution

### Solution outline

1. Filter timestamps using the half-open range 2024-02-01 through 2024-03-01 and aggregate CPU and memory independently by application.
2. Combine the two same-shaped aggregates with UNION ALL, filter on the numeric average greater than 50, then sort by application_id and resource_type.
3. This SQLite example uses printf for exactly two displayed decimal places; formatting returns text. Other SQL dialects use a different formatting function or a suitable fixed-scale decimal output.

### Understand why the approach works

#### Establish row grain before writing a join

Say what one output row represents: an event, user, vendor, parent type or time interval. Then inspect the cardinality of every join. Joining two one-to-many relations can multiply rows and inflate both totals and averages; `DISTINCT` is not a general repair because legitimate equal-valued records can also exist.

For mergeable averages store a sum and count:

$$
\bar x_{\rm pooled}=\frac{\sum_g \operatorname{sum}_g}{\sum_g \operatorname{count}_g}.
$$

Do not average subgroup means unless the intended weighting gives each group equal weight. Likewise, daily distinct users cannot be added to obtain monthly distinct users.

Use half-open time windows, such as `timestamp >= start AND timestamp < end`, and name the timezone. For point-in-time training, feature **availability time** must not exceed prediction time; event occurrence and availability can differ.

Choose tie semantics deliberately: `ROW_NUMBER` produces a fixed number of rows under a deterministic secondary order, while `DENSE_RANK` preserves equal primary scores. A predicate on a nullable right-table column in `WHERE` can undo the unmatched-row preservation of a `LEFT JOIN`. Test duplicate events, absent dimension rows, nulls, tied maxima and an empty denominator. These cases explain correctness more convincingly than running only one ordinary example.

### Complete reference query

```sql
WITH usage AS (
 SELECT 'CPU' AS resource_type,application_id,AVG(usage_percentage) AS avg_usage
 FROM cpu_metrics WHERE dt>='2024-02-01' AND dt<'2024-03-01'
 GROUP BY application_id
 UNION ALL
 SELECT 'Memory',application_id,AVG(usage_percentage)
 FROM memory_metrics WHERE dt>='2024-02-01' AND dt<'2024-03-01'
 GROUP BY application_id
)
SELECT resource_type,application_id,printf('%.2f',avg_usage) AS average_usage_percentage
FROM usage WHERE avg_usage>50
ORDER BY application_id,resource_type;
```

### Work a small example

An average of exactly 50 is excluded; 50.005 is filtered numerically before display rounding. February 29, 2024 is included.

### Edge cases and common mistakes

Averaging CPU and memory together or filtering by a rounded string rather than the numeric aggregate.
