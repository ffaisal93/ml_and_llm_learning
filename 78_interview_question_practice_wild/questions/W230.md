## Question

An MLE domain round: a short ML coding warm-up (~20 min, e.g. a logistic-regression gradient step or k-means iteration from spec) then a medium SQL problem (~40 min) that almost always needs a window function (ROW_NUMBER, LAG, or SUM() OVER (PARTITION BY ...)) plus a sub-query/CTE. Typical shape: 'for each user, the X-th most recent event meeting condition Y, joined to its preceding event for a delta'. The window-function half is the most common failure point (interviewers probe whether you can go beyond GROUP BY). Verbal template that scores: a CTE partitioning by user ordered by time, ROW_NUMBER to filter the N-th event, LAG for the preceding-event delta. Show the query plan verbally (partition columns, order columns, what the inner CTE produces).

## Worked solution

### State an explicit demonstration when the actual tasks are absent

The exact ML spec, SQL schema, event condition and meaning of “preceding” are not supplied. The following is a **demonstration**, not a purported solution to unseen judge inputs. Ask whether the predecessor is the previous event overall or the previous qualifying event; their SQL differs.

For the warm-up, assume mean binary cross-entropy, `X [n,d]`, binary `y [n]`, weights `[d]` and scalar intercept. Since $\partial\ell/\partial z=p-y$, one gradient step is $w'=w-\eta X^T(p-y)/n$, $b'=b-\eta\operatorname{mean}(p-y)$. No regularization was assumed. The stable sigmoid below avoids overflow at large logits.

```python
import numpy as np


def logistic_step(X, y, w, b, learning_rate):
    """X [n,d], y [n], w [d], scalar b; mean BCE gradient step."""
    z = X @ w + b
    # Stable sigmoid without evaluating an overflowing unused branch.
    p = np.empty_like(z, dtype=float)
    positive = z >= 0
    p[positive] = 1 / (1 + np.exp(-z[positive]))
    ez = np.exp(z[~positive])
    p[~positive] = ez / (1 + ez)
    error = p - y
    return w - learning_rate * X.T @ error / len(y), b - learning_rate * error.mean()
```

For SQL, choose `events(user_id,event_id,event_time,kind,value)` and find the N-th most recent purchase plus its preceding event **of any kind**:

```sql
-- N=:n, qualifying condition kind='purchase'; preceding means previous event OF ANY kind.
WITH all_events AS (
  SELECT *,LAG(event_time) OVER(PARTITION BY user_id ORDER BY event_time,event_id) AS previous_time,
           LAG(value) OVER(PARTITION BY user_id ORDER BY event_time,event_id) AS previous_value
  FROM events
), qualifying AS (
  SELECT *,ROW_NUMBER() OVER(PARTITION BY user_id ORDER BY event_time DESC,event_id DESC) AS rn
  FROM all_events WHERE kind='purchase'
)
SELECT user_id,event_id,event_time,previous_time,
       event_time-previous_time AS elapsed,value-previous_value AS value_delta
FROM qualifying WHERE rn=:n;

```

The inner CTE emits every event with its chronological predecessor. Only then filter purchases and rank them newest-first per user; `event_id` resolves tied timestamps. If the predecessor means previous purchase, move the purchase filter before LAG instead. Users with fewer than N purchases produce no row; an event without a predecessor has NULL deltas. For events `(1,view,10)`, `(2,purchase,20)`, `(3,view,25)`, `(4,purchase,40)` in time order, the most recent purchase has value delta 15 versus the previous event, or 20 versus the previous purchase. This example exposes the filter-order trap.

The plan partitions and sorts by user/time, computes LAG, filters qualifying rows, then computes descending ROW_NUMBER and filters rn. An index `(user_id,event_time,event_id)` can help access/order, but two order directions and materialization choices still need an EXPLAIN on the actual database. Tests compare the gradient to finite differences and execute a portable SQLite timestamp/value variant of the window query. The original unspecified task cannot honestly be marked as passed.
