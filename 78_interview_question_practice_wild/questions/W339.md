## Question

A Data Engineer technical screen built around SQL over an employee / project / budget schema. Two prompts:
1. Return the names of employees who have completed a project that lasted more than 90 days.
2. Return the average budget per employee per project. Each project has multiple employees and its budget is divided across them, so compute each employee's share and aggregate.
Notes
Exact schema not published. Expect an employees table, a projects table (with start/end dates and a budget column), and an assignment/membership table linking employees to projects.
Duration filtering (DATEDIFF / date subtraction &gt; 90) and per-project allocation (budget / COUNT(employees)) are the core skills; no window functions strictly required.
The same round also included a Python data-manipulation task; the second technical round added a data-modeling / pipeline-design exercise.

## Worked solution

### Solution outline

Prevent assignment joins from duplicating project-level amounts before computing employee summaries.

1. Define duration units, inclusive/exclusive endpoints and open-project treatment.
2. Aggregate assignment allocations under a documented rule: equal share, hours or explicit percentages.
3. Then summarize by employee, preserving project ids to audit double counts and overlapping periods.

### Understand why the approach works

#### Establish row grain before writing a join

Say what one output row represents: an event, user, vendor, parent type or time interval. Then inspect the cardinality of every join. Joining two one-to-many relations can multiply rows and inflate both totals and averages; `DISTINCT` is not a general repair because legitimate equal-valued records can also exist.

For mergeable averages store a sum and count:

$$
\bar x_{\rm pooled}=\frac{\sum_g \operatorname{sum}_g}{\sum_g \operatorname{count}_g}.
$$

Do not average subgroup means unless the intended weighting gives each group equal weight. Likewise, daily distinct users cannot be added to obtain monthly distinct users.

Use half-open time windows, such as `timestamp >= start AND timestamp < end`, and name the timezone. For point-in-time training, feature **availability time** must not exceed prediction time; event occurrence and availability can differ.

Choose tie semantics deliberately: `ROW_NUMBER` produces a fixed number of rows under a deterministic secondary order, while `DENSE_RANK` preserves equal primary scores. A predicate on a nullable right-table column in `WHERE` can undo the unmatched-row preservation of a `LEFT JOIN`. Test duplicate events, absent dimension rows, nulls, tied maxima and an empty denominator. These cases explain correctness more convincingly than running only one ordinary example.

### Work a small example

A 1000-unit project assigned equally to four employees contributes 250 units each, not 1000 each, if allocation rather than participation totals is requested.

### Edge cases and common mistakes

Adding full project budgets once per employee without stating that duplication is intentional.
