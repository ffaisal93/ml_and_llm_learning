## Question

After solving a routine scheduling problem in HackerRank, candidates are asked to refactor the function into a production-quality REST service on the same platform, then defend the design under aggressive questioning. The round has been reported as deliberately adversarial.

### Requirements

Phase 1: solve a standard LeetCode-style problem (meeting-scheduler family in the reported round) and pass tests.
Phase 2: refactor the function into a RESTful service. The interviewer decides the API surface — clarification on input/output shape is expected, but the interviewer may dismiss the question and demand you proceed.
Phase 3: incrementally harden the service toward production quality. The interviewer pushes on input validation, observability (metrics, structured logging), error handling and retry, and graceful failure boundaries.
Constraint reported: the HackerRank environment may not have the framework library you pick (FastAPI, Spring Boot). Treat code as production pseudocode and call out which dependencies you would import.
Notes
Graded on production instinct, not whether the code compiles. A strong answer brings a checklist into the room: REST verbs and routing, request schema validation, error model (4xx vs 5xx boundaries), idempotency, structured logging with correlation IDs, metrics (RED — rate/errors/duration), retries with backoff, dependency injection for testability.
Layer the code explicitly: handler -&gt; service -&gt; repository, with the service layer holding the Phase 1 business logic.
The interviewer was unsympathetic ("I don't care" on API clarification). Restate each design choice with its trade-off rather than seeking permission.
The round closed by demanding a frontend smoke-test against the backend; call out that HackerRank cannot do live front/back integration and offer to describe the smoke-test plan instead.

## Worked solution

### Declare the missing scheduler contract and build a reviewable demo

The original Phase-1 problem and API schema are absent. Assume a **demonstration**: given two lists of half-open integer availability intervals and positive integer duration, return the earliest overlap of that duration or None. This is a search endpoint, not an actual reservation; no original HackerRank pass is claimed. Sort both lists and advance the one ending first, because it cannot overlap a later partner interval better. Time is O(A log A+B log B), or O(A+B) if sorted, with O(A+B) copied storage.

```python

def earliest_meeting(slots_a, slots_b, duration):
    """DEMO contract: half-open integer intervals, positive integer duration."""
    if not isinstance(duration, int) or isinstance(duration, bool) or duration <= 0:
        raise ValueError('duration must be a positive integer')
    def validate(slots):
        if len(slots) > 10000: raise ValueError('too many slots')
        for slot in slots:
            if len(slot) != 2 or any(not isinstance(x,int) or isinstance(x,bool) for x in slot) or slot[0] >= slot[1]:
                raise ValueError('invalid interval')
        return sorted(slots)
    a, b = validate(slots_a), validate(slots_b)
    i = j = 0
    while i < len(a) and j < len(b):
        start, end = max(a[i][0],b[j][0]), min(a[i][1],b[j][1])
        if end - start >= duration: return [start,start+duration]
        if a[i][1] <= b[j][1]: i += 1
        else: j += 1
    return None

class SchedulingRepository:
    """Injected boundary; booking persistence would replace this read-only demo."""
    def availability(self, request):
        return request['slots_a'], request['slots_b']

class SchedulingService:
    def __init__(self, repository): self.repository = repository
    def find(self, request):
        a,b = self.repository.availability(request)
        return earliest_meeting(a,b,request['duration'])

class SchedulingHandler:
    def __init__(self, service): self.service = service
    def post(self, body):
        # Framework adapter would parse JSON, enforce body size/auth and add tracing.
        try:
            if not isinstance(body, dict) or set(body) != {'slots_a','slots_b','duration'}:
                raise ValueError('expected slots_a, slots_b, duration')
            return 200, {'meeting': self.service.find(body)}
        except (ValueError, TypeError, KeyError) as exc:
            return 422, {'error': 'invalid_request', 'message': str(exc)}
```

Expose `POST /v1/meeting-options` with JSON `{slots_a:[[10,50]],slots_b:[[20,40]],duration:15}` returning 200 `{meeting:[20,35]}`; no overlap is 200 `{meeting:null}`, malformed input is 422. The code is a runnable framework-independent handler→service→repository boundary. A FastAPI adapter would require that dependency and request/response models; a standard-library test exercises the same handler when the platform lacks it. For real calendars, use server-side calendar IDs/authorization and a repository, not client-supplied availability presented as trusted data.

Production hardening includes body/list limits, finite validated timestamps, explicit timezone policy, authentication and no PII in logs. Propagate a correlation ID and deadline; record request rate, error code, duration and dependency latency. Convert expected validation/not-found/conflict errors to 4xx and unexpected exceptions to a sanitized 500 with an internal trace. The read-only search is safe to retry, but dependency retries need bounded backoff+jitter and a shared deadline. An actual `POST /bookings` is a different operation: recheck availability and atomically reserve with an idempotency key; returning an option does not prevent a concurrent booking race.

Inject repositories, clocks and clients for tests. A frontend smoke test should submit the fixture, assert `[20,35]`, render no-overlap and validation states, and verify one request's correlation ID reaches backend logs. If the assessment cannot run a frontend/server, label this as the smoke-test plan and run handler tests locally; do not claim an integration was executed. Explain choices calmly when clarification is dismissed: “I will proceed with integer half-open intervals and a read-only search; booking would require transactional persistence.”
