## Question

Given a user login log table user_login_log(user_id, login_date), write SQL (and describe the output schema) to compute:
1. Consecutive login days within any rolling 15-day window — for each user, the maximum consecutive-day streak that occurs within any rolling 15-day window.
2. Maximum consecutive login days — for each user, the longest consecutive-day streak over the entire timeline.
3. Users with at least 2 active days — count each user's distinct login days (multiple logins on the same day count once) and return users with active_days &gt;= 2.
Requirements / constraints
Deduplicate to distinct days per user before computing streaks.
A streak is consecutive if the date difference between adjacent login days is exactly 1.
Clearly define output columns (e.g. user_id, max_streak, max_streak_in_15_days, active_days).
Assume the table can have tens of millions of rows; the SQL should be executable and scalable.
Example
User A logs in on 2024-01-01, 01-02, 01-04, 01-05, 01-06
=&gt; max_streak = 3 (01-04..01-06), max_streak_in_15_days = 3, active_days = 5

## Worked solution

### Solution outline

Convert repeated events into distinct user-days before detecting consecutive dates.

1. Choose timezone and deduplicate (user_id,login_date).
2. Order each user's dates and assign ROW_NUMBER; consecutive runs share a key like login_date minus row_number days.
3. Group by user and run key, then compute length and boundaries with deterministic handling of ties.

### Understand why the approach works

#### Establish row grain before writing a join

Say what one output row represents: an event, user, vendor, parent type or time interval. Then inspect the cardinality of every join. Joining two one-to-many relations can multiply rows and inflate both totals and averages; `DISTINCT` is not a general repair because legitimate equal-valued records can also exist.

For mergeable averages store a sum and count:

$$
\bar x_{\rm pooled}=\frac{\sum_g \operatorname{sum}_g}{\sum_g \operatorname{count}_g}.
$$

Do not average subgroup means unless the intended weighting gives each group equal weight. Likewise, daily distinct users cannot be added to obtain monthly distinct users.

Use half-open time windows, such as `timestamp >= start AND timestamp < end`, and name the timezone. For point-in-time training, feature **availability time** must not exceed prediction time; event occurrence and availability can differ.

Choose tie semantics deliberately: `ROW_NUMBER` produces a fixed number of rows under a deterministic secondary order, while `DENSE_RANK` preserves equal primary scores. A predicate on a nullable right-table column in `WHERE` can undo the unmatched-row preservation of a `LEFT JOIN`. Test duplicate events, absent dimension rows, nulls, tied maxima and an empty denominator. These cases explain correctness more convincingly than running only one ordinary example.

### Work a small example

Days 1,2,4,5,6 contain streaks of lengths 2 and 3; multiple logins on day 5 do not lengthen either streak.

### Edge cases and common mistakes

Applying row numbers to raw events, so duplicates shift the sequence.
