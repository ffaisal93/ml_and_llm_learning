## Question

Data Engineer first-round screen combining a noisy CSV cleaning pipeline with three SQL tasks: monthly-reset cumulative sales, recursive employee hierarchy, and conditional order aggregation.

### Requirements

Cleaning pipeline input: customer transaction CSV with columns date, amount, customer_id, payment_method, and notes.
Data issues:
Dates appear in mixed formats: YYYY-MM-DD, MM/DD/YYYY, and strings such as Jan 5, 2024.
Amounts include currency symbols and commas, such as USD 1,234.56.
customer_id can lose leading zeros after Excel processing.
payment_method contains typos and inconsistent casing.
After cleaning, describe what validations should run.
SQL task 1: sales table with date, store_id, amount; compute cumulative sales by store, resetting to 0 whenever a new month starts. Output store_id, date, total_amount.
SQL task 2: organization table with employee_id, manager_id, name; find all direct and indirect reports under manager_id = 1, returning employee_id, manager_id, name, level, and hierarchy_path.
SQL task 3: orders table with order_id, status, amount, date; in one pass, compute completed-only revenue, pending count, and cancelled count by date.

## Worked solution

### Solution outline

#### Fit a baseline on messy tabular data without leakage.

Build a trustworthy split and simple baseline before sophisticated feature engineering.

1. Define the target, prediction time and unit of independence, then split by time or group if required.
2. Fit imputation, scaling and category encodings on training folds only. Start with a dummy baseline and a regularized linear or small tree model.
3. Evaluate slices, missingness patterns and calibration; document features unavailable at decision time and remove them.

#### Define label windows for click-through-rate analysis.

The numerator and denominator must refer to the same eligible exposures and mature observation windows.

1. Define an impression, a valid click, attribution rules, deduplication and the outcome window.
2. Join outcomes to exposures without multiplying rows, then aggregate clicks and impressions by the intended category.
3. Report counts and uncertainty; distinguish unobserved outcomes from confirmed non-clicks when logs are incomplete.

#### Find each user's consecutive login-day streaks.

Convert repeated events into distinct user-days before detecting consecutive dates.

1. Choose timezone and deduplicate (user_id,login_date).
2. Order each user's dates and assign ROW_NUMBER; consecutive runs share a key like login_date minus row_number days.
3. Group by user and run key, then compute length and boundaries with deterministic handling of ties.

### Understand why the approach works

#### Establish row grain before writing a join

Say what one output row represents: an event, user, vendor, parent type or time interval. Then inspect the cardinality of every join. Joining two one-to-many relations can multiply rows and inflate both totals and averages; `DISTINCT` is not a general repair because legitimate equal-valued records can also exist.

For mergeable averages store a sum and count:

$$
\bar x_{\rm pooled}=\frac{\sum_g \operatorname{sum}_g}{\sum_g \operatorname{count}_g}.
$$

Do not average subgroup means unless the intended weighting gives each group equal weight. Likewise, daily distinct users cannot be added to obtain monthly distinct users.

Use half-open time windows, such as `timestamp >= start AND timestamp < end`, and name the timezone. For point-in-time training, feature **availability time** must not exceed prediction time; event occurrence and availability can differ.

Choose tie semantics deliberately: `ROW_NUMBER` produces a fixed number of rows under a deterministic secondary order, while `DENSE_RANK` preserves equal primary scores. A predicate on a nullable right-table column in `WHERE` can undo the unmatched-row preservation of a `LEFT JOIN`. Test duplicate events, absent dimension rows, nulls, tied maxima and an empty denominator. These cases explain correctness more convincingly than running only one ordinary example.

Fitting preprocessing on all rows before cross-validation, even when labels were not directly used.

### Check your reasoning on related cases

**Define label windows for click-through-rate analysis.** A category with 2 clicks from 2 impressions has CTR 100% but far more uncertainty than one with 10000 clicks from 20000 impressions.

Why can category comparisons be confounded? Users, positions and exposure policies may differ systematically.

**Find each user's consecutive login-day streaks.** Days 1,2,4,5,6 contain streaks of lengths 2 and 3; multiple logins on day 5 do not lengthen either streak.

How do you count currently active streaks? Restrict run end dates using a stated as-of and grace policy.
