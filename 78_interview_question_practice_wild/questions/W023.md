## Question

Training a large language model needs many accelerators working together, and the choice of hardware and parallel layout decides how fast and how cheaply it trains. Answer the three discussion questions below. For each one, state the idea, give the trade-offs, and say when you would choose it.

### Questions

1. Parallelism in LLM training. Name the forms of parallelism used to train a large language model. Explain data parallelism, model parallelism (tensor parallelism and pipeline parallelism), and the parallelism that happens inside a single GPU. Cover:
what is split across devices and what must be communicated;
the memory and communication cost of each, and which interconnect it needs;
when each is the right choice and how they are combined.
2. CPUs, GPUs and TPUs. Compare the architectures of CPUs, GPUs and TPUs. Cover:
how each is built (core count, control logic, memory, matrix units);
memory bandwidth, interconnect and supported number formats;
which large-scale ML workloads suit each device, and why.
3. From small models to large models. Which lessons from small-model research carry over to large-model research? Cover:
optimization (learning rate, initialization, stability);
generalization and evaluation;
architecture design and ablations;
data quality;
what does not carry over, and how to check before you scale up.

## Worked solution

### Solution outline

#### Compare data, tensor and pipeline parallel training.

They partition different parts of the training work and create different communication patterns.

1. Data parallelism replicates the model across workers processing different batches, then synchronizes gradients.
2. Tensor parallelism splits individual matrix operations and usually requires frequent high-bandwidth communication within layers.
3. Pipeline parallelism assigns groups of layers to stages and streams microbatches through them; balance stages and account for pipeline bubbles. Combine approaches only after estimating memory and network costs.

#### Apply the roofline model to a matrix multiplication.

The roofline compares available compute throughput with the rate at which needed data can reach the processor.

1. For A:(M,K) and B:(K,N), estimate about 2MKN floating-point operations.
2. Estimate bytes moved under an explicit reuse assumption, then compute arithmetic intensity=FLOPs/bytes.
3. The idealized throughput ceiling is min(peak_FLOPs,bandwidth*intensity). Use profiling to include tiling, launch overhead and cache behavior.

#### Explain when small-model lessons transfer to large models.

Mechanisms may transfer, but hyperparameters, bottlenecks and emergent failure patterns need fresh evidence at scale.

1. Separate general correctness facts, such as target alignment, from empirical tuning choices.
2. Study how activation statistics, optimization, data mixture, compute and communication change with scale.
3. Use staged scaling experiments and comparable evaluation rather than extrapolating one small-model ranking blindly.

### Understand why the approach works

#### Follow tensor ownership and the resource bottleneck

For every major tensor, state who owns it before and after each collective. Data parallelism divides examples; tensor parallelism divides operations/weights; pipeline parallelism divides layers. Their communication and memory effects differ, so a diagram saying “use more GPUs” is incomplete.

For $C=AB$, $A\in\mathbb R^{m\times k}$ and $B\in\mathbb R^{k\times n}$, a row partition gives

$$
C_r=A_rB,\qquad C=\operatorname{ConcatRows}(C_0,\ldots,C_{p-1}).
$$

Concatenating output shards is different from summing partial products. Backward communication depends on which variables were replicated and where multiple contributions to the same derivative must be added.

Estimate the bottleneck with a roofline bound:

$$
\text{attainable FLOP/s}\leq
\min\!\left(F_{\rm peak},\;\text{bandwidth}\times\frac{\text{FLOPs}}{\text{bytes moved}}\right).
$$

Then add synchronization, imbalance, launch and checkpoint overhead rather than treating the ideal bound as achieved speed.

For a platform/scheduler, distinguish desired state, observed state and durable job completion. Launching a container or receiving a provider response does not prove the computation succeeded. Checkpoint application state, fence stale owners, publish only complete artifacts and monitor both utilization and tenant wait time. A design that maximizes utilization by starving a large job violates a different important service objective.

### Work a small example

Two data-parallel workers with local batch 8 process a global batch of 16 if one synchronized update uses both batches without extra accumulation.

### Edge cases and common mistakes

Assuming all parallelism reduces per-worker model memory, or ignoring communication when predicting speedup.

### Check your reasoning on related cases

**Apply the roofline model to a matrix multiplication.** If bandwidth is 1 TB/s and intensity is 10 FLOPs/byte, the bandwidth ceiling is 10 TFLOPs/s, even if peak compute is 100 TFLOPs/s.

Why can batching help decode? It reuses weight reads across more tokens, increasing arithmetic intensity.

**Explain when small-model lessons transfer to large models.** A data-cleaning fix may transfer broadly, while the best learning rate or parallelization layout can change substantially.

Which signal would you monitor while scaling? Stability, loss-versus-compute curves and representative downstream evaluations.
