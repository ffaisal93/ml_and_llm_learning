## Question

Training a large language model needs many accelerators working together, and the choice of hardware and parallel layout decides how fast and how cheaply it trains. Answer the three discussion questions below. For each one, state the idea, give the trade-offs, and say when you would choose it.

### Questions

1. Parallelism in LLM training. Name the forms of parallelism used to train a large language model. Explain data parallelism, model parallelism (tensor parallelism and pipeline parallelism), and the parallelism that happens inside a single GPU. Cover:
what is split across devices and what must be communicated;
the memory and communication cost of each, and which interconnect it needs;
when each is the right choice and how they are combined.
2. CPUs, GPUs and TPUs. Compare the architectures of CPUs, GPUs and TPUs. Cover:
how each is built (core count, control logic, memory, matrix units);
memory bandwidth, interconnect and supported number formats;
which large-scale ML workloads suit each device, and why.
3. From small models to large models. Which lessons from small-model research carry over to large-model research? Cover:
optimization (learning rate, initialization, stability);
generalization and evaluation;
architecture design and ablations;
data quality;
what does not carry over, and how to check before you scale up.

## Worked solution

### Partition the work at the correct boundary

Data parallelism replicates weights for different examples and all-reduces gradients; it scales throughput when the model fits per replica, but replicated weights/optimizer consume memory. FSDP/ZeRO shard persistent state and gather layer units, exchanging memory for communication. Tensor parallelism splits operators/weights and communicates partial outputs/gradients each layer, favoring within-node fast interconnects. Pipeline parallelism puts layer groups on different devices and exchanges boundary activations/gradients, with microbatch bubbles and load-balance constraints; it can cross slower links more efficiently than frequent tensor collectives. Context/sequence parallelism partitions long-token activations and attention work; expert parallelism partitions MoE experts with token dispatch/all-to-all.

For example,8 GPUs/node can form one tensor-parallel group; several nodes can be pipeline stages; many such model groups can be data-parallel replicas. Tune that decomposition from model/activation/optimizer memory, batch/context size and measured interconnect. Within one GPU, thousands of threads execute SIMD/SIMT work, blocks tile matrices through registers/shared SRAM, and matrix units execute supported small matrix operations. This intra-device parallelism is distinct from assigning model shards across devices. A collective cannot be justified merely by saying “gather”: concatenate disjoint output rows, but sum contributions to the same derivative.

### CPU, GPU and TPU architecture

| Device | Design and memory | Suitable work and trade-off |
|---|---|---|
| CPU | Relatively few complex latency-oriented cores, branching/speculation, large caches and DRAM; vector units; cache-coherent sockets | Data/control, irregular workloads, modest batches, orchestration; lower large-dense-matmul throughput per watt |
| GPU | Many throughput-oriented execution lanes, registers/shared SRAM, high-bandwidth memory, matrix/tensor units and device links | Dense batched matmul/attention and parallel kernels; launch/transfer overhead, divergence and memory pressure can dominate small work |
| TPU | Specialized matrix/systolic units with vector/scalar support, on-chip buffers, HBM and pod interconnect under a compiler/runtime | Large dense ML and supported distributed graphs; strong throughput when compiler/layout/sharding fit, with less general execution flexibility |

Compare actual generations/capacity/bandwidth/topology and supported FP32/BF16/FP16/FP8/integer modes rather than quoting an eternal core count. Host–device links and cross-device links differ; a fast chip with an unsuitable network can underperform. A roofline gives $\min(peak\ FLOP/s,bandwidth\cdot arithmetic\ intensity)$; batching/tiling improves reuse but does not fix every control-bound path.

### What transfers from small to large

Target alignment, leakage prevention, shape/mask correctness and controlled ablations transfer as invariants. Initialization/normalization, activation and gradient statistics, optimizer moment behavior and schedule design transfer as mechanisms, but best learning rates/batch sizes do not transfer unchanged. Use parameterization-aware scaling rules as hypotheses, then staged pilots with loss-versus-tokens/compute and stability logs.

Generalization/evaluation discipline transfers: decontamination, independent test families, uncertainty and calibration/safety slices. Small-model benchmark order can reverse at large scale, and rare failures/capabilities may appear only with longer training/context. Data provenance/dedup/quality/mixture design matter at every size, while filter thresholds and source balance need scaling audits.

Architectural ablations should hold parameters/tokens/compute as appropriate, change one mechanism, and repeat at several scales rather than extrapolate one point. What often fails to transfer is hardware efficiency: large tensors alter compute/bandwidth balance, collectives and input/checkpoint IO emerge, and failures become normal over weeks. Pilot a representative distributed slice, measure scaling efficiency and communication, extrapolate with explicit bounds, then validate before committing the full training budget.
