## Question

<pre class="question-text" style="white-space:pre-wrap;font-family:inherit;line-height:1.55">Training a large language model needs many accelerators working together, and the choice of hardware and parallel layout decides how fast and how cheaply it trains. Answer the three discussion questions below. For each one, state the idea, give the trade-offs, and say when you would choose it.

Questions
1.
Parallelism in LLM training. Name the forms of parallelism used to train a large language model. Explain data parallelism, model parallelism (tensor parallelism and pipeline parallelism), and the parallelism that happens inside a single GPU. Cover:
what is split across devices and what must be communicated;
the memory and communication cost of each, and which interconnect it needs;
when each is the right choice and how they are combined.
2.
CPUs, GPUs and TPUs. Compare the architectures of CPUs, GPUs and TPUs. Cover:
how each is built (core count, control logic, memory, matrix units);
memory bandwidth, interconnect and supported number formats;
which large-scale ML workloads suit each device, and why.
3.
From small models to large models. Which lessons from small-model research carry over to large-model research? Cover:
optimization (learning rate, initialization, stability);
generalization and evaluation;
architecture design and ablations;
data quality;
what does not carry over, and how to check before you scale up.</pre>

## Worked solution

1. Compare data, tensor and pipeline parallel training. They partition different parts of the training work and create different communication patterns.
2. Data parallelism replicates the model across workers processing different batches, then synchronizes gradients.
3. Tensor parallelism splits individual matrix operations and usually requires frequent high-bandwidth communication within layers.
4. Pipeline parallelism assigns groups of layers to stages and streams microbatches through them; balance stages and account for pipeline bubbles. Combine approaches only after estimating memory and network costs.
5. Apply the roofline model to a matrix multiplication. The roofline compares available compute throughput with the rate at which needed data can reach the processor.
6. For A:(M,K) and B:(K,N), estimate about 2MKN floating-point operations.
7. Estimate bytes moved under an explicit reuse assumption, then compute arithmetic intensity=FLOPs/bytes.
8. The idealized throughput ceiling is min(peak_FLOPs,bandwidth*intensity). Use profiling to include tiling, launch overhead and cache behavior.
9. Explain when small-model lessons transfer to large models. Mechanisms may transfer, but hyperparameters, bottlenecks and emergent failure patterns need fresh evidence at scale.
10. Separate general correctness facts, such as target alignment, from empirical tuning choices.
11. Study how activation statistics, optimization, data mixture, compute and communication change with scale.
12. Use staged scaling experiments and comparable evaluation rather than extrapolating one small-model ranking blindly.

### Small example / sanity check

Two data-parallel workers with local batch 8 process a global batch of 16 if one synchronized update uses both batches without extra accumulation.

### Common trap

Assuming all parallelism reduces per-worker model memory, or ignoring communication when predicting speedup.
