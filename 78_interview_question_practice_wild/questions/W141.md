## Question

<pre class="question-text" style="white-space:pre-wrap;font-family:inherit;line-height:1.55">You are given a table of time-stamped market data (prices and a few candidate predictors) and asked to build a predictive model of future returns, then explain and defend the work to a panel of reviewers. Describe how you would carry out the whole project and which choices you would defend.

Requirements
1.
Frame the problem: state the prediction target, the horizon, the evaluation metric, and your assumptions about the data.
2.
Prepare the data with pandas: resample or align timestamps, compute returns, build lagged and rolling features, and join sources. Explain how each step avoids look-ahead bias.
3.
Choose a model and justify it. A simple, interpretable baseline such as linear regression is acceptable if you can explain why it is enough.
4.
Validate honestly: use time-ordered (walk-forward or expanding-window) splits, report out-of-sample performance, and compare against a naive benchmark such as predicting zero or the mean.
5.
Present the result: problem, data and cleaning, features, model, validation, limitations and next steps.
Follow-ups
Follow-up 1: implementation detail. Walk through one pandas transformation line by line, and say what would break if the index were unsorted or the time zones misaligned.
Follow-up 2: signal or overfit. Explain how you would decide whether the signal is real: out-of-sample stability, robustness across periods, sensitivity to transaction costs, and significance of coefficients.
Follow-up 3: limitations. Name the main limitations: regime dependence, sample size, selection effects in the data, and costs left unmodeled.
Constraints
Every feature needs a stated rationale.
Features at time t may use only information available at or before t.</pre>

## Worked solution

1. Plan a four-hour ML take-home exercise. Budget the work so a reproducible baseline and honest evaluation exist before optional improvements.
2. Spend an initial block clarifying the target, split, metric, data quality and a minimal runnable pipeline.
3. Build and evaluate a baseline, then run one or two prioritized improvements with tracked seeds and configurations.
4. Reserve time for error analysis, clean reruns and a short write-up of assumptions, results and remaining limitations.
5. Fit a baseline on messy tabular data without leakage. Build a trustworthy split and simple baseline before sophisticated feature engineering.
6. Define the target, prediction time and unit of independence, then split by time or group if required.
7. Fit imputation, scaling and category encodings on training folds only. Start with a dummy baseline and a regularized linear or small tree model.
8. Evaluate slices, missingness patterns and calibration; document features unavailable at decision time and remove them.

### Small example / sanity check

A simple model with a valid temporal split and reproducible commands is stronger evidence than an elaborate model evaluated on leaked data.

### Common trap

Using the final hour for one unvalidated architecture change and leaving no runnable result.
