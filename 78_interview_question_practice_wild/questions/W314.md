## Question

A task marketplace lets a customer post a task that a driver completes. The driver then uploads evidence (for example photos) that the task was done. Identify where machine learning adds value across this end-to-end flow.

Flow
1. The customer describes and submits a task.
2. The platform turns the request into instructions and assigns a driver.
3. The driver performs the task.
4. The driver uploads evidence, and the platform accepts or rejects it.

### Requirements

1. Walk through each stage of the flow and name the machine-learning opportunities in it. Candidate areas include using an LLM to collect complete requirements from the customer, generating step-by-step guidelines the driver can follow, and automatically judging the quality of the uploaded evidence.
2. Choose the opportunity you would build first and justify the choice with its expected impact and cost.
3. For each opportunity you propose, specify:
the prediction target or label, and where the labels come from;
the input features or context;
the serving path and its latency budget;
the main failure modes and the fallback when the model is wrong;
the offline and online metrics that show it works.

## Worked solution

### Map each model to a decision and fallback

Assume an asynchronous physical-task marketplace, with a customer draft, accepted task contract, driver assignment and evidence review. Keep the accepted requirements version immutable unless both sides accept a change. Here are four concrete opportunities; their latency budgets are design assumptions to validate.

| Stage / prediction | Inputs and labels | Serving / failure fallback | Offline and online evidence |
|---|---|---|---|
| Submission completeness | Customer text, task type/location constraints; experts label missing required slots and prior clarification outcomes | LLM drafts one clarifying question in ~2 s; deterministic required-field checks and customer confirmation prevent invented requirements | Missing-slot recall, unnecessary-question rate; completed submissions and fewer downstream clarifications |
| Instructions + assignment | Confirmed contract/SOPs; reviewed instruction steps and historic on-time completion/travel labels | Generate grounded steps before acceptance (~2 s); batch rank eligible drivers under ~200 ms; approved template/manual dispatch on uncertainty | Step omission/support, ETA calibration; completion, travel cost and worker fairness |
| Execution assistance | Current confirmed step, user-approved context and driver issue reports; support resolutions | Bounded contextual help in seconds; route unsafe/ambiguous cases to support, never silently change scope | Resolution correctness; fewer blocked/cancelled tasks without safety/complaint increase |
| Evidence quality/completion triage | Uploaded images, capture metadata and task criteria; adjudicated accept/reject/appeal labels | Async media checks in ~5 s; request another photo or human review, no automatic punitive rejection on uncertain output | Per-criterion precision/recall and appeal reversals; review minutes/task, dispute and resubmission rates |

Build **submission completeness first** if missing details are a major measured source of cancellations: it is relatively cheap, prevents downstream rework and keeps the customer in the loop. Pilot one task type with known required fields rather than an unconstrained general agent. Estimate value as avoidable failed tasks × cost/failure minus model/support/latency costs; use observed baseline rates, not invented savings. If most loss is fraudulent evidence rather than incomplete instructions, prioritize evidence triage instead.

The flow is customer draft → typed requirements with provenance → customer-confirmed contract → deterministic eligibility plus ranked drivers → execution → evidence checks → human/approved-policy acceptance. Store task/contract versions, model versions, decision reasons and appeals; a model retries with a stable run key rather than assigning two drivers. Do not let an image's overlaid text alter task policy. For evaluation, split by customer/driver/task family and time, include hard negatives, and distinguish helpful-photo quality from proof the task truly occurred. Online experiments must guard worker pay, unsafe instructions, false rejection and dispute resolution, not merely model acceptance rate.
