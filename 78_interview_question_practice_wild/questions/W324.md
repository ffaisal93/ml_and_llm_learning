## Question

A fitness app logs every workout a user records. Product wants to know how many people use the app each day, month and week, and what they do. Using the schema below, define the engagement metrics precisely and write the SQL queries (PostgreSQL) that compute them.

Schema
users(id, email, signup_date)                    -- signup_date is a date
workout_types(id, name)                          -- e.g. run, yoga, cycle
workouts(id, user_id, workout_type_id,           -- one row per logged workout session
started_at, duration_min)               -- started_at is a UTC timestamp without time zone

workouts.user_id references users.id and workouts.workout_type_id references workout_types.id. All dates and weeks are in UTC, and a week starts on Monday (date_trunc('week', ...)).

What to deliver
1. Schema discussion. In a few sentences, justify the three tables above and say what you would add to support device telemetry (for example a devices table keyed by user) without changing the queries below.
2. Daily active users. A user is *active* on day D if they have at least one workouts row whose started_at falls on day D. Write a query for the parameters :start_date and :end_date (both inclusive dates) that returns the columns day and dau, one row per day that has at least one active user, ordered by day.
3. Follow-up 1: monthly active users. For each day D from :start_date to :end_date inclusive, mau is the number of distinct users active at least once in the 30 days ending on D (D and the 29 days before it). Return day and mau for every day in the range, including days with no activity (then mau counts the earlier days).
4. Follow-up 2: weekly retention. A user's cohort is the week of their first workout. For every cohort week and every week_offset (0 for the cohort week itself, 1 for the next week, and so on) in which at least one cohort member worked out, return cohort_week, week_offset (an integer), cohort_size, retained_users (cohort members with a workout in that week) and retention_rate (retained_users / cohort_size, rounded to 2 decimals).
5. Follow-up 3: favourite workout types. For each user return their three most frequent workout types: user_id, workout_type_id, workouts_count and rank (1, 2, 3). Break ties on count by the smaller workout_type_id. A user with fewer than three types gets fewer rows.
6. Scale. In two or three sentences, say how you would serve these queries for a table with billions of rows (pre-aggregation, partitioning by started_at, and what the trade-off is).

## Worked solution

### Solution outline

1. Define the qualifying activity event, user identity, timezone, bot/test exclusions and observation boundary. Store users, sessions/events and product entities at explicit grains.
2. DAU is COUNT(DISTINCT user_id) per activity day; monthly active users use distinct users over the stated calendar month or trailing 30-day window, which are different definitions.
3. Deduplicate event ids before additive metrics, but distinct-user counts cannot be merged by summing daily counts. Use exact distinct state or a documented approximate sketch for scale.
4. Partition by event date and maintain late-correction policies. Fitness-app data additionally needs a clear distinction between registration, starting a workout and completed qualifying activity.

### Understand why the approach works

#### Establish row grain before writing a join

Say what one output row represents: an event, user, vendor, parent type or time interval. Then inspect the cardinality of every join. Joining two one-to-many relations can multiply rows and inflate both totals and averages; `DISTINCT` is not a general repair because legitimate equal-valued records can also exist.

For mergeable averages store a sum and count:

$$
\bar x_{\rm pooled}=\frac{\sum_g \operatorname{sum}_g}{\sum_g \operatorname{count}_g}.
$$

Do not average subgroup means unless the intended weighting gives each group equal weight. Likewise, daily distinct users cannot be added to obtain monthly distinct users.

Use half-open time windows, such as `timestamp >= start AND timestamp < end`, and name the timezone. For point-in-time training, feature **availability time** must not exceed prediction time; event occurrence and availability can differ.

Choose tie semantics deliberately: `ROW_NUMBER` produces a fixed number of rows under a deterministic secondary order, while `DENSE_RANK` preserves equal primary scores. A predicate on a nullable right-table column in `WHERE` can undo the unmatched-row preservation of a `LEFT JOIN`. Test duplicate events, absent dimension rows, nulls, tied maxima and an empty denominator. These cases explain correctness more convincingly than running only one ordinary example.

### Work a small example

One user active on three days contributes three user-days but one distinct user to that month’s MAU. DAU/MAU should use compatible populations/windows.
