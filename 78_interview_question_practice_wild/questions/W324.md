## Question

<pre class="question-text" style="white-space:pre-wrap;font-family:inherit;line-height:1.55">A fitness app logs every workout a user records. Product wants to know how many people use the app each day, month and week, and what they do. Using the schema below, define the engagement metrics precisely and write the SQL queries (PostgreSQL) that compute them.

Schema
users(id, email, signup_date)                    -- signup_date is a date
workout_types(id, name)                          -- e.g. run, yoga, cycle
workouts(id, user_id, workout_type_id,           -- one row per logged workout session
started_at, duration_min)               -- started_at is a UTC timestamp without time zone

workouts.user_id references users.id and workouts.workout_type_id references workout_types.id. All dates and weeks are in UTC, and a week starts on Monday (date_trunc(&#x27;week&#x27;, ...)).

What to deliver
1.
Schema discussion. In a few sentences, justify the three tables above and say what you would add to support device telemetry (for example a devices table keyed by user) without changing the queries below.
2.
Daily active users. A user is *active* on day D if they have at least one workouts row whose started_at falls on day D. Write a query for the parameters :start_date and :end_date (both inclusive dates) that returns the columns day and dau, one row per day that has at least one active user, ordered by day.
3.
Follow-up 1: monthly active users. For each day D from :start_date to :end_date inclusive, mau is the number of distinct users active at least once in the 30 days ending on D (D and the 29 days before it). Return day and mau for every day in the range, including days with no activity (then mau counts the earlier days).
4.
Follow-up 2: weekly retention. A user&#x27;s cohort is the week of their first workout. For every cohort week and every week_offset (0 for the cohort week itself, 1 for the next week, and so on) in which at least one cohort member worked out, return cohort_week, week_offset (an integer), cohort_size, retained_users (cohort members with a workout in that week) and retention_rate (retained_users / cohort_size, rounded to 2 decimals).
5.
Follow-up 3: favourite workout types. For each user return their three most frequent workout types: user_id, workout_type_id, workouts_count and rank (1, 2, 3). Break ties on count by the smaller workout_type_id. A user with fewer than three types gets fewer rows.
6.
Scale. In two or three sentences, say how you would serve these queries for a table with billions of rows (pre-aggregation, partitioning by started_at, and what the trade-off is).
Example

workouts (id, user_id, workout_type_id, started_at):

1  1  1  2026-03-02 08:00
2  1  2  2026-03-02 18:30
3  2  1  2026-03-02 09:15
4  1  1  2026-03-03 07:45
5  3  3  2026-03-04 12:00
6  2  1  2026-03-09 10:00
7  3  1  2026-03-10 11:00

With :start_date = 2026-03-02 and :end_date = 2026-03-04:

dau:  2026-03-02 -&gt; 2 (users 1 and 2; user 1 worked out twice and counts once)
2026-03-03 -&gt; 1
2026-03-04 -&gt; 1
mau:  2026-03-02 -&gt; 2,  2026-03-03 -&gt; 2,  2026-03-04 -&gt; 3

Weekly retention: all three users first worked out in the week starting 2026-03-02, so that cohort has size 3. In week offset 0 all 3 were active (rate 1.00); in offset 1 (week of 2026-03-09) users 2 and 3 were active (2 of 3, rate 0.67).

Favourite types: user 1 gets (type 1, count 2, rank 1) and (type 2, count 1, rank 2); user 2 gets (type 1, count 2, rank 1); user 3 gets (type 1, count 1, rank 1) and (type 3, count 1, rank 2), because the tie on count goes to the smaller type id.

Constraints
Return exactly the column names given above; the order of columns is as listed.
The queries must work for any date range, including a range of a single day, and must not assume the table is small.</pre>

## Worked solution

1. Define the qualifying activity event, user identity, timezone, bot/test exclusions and observation boundary. Store users, sessions/events and product entities at explicit grains.
2. DAU is COUNT(DISTINCT user_id) per activity day; monthly active users use distinct users over the stated calendar month or trailing 30-day window, which are different definitions.
3. Deduplicate event ids before additive metrics, but distinct-user counts cannot be merged by summing daily counts. Use exact distinct state or a documented approximate sketch for scale.
4. Partition by event date and maintain late-correction policies. Fitness-app data additionally needs a clear distinction between registration, starting a workout and completed qualifying activity.

### Small example / sanity check

One user active on three days contributes three user-days but one distinct user to that month’s MAU. DAU/MAU should use compatible populations/windows.

### Common trap

Adding daily distinct counts to obtain monthly distinct users.
