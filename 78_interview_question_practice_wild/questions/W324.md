## Question

A fitness app logs every workout a user records. Product wants to know how many people use the app each day, month and week, and what they do. Using the schema below, define the engagement metrics precisely and write the SQL queries (PostgreSQL) that compute them.

Schema
users(id, email, signup_date)                    -- signup_date is a date
workout_types(id, name)                          -- e.g. run, yoga, cycle
workouts(id, user_id, workout_type_id,           -- one row per logged workout session
started_at, duration_min)               -- started_at is a UTC timestamp without time zone

workouts.user_id references users.id and workouts.workout_type_id references workout_types.id. All dates and weeks are in UTC, and a week starts on Monday (date_trunc('week', ...)).

What to deliver
1. Schema discussion. In a few sentences, justify the three tables above and say what you would add to support device telemetry (for example a devices table keyed by user) without changing the queries below.
2. Daily active users. A user is *active* on day D if they have at least one workouts row whose started_at falls on day D. Write a query for the parameters :start_date and :end_date (both inclusive dates) that returns the columns day and dau, one row per day that has at least one active user, ordered by day.
3. Follow-up 1: monthly active users. For each day D from :start_date to :end_date inclusive, mau is the number of distinct users active at least once in the 30 days ending on D (D and the 29 days before it). Return day and mau for every day in the range, including days with no activity (then mau counts the earlier days).
4. Follow-up 2: weekly retention. A user's cohort is the week of their first workout. For every cohort week and every week_offset (0 for the cohort week itself, 1 for the next week, and so on) in which at least one cohort member worked out, return cohort_week, week_offset (an integer), cohort_size, retained_users (cohort members with a workout in that week) and retention_rate (retained_users / cohort_size, rounded to 2 decimals).
5. Follow-up 3: favourite workout types. For each user return their three most frequent workout types: user_id, workout_type_id, workouts_count and rank (1, 2, 3). Break ties on count by the smaller workout_type_id. A user with fewer than three types gets fewer rows.
6. Scale. In two or three sentences, say how you would serve these queries for a table with billions of rows (pre-aggregation, partitioning by started_at, and what the trade-off is).
Example

workouts (id, user_id, workout_type_id, started_at):

```text

2  1  2  2026-03-02 18:30
3  2  1  2026-03-02 09:15
4  1  1  2026-03-03 07:45
5  3  3  2026-03-04 12:00
6  2  1  2026-03-09 10:00
7  3  1  2026-03-10 11:00
```

```sql
With :start_date = 2026-03-02 and :end_date = 2026-03-04:
```

dau:  2026-03-02 -&gt; 2 (users 1 and 2; user 1 worked out twice and counts once)
2026-03-03 -&gt; 1
2026-03-04 -&gt; 1
mau:  2026-03-02 -&gt; 2,  2026-03-03 -&gt; 2,  2026-03-04 -&gt; 3

Weekly retention: all three users first worked out in the week starting 2026-03-02, so that cohort has size 3. In week offset 0 all 3 were active (rate 1.00); in offset 1 (week of 2026-03-09) users 2 and 3 were active (2 of 3, rate 0.67).

Favourite types: user 1 gets (type 1, count 2, rank 1) and (type 2, count 1, rank 2); user 2 gets (type 1, count 2, rank 1); user 3 gets (type 1, count 1, rank 1) and (type 3, count 1, rank 2), because the tie on count goes to the smaller type id.

### Constraints

Return exactly the column names given above; the order of columns is as listed.
The queries must work for any date range, including a range of a single day, and must not assume the table is small.

## Worked solution

### Define activity and preserve the required output schemas

`users`, `workout_types` and `workouts` separate identity, reusable type metadata and session facts; foreign keys prevent orphan sessions. Add `devices(id,user_id,kind)` and telemetry keyed by `(device_id,timestamp)` without changing workout-based activity definitions. A workout counts on its UTC start date only; duration crossing midnight does not create a second active day under the stated definition.

```sql
-- DAU; UTC timestamp-without-time-zone input.
SELECT started_at::date AS day,COUNT(DISTINCT user_id) AS dau
FROM workouts
WHERE started_at>=:start_date::date AND started_at<:end_date::date+INTERVAL '1 day'
GROUP BY started_at::date ORDER BY day;

-- Rolling 30-day MAU, including zero-activity output days.
WITH days AS (
 SELECT generate_series(:start_date::date,:end_date::date,INTERVAL '1 day')::date AS day
), user_days AS (
 SELECT DISTINCT user_id,started_at::date AS active_day FROM workouts
 WHERE started_at>=:start_date::date-INTERVAL '29 days'
   AND started_at<:end_date::date+INTERVAL '1 day'
)
SELECT d.day,COUNT(DISTINCT u.user_id) AS mau
FROM days d LEFT JOIN user_days u ON u.active_day BETWEEN d.day-29 AND d.day
GROUP BY d.day ORDER BY d.day;

-- First-workout cohorts use complete available history, not just the report range.
WITH firsts AS (
 SELECT user_id,date_trunc('week',MIN(started_at))::date AS cohort_week
 FROM workouts GROUP BY user_id
), sizes AS (
 SELECT cohort_week,COUNT(*) AS cohort_size FROM firsts GROUP BY cohort_week
), weekly AS (
 SELECT DISTINCT user_id,date_trunc('week',started_at)::date AS active_week FROM workouts
), retained AS (
 SELECT f.cohort_week,(w.active_week-f.cohort_week)/7 AS week_offset,COUNT(*) AS retained_users
 FROM firsts f JOIN weekly w USING(user_id) GROUP BY f.cohort_week,week_offset
)
SELECT r.cohort_week,r.week_offset,s.cohort_size,r.retained_users,
       ROUND(r.retained_users::numeric/s.cohort_size,2) AS retention_rate
FROM retained r JOIN sizes s USING(cohort_week) ORDER BY r.cohort_week,r.week_offset;

-- Exactly three favourite types at most, deterministic count ties.
WITH counts AS (
 SELECT user_id,workout_type_id,COUNT(*) AS workouts_count
 FROM workouts GROUP BY user_id,workout_type_id
), ranked AS (
 SELECT *,ROW_NUMBER() OVER(PARTITION BY user_id ORDER BY workouts_count DESC,workout_type_id) AS rank
 FROM counts
)
SELECT user_id,workout_type_id,workouts_count,rank FROM ranked WHERE rank<=3 ORDER BY user_id,rank;
```

DAU emits only active days in the inclusive report range, implemented as a half-open timestamp range ending at end_date+1 day. MAU here means **rolling 30 days**, not calendar month; generate all output days and include 29 days of pre-range history. A day with no new workouts can still have nonzero MAU. Weekly cohorts come from the first workout over full history, not signup_date or first workout within a filtered report. Deduplicated user/week rows avoid multiple workouts inflating retained users. Numeric division and round produce .67 for 2/3. ROW_NUMBER with type-ID tie-break returns at most three favorites, unlike RANK which can return more.

For the supplied fixture, DAU is 2,1,1 on March 2–4; MAU is 2,2,3; cohort week March 2 has size 3 with retained 3 then 2, rates 1.00/.67. User3's tied types rank type1 before type3. Tests execute equivalent day/window/cohort/favorite calculations in SQLite and compare expected rows; PostgreSQL generate_series/casts are reviewed, not claimed executed on an unavailable server.

At billions of workouts, partition sessions by started_at and maintain exact user-day/user-week presence plus per-user/type counts; query aggregates read these smaller facts. Late sessions require idempotent correction, and exact rolling distinct counts cannot be formed by summing daily distinct totals; use unions/bitmaps or explicitly approximate sketches. Preaggregation trades freshness, correction logic and storage for predictable dashboard cost.
