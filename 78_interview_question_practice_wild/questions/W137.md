## Question

You join a timed debugging exercise: a small backend repository with seeded bugs, a test suite, and an AI coding assistant built into the editor that can see only the file currently open. You have 60 minutes to make as many tests pass as you can. This question gives you one concrete repository state and asks how you would work through it, from reading the test output to submitting a minimal fix.

The repository

A product-review service. The task description lists three broken behaviours:
1. A review containing a banned word is saved and returns 201. It must be rejected with 403 and the body {"error": "review contains banned content", "words": [...]} listing the banned words found.
2. The user's violation count does not go up when a review is rejected.
3. A user is not flagged after their third violation.

The README also states the contract the tests check:

A flagged user cannot add or edit reviews: both return 403 with {"error": "user is blocked"} and nothing is saved.
A rejected review or edit is not saved. Each rejection adds 1 to user.violations and appends the banned words to user.violated_words; the user is flagged when violations reaches 3.
The repository object repo returns copies. A change to a User or Review is kept only after repo.save_user(user) or repo.save_review(review). repo.create_review(...) saves the new review itself.

## Worked solution

### Solution outline

1. Reproduce the failure from a clean checkout and capture the smallest failing input. Read the contract and trace the relevant data/control path before editing.
2. Form one testable hypothesis, inspect logs/stack traces and add a regression case that distinguishes the bug from correct behavior.
3. Make the smallest justified patch, run the regression and relevant surrounding checks, and inspect the diff for unrelated changes. Verify any AI-suggested code against the contract rather than accepting its explanation as evidence.
4. Separate immediate repair from longer-term cleanup: document the underlying invariant, improve interfaces or observability, and prioritize follow-up work by recurrence and impact.

### Understand why the approach works

#### Write the invariant and identify its atomic boundary

A thread-safe container is not enough if an operation spans several individually safe calls. In “check then insert,” the check and insertion must be one logical atomic action; otherwise two workers can both observe absence and both perform the effect.

Use one lock to protect the smallest relevant shared state. For condition variables, wait in a loop that rechecks the predicate after waking, because wakeup alone does not prove the desired state holds. Do not execute arbitrary slow callbacks under a central registry lock: they may block unrelated work or reenter the same system.

Separate pure transformations, state transitions and external I/O. This makes a small deterministic test possible and keeps a refactor from silently changing behavior. For single-flight loading, represent loading/ready/failed state and notify every waiter once; one canceled waiter need not cancel work still needed by others.

Test interleavings, failure after claiming state, shutdown and stale completion callbacks. State the scope honestly: a Python mutex protects cooperating threads in one process, not another process or machine. A concurrent algorithm's linearization point and ownership rules explain correctness more clearly than a list of synchronization primitives.

### Work a small example

If one branch passes a stale cache key, a regression must use two distinct model/input versions so the incorrect sharing becomes observable.

### Edge cases and common mistakes

Changing several suspected causes at once or replacing the failing assertion instead of fixing the cause.

### Check your reasoning on related cases

**A classifier's loss does not decrease. What do you check first?** Passing softmax probabilities into a loss expecting logits applies a second normalization and can produce weak or misleading gradients.

If only validation loss is flat, what changes? Inspect generalization, split mismatch and validation preprocessing rather than only optimizer plumbing.

**How do you find a silent training-data leak?** Near-duplicate support tickets appearing in both train and test can let a model memorize answers without generalizing to new cases.

What should a label-shuffle control do? Performance should fall toward the appropriate chance baseline when genuine signal is destroyed.

**How do you practice an unfamiliar ML coding problem?** For masked loss, “all examples masked” and “very large logits” are more revealing than ten random ordinary batches.

How should you recover from a bug? State the violated invariant, isolate the smallest failing case and fix that cause.
