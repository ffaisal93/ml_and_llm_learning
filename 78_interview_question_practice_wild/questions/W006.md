## Question

Debug a Small GPT-Style Transformer

A small GPT-style transformer in PyTorch is meant to learn next-character prediction on a handful of short strings, with causal self-attention and key/value-cache decoding. Four bugs were injected, and each one is marked in the code with a BUG label. Find them, explain the damage each one does, and fix them. Then adapt the model to a different task.

What to deliver
1. For each of BUG 1 to BUG 4: say what is wrong, the failure mode it causes, and a corrected version of the marked code.
2. Name one line that looks suspicious but is correct, and say why.
3. Follow-up: change the model from next-token prediction into a classifier that tells whether a decimal number is odd or even. Describe the architecture change, the loss, and how the training labels are built.
Where the bugs are
BUG 1 and BUG 2 are in the self-attention module.
BUG 3 is in the handling of positional embeddings.
BUG 4 is in the loss.
Observed symptoms

These are what you see when you run the code below on CPU with PyTorch 2.x.

Example 1, training: the loss falls from about 5.8 to below 0.001 within 100 steps, far faster than a correct model on this data. The samples printed afterwards contain only the prompt digits followed by _ padding, not the training sentences.
Example 2, cache decoding: take a batch x, run gpt(x[:, :-1], mode="prefill"), then gpt(x[:, -1:], mode="decode"). The logits of that single decode step should equal the last position of gpt(x, mode=None). They differ by several units (about 4 in one run).
Example 3, causality: change only the last few tokens of an input. The logits at the earlier positions must not change. They do change, by more than 1 in one run.
Follow-up: odd or even
Input: each example is a decimal number written as exactly 8 characters, left-padded with 0, so "00001234". Tokens are the character codes ord(c), as in the code below.
Output: one class per example, 0 for an even number and 1 for an odd number.
Describe which parts of the model and of loss change, and how the label tensor is created.

### Constraints

Hidden size 64, 4 heads, 4 layers, at most 64 positions, vocabulary 256.
The fixes must keep the public interface: GPT.forward(x, mode) with mode in "prefill", "decode" or None, and GPT.loss(tokens, train_label, mode).

import math

class CausalSelfAttention(nn.Module):
def __init__(self, hiddens, n_heads):
super().__init__()
self.key = nn.Linear(hiddens, hiddens)
self.query = nn.Linear(hiddens, hiddens)
self.value = nn.Linear(hiddens, hiddens)
self.out = nn.Linear(hiddens, hiddens)
self.n_heads = n_heads

self.k_cache = None
self.v_cache = None

def forward(self, x, mode="prefill"):
b, t, c = x.size()

# b, h, t, hd
q = self.query(x).view(b, t, self.n_heads, c // self.n_heads).transpose(1,2)
k = self.key(x).view(b, t, self.n_heads, c // self.n_heads).transpose(1,2)
v = self.value(x).view(b, t, self.n_heads, c // self.n_heads).transpose(1,2)

if mode == "prefill":
self.k_cache = k
self.v_cache = v
elif mode == "decode":
k = torch.concatenate((self.k_cache, k), dim=2)
self.k_cache = k
v = torch.concatenate((self.v_cache, v), dim=2)
self.v_cache = v

att = torch.matmul(q, k.transpose(-2, -1)) # b, h, qt, kt
att = att / math.sqrt(k.shape[-1])

# BUG 1
if mode != "decode":
mask = torch.triu(torch.ones(t, t, dtype=torch.bool)).view(1, 1, t, t)
att = torch.where(mask, att, float('-inf'))

y = torch.matmul(att, v) # b, h, qt, hd

# BUG 2

y = self.out(y)

## Worked solution

### Solution outline

#### Debug a miniature GPT that fails to learn.

Localize the first broken invariant rather than changing many hyperparameters at once.

1. Check shifted labels, causal masking, tensor axes, vocabulary bounds and padding/loss masks on a tiny batch.
2. Check train/eval mode, gradient presence, optimizer steps and parameter changes. Overfit a tiny dataset with dropout disabled as a diagnostic.
3. Compare against a simple trusted baseline; then test generation and caching separately. Record one controlled change and its effect at a time.

#### Add a KV cache and prove equivalence to full-prefix attention.

Previously computed keys and values do not need to be recomputed when a causal decoder receives one new token.

1. During prefill, compute and store all layerwise K and V tensors.
2. At each decode step, project only the new token, append its K,V, and attend its Q over the entire available cache. Use the correct position offset.
3. Compare each step's last-position logits against a fresh full-prefix forward pass in evaluation mode, using tolerances before comparing sampled tokens.

### Understand why the approach works

#### Why the cache preserves the computation

Causality means a previously computed token representation cannot depend on newly appended future tokens. Therefore its layerwise key and value remain reusable in evaluation mode. Cache them separately for every layer, request and compatible model/configuration.

At step $t$, compute only the new query, key and value, append the new K/V, and evaluate

$$
o_t=\operatorname{softmax}\!\left(\frac{q_t[K_1;\ldots;K_t]^\top}{\sqrt d}\right)
[V_1;\ldots;V_t].
$$

The single new query can see **all** cached prefix positions. A naive top-left triangular mask of shape $1\times t$ permits only the first key; if multiple new tokens are processed together, offset query positions by the existing cache length.

For RoPE, apply the correct absolute position to the new Q/K and do not rotate stored keys again. Compare cached last-position logits against a full-prefix run with dropout disabled. Test every prefix length before comparing sampled sequences, because tiny numerical changes near a sampling threshold can cause later samples to diverge.

For the attention interaction alone, cached one-token steps total $O(T^2d)$ across a generated length $T$, versus $O(T^3d)$ if a full growing-prefix attention calculation is redundantly recomputed each step. This excludes architecture-specific projection and prefill costs. The teaching code concatenates arrays and therefore copies memory; production caches normally use preallocation or blocks. Cache correctness is not, by itself, evidence of a particular speedup on a given machine.
