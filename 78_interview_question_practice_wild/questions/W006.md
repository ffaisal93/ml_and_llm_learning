## Question

You are given a small character-level GPT written in PyTorch. It should read the beginning of a string and predict the **next character**. It should also support faster generation by keeping previously computed keys and values in a **KV cache**.

The model has hidden size 64, four attention heads, four layers, a vocabulary of 256 character codes, and a maximum context of 64 positions. The interface is `GPT.forward(x, mode)` and `GPT.loss(tokens, train_label, mode)`.

There are four marked bugs. Find each bug, explain what it breaks, and show the corrected code. Also identify one suspicious-looking line that is actually correct. Finally, adapt the model to classify an eight-digit number as odd or even.

### What do the failures look like?

The training loss drops from about 5.8 to below 0.001 within 100 steps, but generation mostly repeats padding instead of producing the training strings. Two correctness checks also fail:

- Changing future characters changes the model's predictions at earlier positions.
- Processing a prefix and then decoding one token gives different logits from processing the complete sequence at once.

An interview answer needs to explain these failures. Simply lowering the learning rate does not repair the computation.

### The four marked sections

The relevant code is isolated below so you can reason about each bug without reading the entire training script. `b` is batch size, `t` is the number of input tokens, and `c` is hidden size. Inside attention, the projected tensors have shape `(batch, heads, tokens, head_dim)`.

```python
# BUG 1: mask before the attention softmax
if mode != "decode":
    mask = torch.triu(torch.ones(t, t, dtype=torch.bool)).view(1, 1, t, t)
    att = torch.where(mask, att, float("-inf"))

# BUG 2: merge attention heads, after y = attention_weights @ v
# y currently has shape (batch, heads, tokens, head_dim)
y = y.reshape(b, t, c)

# BUG 3: select learned positional embeddings
position_embeddings = self.pos_emb[:, :t, :]

# BUG 4: construct the language-model targets
inputs = tokens[:, :-1]
targets = tokens[:, :-1]
logits = self.forward(inputs, mode=mode)
loss = F.cross_entropy(logits.reshape(-1, logits.size(-1)), targets.flatten())
```

For the cache, the model uses three modes: `None` processes a sequence without using the cache; `"prefill"` processes a prefix and replaces the cache; `"decode"` receives **one new token** and appends its keys and values to the cache.

## Worked solution

### 1. First understand what the model is supposed to learn

Suppose a training string is `CAT`. The useful training pairs are:

| Input seen so far | Character to predict |
|---|---|
| `C` | `A` |
| `CA` | `T` |

We can train both positions in one forward pass. Feed `[C, A]`, use targets `[A, T]`, and ensure the first position cannot attend to the second input token. The causal mask makes the parallel computation behave as if the model saw one prefix at a time.

In symbols, a sequence model learns

$$
p_\theta(x_1,\ldots,x_T)
= p_\theta(x_1)\prod_{i=1}^{T-1}p_\theta(x_{i+1}\mid x_1,\ldots,x_i).
$$

This exercise trains the conditional predictions after the supplied first character. The same idea extends to the first character by introducing a beginning-of-sequence token.

Two things must therefore agree: **position $i$ can read only positions up to $i$, and its target is token $i+1$.** Bugs 1 and 4 break those two rules. Bugs 2 and 3 corrupt the representation used to make the prediction.

### 2. Bug 1: the mask lets the model read the future

**What is wrong?** `torch.triu(...)` keeps the upper triangle, and `torch.where(mask, att, -inf)` retains scores wherever that mask is true. Together, they allow a query to see itself and **later** tokens while blocking earlier tokens.

For three tokens, causal attention must allow the following pattern. Rows are queries; columns are keys:

```text
                 key 0  key 1  key 2
query 0             1      0      0
query 1             1      1      0
query 2             1      1      1
```

**Why does this matter?** During training, a position can look at characters it will not have during generation. This breaks the next-character task and explains why changing a suffix changes earlier logits. It can also make training loss misleadingly good. In this example, Bug 4 separately makes the task easy by rewarding copying, so the loss alone cannot tell you which bug is responsible.

**The fix:** construct a mask that marks *strictly future* positions, then replace those scores with negative infinity.

```python
future = torch.ones(t, t, dtype=torch.bool, device=x.device).triu(diagonal=1)
att = att.masked_fill(future, float("-inf"))
weights = F.softmax(att, dim=-1)
```

Here `True` means **blocked**, because that is how `masked_fill` works. The diagonal stays allowed: a token may read its own current representation when predicting the next character. Negative infinity gives the blocked key zero probability after softmax. `device=x.device` also makes the mask work when the model runs on a GPU.

**How to check it:** change only tokens at positions 4 onward. With dropout disabled, logits at positions 0–3 must stay the same. This tests the property directly, rather than relying on training loss.

### 3. Bug 2: reshaping mixes up the token and head axes

**What is wrong?** The attention result has shape `(B, H, T, D)`. The desired output has shape `(B, T, H * D)`: one row per token, containing that token's output from every head. A reshape changes the dimensions, but it does not swap the head and token axes.

A tiny example makes the error visible. Ignore the batch axis and let each head return one number per token:

```text
Head 0: token 0 → 10, token 1 → 11
Head 1: token 0 → 20, token 1 → 21

Desired rows:       Wrong direct reshape:
token 0: [10, 20]   token 0: [10, 11]
token 1: [11, 21]   token 1: [20, 21]
```

The wrong result has the expected shape, so there may be no runtime error. But its rows no longer mean what the next layer expects. It can even move information between token positions and break causality despite a correct attention mask.

**The fix:** put the token axis before the head axis, then concatenate the head features.

```python
# (B, H, T, D) -> (B, T, H, D) -> (B, T, H*D)
y = y.transpose(1, 2).contiguous().view(b, t, c)
```

`transpose` corrects the axis order. `contiguous` arranges the transposed data so that `view` can safely merge its last two dimensions. `y.transpose(1, 2).reshape(b, t, c)` is also valid; the essential correction is the transpose.

**How to check it:** use the two-head example above and verify that each output row contains features from the same token. Then rerun the causality test. Shape checks alone will miss this bug.

### 4. Bug 3: every decoded token gets position zero

**What is wrong?** `self.pos_emb[:, :t, :]` is correct for a fresh sequence starting at position zero. But cached decoding supplies only one token, so `t` is always 1. The buggy line gives **every new token the position-zero embedding**.

For example, prefill `C, A` at positions 0 and 1. When `T` arrives, it belongs at position 2. A full forward pass knows that; the buggy cached pass adds the embedding for position 0 instead. The two paths now describe different computations, so their logits do not match.

**The fix:** use the number of tokens already cached as the starting position during decoding.

```python
start = self.size_of_kv_cache if mode == "decode" else 0
position_embeddings = self.pos_emb[:, start:start + t, :]
x = self.tok_emb(tokens) + position_embeddings
```

After all layers have processed the tokens successfully, update the cached length:

```python
if mode in ("prefill", "decode"):
    self.size_of_kv_cache = start + t
```

A new prefill starts at zero and replaces each layer's old cache. A stateless `mode=None` call starts at zero and leaves cache state untouched. Reject a request that exceeds the positional embedding table instead of silently reusing positions.

**Why can the old keys and values be reused?** Once causality is correct, an old token cannot depend on future input. Its representation—and therefore its key and value in each layer—stays the same when a new token is appended. The new query attends over those old entries plus its own new entry:

$$
o_t=\operatorname{softmax}\left(
\frac{q_t[K_0;\ldots;K_t]^\top}{\sqrt{d_h}}
\right)[V_0;\ldots;V_t].
$$

For **one-token decode**, every key in that cache is allowed. Skipping a triangular mask in this mode is correct. If you extend the interface to accept several new tokens per decode call, you must instead build a causal mask with the cached-prefix offset; simply skipping the mask would then expose future tokens within the new chunk.

**How to check it:** prefill three tokens, decode the fourth, and compare its logits to the last logits of a fresh four-token forward pass. Repeat after every additional token. Use evaluation mode and compare logits with a numerical tolerance before comparing sampled text.

### 5. Bug 4: the loss rewards copying the input

**What is wrong?** The inputs and targets are both `tokens[:, :-1]`. At each position, the model is asked to output the character it was just given, instead of the next character.

For `CAT`, the buggy pairs are `C → C` and `A → A`. The character's embedding is already available through the residual path, so learning an identity-like mapping is much easier than learning the sequence. Very low loss can therefore coexist with useless generation.

**The fix:** shift the targets one position to the right.

```python
inputs = tokens[:, :-1]       # CAT -> CA
targets = tokens[:, 1:]       # CAT -> AT
```

The complete loss function is:

```python
def loss(self, tokens, train_label=None, mode="prefill"):
    inputs = tokens[:, :-1]
    targets = tokens[:, 1:]
    logits = self.forward(inputs, mode=mode)  # (B, T-1, vocabulary_size)
    return F.cross_entropy(
        logits.reshape(-1, logits.size(-1)),
        targets.reshape(-1),
    )
```

The loss now measures

$$
\mathcal L=-\frac{1}{B(T-1)}
\sum_{b=1}^{B}\sum_{i=0}^{T-2}
\log p_\theta(x_{b,i+1}\mid x_{b,0},\ldots,x_{b,i}).
$$

Pass **raw logits** to cross-entropy; do not apply softmax first. `train_label` is unused for this language-model objective because the targets are derived from the token sequence itself. Keeping the argument preserves the requested interface.

A uniform predictor over this exercise's 256-character vocabulary has loss $\log 256\approx5.545$ nats per predicted character. Real random logits need not be uniform, so an initial value near 5.8 is not itself proof of a bug. Conversely, a correctly trained model can memorize a tiny dataset: the suspicious observation is **low loss combined with failed correctness checks and poor generation**.

The training data also uses `_` for padding. Including many padding targets can make the average loss look better and encourage padding-heavy output. After fixing the four marked defects, consider separate padding metadata and a loss mask if padding should not count. Do not blindly ignore every `_`, because the same character also appears as a meaningful separator in the strings.

### 6. One suspicious-looking line that is correct

The cache concatenates keys and values along dimension 2:

```python
k = torch.cat((self.k_cache, k), dim=2)
v = torch.cat((self.v_cache, v), dim=2)
```

That is correct because the layout is `(batch, heads, sequence, head_dim)`. Dimension 2 is the sequence dimension: append a new **position**, while keeping batch, head count and head width unchanged. Concatenating along the last dimension would change the head width and break the attention calculation.

This assumes the existing cache belongs to the same request and batch. Reset it when starting another sequence. The simple implementation copies tensors when concatenating; that is fine for understanding correctness, while an optimized serving system would usually preallocate or manage blocks.

### 7. Follow-up: classify an eight-digit number as odd or even

Now the task changes. Input `00001234` should produce **one class for the whole number**: class 0 for even, class 1 for odd. We no longer want a vocabulary prediction at every position.

Keep the token embeddings, position embeddings and Transformer blocks. Take the final hidden state at the **last** input position and apply a new linear head with two outputs:

$$
h_{\mathrm{last}}\in\mathbb R^{B\times64},\qquad
z=h_{\mathrm{last}}W+b\in\mathbb R^{B\times2}.
$$

The last position is convenient because the causal mask lets it see the entire eight-character sequence. The first position cannot see later digits, so using it without changing the attention pattern would be inappropriate here.

Build labels from the last digit. Inputs contain character codes, so subtract `ord("0")` before taking the remainder:

```python
labels = (tokens[:, -1] - ord("0")) % 2  # shape (B,), integer classes
hidden = backbone.hidden_states(tokens, mode=None)
logits = parity_head(hidden[:, -1, :])    # shape (B, 2)
loss = F.cross_entropy(logits, labels.long())
```

For `00001234`, the final digit is 4, so the label is $4\bmod2=0$. For `00001235`, it is $5\bmod2=1$. Feed **all eight characters**, not `tokens[:, :-1]`: dropping the last character would remove the digit that determines parity. Do not use shifted language-model targets for this classifier.

A Transformer is unnecessary for decimal parity; a last-digit rule solves it exactly. The purpose of the follow-up is to show that you understand how a sequence model's representation, prediction head and training targets change when the task changes.

### 8. Verify the repairs before training

Fix all four bugs, then run three checks on small inputs:

| Check | Procedure | What it establishes |
|---|---|---|
| Causality | Change a suffix; compare earlier logits. | The full computation, including head merging, cannot leak future input. |
| Cache equivalence | Compare each cached decode step with a fresh full-prefix forward pass. | Cached keys/values and position offsets preserve the computation. |
| Target alignment | Compare `loss(...)` with cross-entropy against `tokens[:, 1:]`. | The objective predicts the next character instead of copying the current one. |

Also check that gradients are finite and that a new prefill replaces an earlier request's cache. These tests do not require a corpus download or a long training run.

### How to explain the answer in an interview

“The intended task is to predict the next character using only the current prefix. The mask is reversed, so it exposes future tokens. The attention output is reshaped before its token and head axes are reordered, so features land in the wrong token rows. Cached decoding restarts positional embeddings at zero instead of continuing from the cache length. Finally, the targets equal the inputs, so the loss rewards copying. I would fix those four computations, then verify causality, full-versus-cached logits, and shifted targets before tuning training. For parity classification, I would use the last hidden state, a two-class head, and one label derived from the last digit.”

For background, see [attention and KV caching](../02_attention_and_decoding_code.md#f013). The key is to connect each correction to the computation it restores, rather than listing general debugging tips.
