## Worked solution

### Solution outline

#### Why do prefill and decode have different bottlenecks?

Prefill processes many prompt tokens together; decode repeatedly produces the next token for each active request.

1. Prefill uses larger matrix operations and can often exploit substantial parallel compute.
2. Decode at small batch sizes frequently rereads large weights for relatively little work and also reads a growing KV cache.
3. Measure arithmetic intensity, batch size, sequence length and hardware. The bottleneck can change; “prefill compute-bound, decode bandwidth-bound” is a useful tendency, not a universal law.

#### Explain continuous batching and paged KV storage.

Continuous batching changes the active set between generation steps; paged storage makes growing caches easier to allocate.

1. Admit new requests as capacity becomes available and remove finished requests instead of waiting for a fixed batch to complete.
2. Store each request's KV sequence in fixed-size blocks referenced by a logical block table, allowing physical blocks to be non-contiguous.
3. Track live-token memory, fragmentation, eviction and scheduler fairness. Paged allocation changes storage management; it does not change what attention means.

#### Estimate an LLM serving capacity budget.

Capacity is constrained by memory, computation, memory traffic and arrival patterns, so one parameter count is insufficient.

1. Estimate weight bytes, KV bytes for the live-token budget, temporary buffers and runtime overhead.
2. Benchmark prefill and decode at representative lengths and concurrency; measure throughput and tail latency together.
3. Set admission limits below the measured saturation point and handle overload with bounded queues, rejection or a stated fallback.

### Understand why the approach works

#### Separate service time, queueing and memory

A request's observed latency is not just the model kernel duration:

$$
T_{\rm request}=T_{\rm queue}+T_{\rm preprocess}+T_{\rm prefill}
+T_{\rm decode}+T_{\rm delivery}.
$$

Prefill processes the prompt; decode repeatedly adds tokens. Measure both time to first token and inter-token latency, because a configuration can improve aggregate throughput while worsening the user's experience. Batching amortizes work but may increase waiting.

Estimate the KV tensor budget independently of fixed weights. For equal-length requests,

$$
M_{\rm KV}=2BLT H_{\rm KV}d_h s,
$$

where $L$ is layer count, $T$ cached length and $s$ bytes per element. The factor two is keys plus values. With $L=32$, $T=4096$, $H_{\rm KV}=8$, $d_h=128$, $B=1$ and $s=2$, the raw cache is $512$ MiB, before allocator overhead.

Use measured capacity to set admission and live-token limits. If a worker serves batches of at most $b$ in $s_b$ seconds, $b/s_b$ is an optimistic service-rate ceiling, not a per-request guarantee. Sustained arrivals above that rate grow backlog; even lower averages can hide damaging bursts. Bound queues, define cancellation and partial-failure behavior, and compare latency on matched length/concurrency distributions rather than one isolated request.

One request with a long prompt can have high time-to-first-token, while a large active batch can increase inter-token latency.
